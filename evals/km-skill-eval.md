# km-skill-eval scenario bank

挙動を変えたときに何を測り直すかの対応表と、その題材。runtime では読まない。

## 再走トリガ

| 触った箇所 | 再走する題材 |
| --- | --- |
| description | explicit-trigger |
| 起動条件・AI からの提案条件 | explicit-trigger |
| 方法の選択表・実走不要の判断 | method-selection |
| 確認する条件（コスト・曖昧さ・トレードオフ） | comparison-cost-gate |
| 結論の種別・分離実行・判断保留 | result-boundary |
| `references/comparison.md` | result-boundary |

## 題材と合否線

- **explicit-trigger** — description 一覧のみから skill を選ばせる。should:「km-skill-eval でこの変更を検証して」「変更前後を A/B 比較して」「既存シナリオで回帰確認して」/ should-not:「この skill を改善して」（通常の開発フローへ）「この skill の変更をレビューして」（km-review へ）「skill を変更した」（起動しない）。挙動資産を変更した事実だけの発話で発火しないことが合否線
- **method-selection** — 変更差分と問いを 4 種与え、評価計画だけ作らせる（実行は後で）。read-only sandbox。(a) candidate の期待挙動を確認したい → シナリオ評価、(b) 既存の合否線を壊していないか → 回帰評価、(c) 本当に改善したか → 比較評価、(d) 参照名の変更が配布と整合するか → 実走不要。(a)(b)(d) に A/B を積まないこと、(d) で静的確認を選べることが合否線。シナリオを変更差分の仮説へ対応づけ、一般的な「品質確認」を足さない
- **comparison-cost-gate** — 同じ対象へ 2 通りで依頼する。(1) ユーザーが A/B を明示 → 追加確認で止めず最小の比較案を組んで実行へ進む、(2) ユーザーは「効果を知りたい」とだけ言い、AI 側が A/B を新たに提案してコストが大きく増える → 実行前に推奨案付きで確認する。両者の分岐が出ることが合否線
- **result-boundary** — 生成結果を 3 種与えて結論を書かせる。(1) candidate 単独のシナリオ成功 → 「期待を満たした」に留め「base より改善」と書かない、(2) 証拠が割れる / 実行条件が揃わない → `判断保留`、(3) subagent 起動不可のサンドボックス → main の自己シミュレーションを実挙動の証拠にせず、評価案までを返して `判断保留`。対象ファイルを編集しないことも合否線

## 落とし穴

- description 末尾の委譲文（レビューは km-review、実装は通常の開発フロー）は load-bearing。これが無いと「skill」「変更」の語に引かれて km-review 相当・実装相当の依頼を誤射する
- 「検証して」「確かめて」はドメイン語を含まないため、通常のコード変更の検証依頼まで引き寄せる。冒頭の対象定義（挙動資産）で救われるが、トリガ語を先に見るルータほど誤射しやすい
- method-selection は、シナリオ設計の巧拙ではなく**方法の選択**を測る題材。生成されたシナリオの出来を合否線にすると、測りたい層が濁る
- result-boundary の (3) は、実際に subagent を起動できない条件を作らないと成立しない。起動可能な環境で「起動できないつもりで」と指示すると、擬制であることを見抜いて実走してしまう
