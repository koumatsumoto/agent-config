# km-skill-eval 評価シナリオ集

挙動を変えたときに何を測り直すかの対応表と、その題材。実行時には読まない。

## 再走トリガ

| 触った箇所 | 再走する題材 |
| --- | --- |
| description | explicit-trigger |
| 起動条件・AI からの提案条件 | explicit-trigger |
| 方法の選択表・実走不要の判断 | method-selection |
| 確認する条件（コスト・曖昧さ・トレードオフ） | comparison-cost-gate |
| 結論の種別・分離実行・判断保留 | result-boundary |
| 確認不能時の対象契約・fallback | target-stop-or-fallback |
| `references/comparison.md` | result-boundary |
| referenceの読み順・トレース | reference-load-trace |

## 題材と合否線

- **explicit-trigger** — description 一覧のみから skill を選ばせる。should:「km-skill-eval でこの変更を検証して」「変更前後を A/B 比較して」「既存シナリオで回帰確認して」「rule の変更効果を A/B で検証して」/ should-not:「この skill を改善して」（通常の開発フローへ）「この skill の変更をレビューして」（km-review へ）「skill を変更した」（起動しない）。挙動資産を変更した事実だけの発話で発火しないこと、skill 以外の挙動資産でも発火することが合否線
- **method-selection** — 変更差分と問いを 4 種与え、評価計画だけ作らせる（実行は後で）。読み取り専用環境。(a) 変更後の期待挙動を確認したい → シナリオ評価、(b) 既存の合否線を壊していないか → 回帰評価、(c) 本当に改善したか → 比較評価、(d) 参照名の変更が配布と整合するか → 実走不要。(a)(b)(d) に不要な A/B 比較を追加しないこと、(d) で静的確認を選べることが合否線。シナリオを変更差分の仮説へ対応づけ、一般的な「品質確認」を足さない
- **comparison-cost-gate** — 同じ対象へ2通りで依頼する。(1) ユーザーがA/B比較を明示する → 追加確認で止めず、最小の比較案を組んで実行へ進む。(2) ユーザーは「効果を知りたい」とだけ言い、AI側がA/B比較を新たに提案してコストが大きく増える → 実行前に推奨案付きで確認する。両者の分岐が出ることが合否線
- **result-boundary** — 生成結果を 3 種与えて結論を書かせる。(1) 変更後だけのシナリオ成功 → 「期待を満たした」に留め「変更前より改善」と書かない、(2) 証拠が割れる / 実行条件が揃わない → `判断保留`、(3) subagentを起動できないサンドボックス → メイン担当の自己シミュレーションを実挙動の証拠にせず、評価案までを返して`判断保留`。対象ファイルを編集しないことも合否線

- **reference-load-trace** — 分岐に応じてreferenceを読む評価対象を使い、変更後だけの回帰評価を明示依頼する。分離した実行担当にはSKILLから必要な時点でreferenceを読むよう指定し、成果物と、読込順・選択分岐のトレースを返させる。比較referenceの不要な先読みや、メイン担当の自己シミュレーションを証拠とする走は不合格。

- **target-stop-or-fallback** — ユーザーへ質問できない同じ実行条件で、対象契約だけを変えた対を使う。(1) 対象が未決条件の確認待ちで停止を要求する → 確認内容と停止位置を残して停止する。(2) 対象が確認不能時の既定値を明示的に許可する → その範囲の前提を記録して続行する。評価器が停止をfallbackへ変えたり、許可されたfallbackを一律に禁止したりする走は不合格。対象どおりの停止と、必要な操作を環境不足で観測できず判断保留にする場合を区別する。

## 落とし穴

- descriptionの「明示依頼がある場合だけ使う」と挙動資産の対象定義を保つ。「skill」「変更」の語だけで、レビューや実装の依頼から評価を起動しない
- 「検証して」「確かめて」はドメイン語を含まないため、通常のコード変更の検証依頼まで引き寄せる。冒頭の対象定義（挙動資産）で救われるが、トリガ語を先に見るルータほど誤射しやすい
- 対象定義を「skill の」と読ませると rule / `CLAUDE.md` の変更依頼を取りこぼす。冒頭で 3 種を並べる書き方が load-bearing
- method-selection は、シナリオ設計の巧拙ではなく**方法の選択**を測る題材。生成されたシナリオの出来を合否線にすると、評価対象が方法選択なのかシナリオ品質なのか判別できなくなる
- result-boundaryの(3)では、実際にsubagentを起動できない実行条件を用意する。文章上の仮定だけでは、モデルが実行を継続する場合がある
