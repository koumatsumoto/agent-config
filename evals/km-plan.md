# km-plan 評価シナリオ集

挙動を変えたときに何を測り直すかの対応表と、その題材。実行時には読まない。

## 再走トリガ

| 触った箇所 | 再走する題材 |
| --- | --- |
| description | trigger-pairs |
| 確認段階でユーザーに聞く条件 | question-gate |
| 計画の情報量と拘束の線引き / 必要な保留事項 | decision-handoff / detail-deferral |
| 独立レビューの起動条件 | reviewer-routing |
| blocker の条件・指摘の扱い | blocker-convergence |
| 作業ファイル / issue反映 | plan-publication |

## 題材と合否線

- **trigger-pairs** — description 一覧のみから skill を選ばせる。should:「この機能の実装計画を issue にして」「この構造変更の背景と判断理由を残した計画を作って」/ should-not:「この bug をさくっと直して」（skill を挟まず直接実装へ）「実装が終わったので PR にして」（km-github-workflow へ）「この diff をレビューして」（km-review へ）。隣接 skill との境界と「計画を作り込む価値が無い小さな依頼」の両方を切り分けられているかを見る
- **question-gate** — 可逆な実装分岐（内部データ構造の選択など）と、ユーザーが持つ重要なトレードオフ（対外互換を切るか維持するか）を同時に含む依頼。可逆な分岐を自分で決め、トレードオフだけを選択肢 + 推奨付きで聞くのが合格。可逆な分岐まで質問へ寄せる走、トレードオフを無断で決める走はどちらも不合格
- **decision-handoff** — 複数ファイル・コンポーネントにまたがり、現実的な設計案が 2 つある変更（例: 既存 writer の再利用と新規 exporter 層の追加が並び立つ CLI サブコマンド追加）で「計画を issue にして」。読み取り専用環境で実行し `gh` 相当はテキスト報告させる。背景・現在地・各コンポーネントの責務・採用理由・代替案の不採用理由・トレードオフ・実装者の自由度が本文に残り、会話を読まない別 AI が調査をやり直さず着手できるかを見る。ゴールと作業一覧だけの本文や、より単純な設計で目的を達成できるのに過剰な新規 layer・framework・abstraction を無条件に採用し、長期的なアーキテクチャ負債を持ち込む走は不合格
- **detail-deferral** — 内部ライブラリの細かな挙動・個別の異常系・テスト境界が実装中にしか確定しない変更。計画時に全列挙・過剰調査せず、必要な保留事項に、確認・決定する内容、保留する理由、どこで何を確認すれば決められるかが揃うのが合格。見出し名は問わない。異常系を計画本文で網羅した実行、blocker 級の未決を実装へ送った実行は不合格
- **reviewer-routing** — 不確実性の異なる題材を並べて起動判断を見る。(a) 既存パターンの直接適用で、見直し後に残る不確実性が無い → 独立レビューを起動しない。(b) スキーマ / 移行 / 認可境界を変えるが、メイン担当が repo と一次情報から設計を確定でき不確実性が残らない → **カテゴリを理由に起動した走は不合格**。(c) 方式選択を誤ると広い手戻りになり、repo・一次情報だけではメイン担当が決着できず、別視点の検証が計画を変えうる → 独立レビューを使う。計画の長さ・ドキュメントだけの変更・規模を理由にレビューを増やした走は不合格
- **blocker-convergence** — 局所仕様は満たすがユーザーの主目的を満たさない計画（誤ゴール）と、可逆な改善提案を混ぜる。誤ゴールを止め最小の解消策がゴール・スコープの修正を指すこと、可逆な提案を重大な未決にしないこと、修正後はメイン担当が解消を確認すること、必要な保留事項が残っていてもissueを完成できることを見る
- **plan-publication** — GitHub Issueへ反映する計画を作る。新規Issueでは`prepare-plan.js`で本文ファイルを用意し、完成した計画を`--body-file`で反映する。既存Issueではmarkerの有無に関係なく、指定されたIssueの現在本文を踏まえて依頼範囲を更新する。保留事項は固定見出しを要求せず、必要な場合だけ内容・理由・確認先を引き継ぐ。helperへ計画内容の生成・評価やGitHub操作を任せず、反映に失敗した場合は成功扱いしなければ合格

## 落とし穴

- 「issue にして」は、計画作成を求めているのか、単純な issue 起票だけを求めているのかを依頼内容から判断する。実装・PR提出を伴わない issue 作成だけの依頼を、km-github-workflow による実装・提出へ広げない
- 本文の情報量は文字数で採点しない。見るのは「再調査を防げているか」と「実装経路を不要に固定していないか」の 2 軸で、長い本文が細切れの作業手順と教科書的説明で埋まっている走は decision-handoff でも不合格
- helperの一時ファイル作成はunit testで確認する。evalでは計画内容の品質、必要な保留事項、Issueへの反映を見て、helperの内部実装検証と混ぜない
