# km-plan 評価シナリオ集

挙動を変えたときに何を測り直すかの対応表と、その題材。実行時には読まない。

## 再走トリガ

| 触った箇所 | 再走する題材 |
| --- | --- |
| description | trigger-pairs |
| 確認段階でユーザーに聞く条件 | question-gate |
| 冒頭の情報量と拘束の線引き / goal-contract.md の入れるもの・実装時確認事項 | decision-handoff / detail-deferral |
| 独立レビューの起動条件 | reviewer-routing |
| blocker の条件・指摘の扱い | blocker-convergence |

## 題材と合否線

- **trigger-pairs** — description 一覧のみから skill を選ばせる。should:「この機能の実装計画を issue にして」「この構造変更の背景と判断理由を残した計画を作って」/ should-not:「この bug をさくっと直して」（skill を挟まず直接実装へ）「実装が終わったので PR にして」（km-github-workflow へ）「この diff をレビューして」（km-review へ）。隣接 skill との境界と「計画を作り込む価値が無い小さな依頼」の両方を切り分けられているかを見る
- **question-gate** — 可逆な実装分岐（内部データ構造の選択など）と、ユーザーが持つ重要なトレードオフ（対外互換を切るか維持するか）を同時に含む依頼。可逆な分岐を自分で決め、トレードオフだけを選択肢 + 推奨付きで聞くのが合格。可逆な分岐まで質問へ寄せる走、トレードオフを無断で決める走はどちらも不合格
- **decision-handoff** — 複数ファイル・コンポーネントにまたがり、現実的な設計案が 2 つある変更（例: 既存 writer の再利用と新規 exporter 層の追加が並び立つ CLI サブコマンド追加）で「計画を issue にして」。読み取り専用環境で実行し `gh` 相当はテキスト報告させる。背景・現在地・各コンポーネントの責務・採用理由・代替案の不採用理由・トレードオフ・実装者の自由度が本文に残り、会話を読まない別 AI が調査をやり直さず着手できるかを見る。ゴールと作業一覧だけの本文や、より単純な設計で目的を達成できるのに過剰な新規 layer・framework・abstraction を無条件に採用し、長期的なアーキテクチャ負債を持ち込む走は不合格
- **detail-deferral** — 内部ライブラリの細かな挙動・個別の異常系・テスト境界が実装中にしか確定しない変更。計画時に全列挙・過剰調査せず、実装時確認事項に、確認・決定する事項、保留する理由、どこで何を確認すれば決められるかが揃うのが合格。異常系を計画本文で網羅した実行、blocker 級の未決を実装時確認事項へ落とした実行は不合格
- **reviewer-routing** — 3 種を並べて起動判断だけを見る。(a) 既存パターンの直接適用で、メイン担当の反証後に残る不確実性が無い → 独立レビューを起動しない。(b) スキーマ / 移行 / 認可境界を変えるが、メイン担当が repo と一次情報から設計を確定でき不確実性が残らない → **カテゴリを理由に起動した走は不合格**。(c) 方式選択を誤ると広い手戻りになり、repo・一次情報だけではメイン担当が決着できず、別視点の検証が計画を変えうる → 1 名を起動し、担当する反証命題を渡す。**複数カテゴリに触れることを理由に 2 名起動した走、計画の長さ・ドキュメントだけの変更・規模で決めた走は不合格**
- **blocker-convergence** — 局所仕様は満たすがユーザーの主目的を満たさない計画（誤ゴール）と、可逆な改善提案を混ぜる。誤ゴールを blocker として止め最小の解消策がゴール・スコープの修正を指すこと、可逆な提案を blocker にしないこと、**確定した blocker の修正後はメイン担当が解消を確認し、同じ指摘のために新しいレビュアを起動しないこと**、実装時確認事項が残っていても issue を完成できることを見る

## 落とし穴

- 「issue にして」は計画を伴わない issue 起票まで引き寄せる。km-github-workflow は後続 issue の起票を PR 作成・提出の契約に含むため、この一語でトリガ語と責務範囲が交差する
- 本文の情報量は文字数で採点しない。見るのは「再調査を防げているか」と「実装経路を不要に固定していないか」の 2 軸で、長い本文が細切れの作業手順と教科書的説明で埋まっている走は decision-handoff でも不合格
- 設計案の形式要件（`<!-- km:plan:managed -->` / 「実装時確認事項」節名 / `--body-file` 全文ミラー）は成果物を見れば決まる決定的チェック。題材の評価軸に混ぜると形式要件の評価が大きくなり、測りたい設計判断を判別できなくなるため、契約チェックとして別に確かめる
