# Skill Verification (A/B 運用テスト)

`templates/skills` のような prompt / rule / skill の変更は、diff の静的レビューだけでは「意図した挙動改善が実際に起きるか・既存挙動を退行させないか」を判定できない。変更したものをサブエージェントで実際に動かし、base 版（変更前）と candidate 版（変更後）の挙動を A/B 比較し、**質を評価してから採用する**。

## 評価軸（最重要）

評価するのは「**この指示に従うと開発の成果物・判断の質が高まるか**」。手順や分岐が発火したか（前提で停止した・委譲が起きた等）は手段の健全性チェックに過ぎず、それを改善判定のベースにしない。

質の観点:

- 目的達成: ユーザーが本当に達成したいこと（ビジネス価値）を的確に捉え達成しているか
- スコープ判断の的確さ: 同 PR / follow-up / 対象外 の振り分けが過不足ないか
- 成果物の質: issue / PR 本文・コミット分割・報告が、読み手が次工程に進める質か
- 手戻り / 事故リスク: 無関係変更の混入・scope 逸脱・停滞を招く判断がないか

## 手順

1. **対象の特定**: 変更した skill を決め、base 版（`git show <ref>:<path>` で変更前）と candidate 版（作業ツリー）を用意する。references があれば一式揃える（base 版は一時ディレクトリに再現し、相対参照を解決できるようにする）
2. **題材タスクの設計**: 判断を要する代表タスクを用意する。発火確認用の単純シナリオではなく、スコープ判断・follow-up 判断・レビュー対応・報告など**質の差が出る**タスクにする。変更が触れた分岐・既定・gate を踏ませる
3. **成果物生成 A/B**: 素のサブエージェントを 2 体、同一メッセージで並列起動する。各々に base 版 / candidate 版の skill **だけ**を絶対パスで渡し（独立・公平）、題材タスクの**実際の成果物**（ブランチ名・issue / PR 本文・コミット分割・スコープ判断・最終報告）を生成させる。実コマンドは実行させず（副作用なし）、「skill に書かれていないことは推測で足さない」と指示する
4. **independent judge**: 第三のサブエージェントに、**どちらが base / candidate か伏せて** 2 成果物と題材タスクを渡し、上記「評価軸」で各観点の優劣・総合判定・各版の長所/短所を返させる
5. **自分でも分析**: judge に丸投げせず、自分でも 2 成果物を評価軸で分析する。**judge の結論も自分の結論も疑い**、根拠を成果物で裏づけてから採用する。judge と自分の判定が割れたら、なぜ割れたかを詰める
6. **改善反映と再テスト**: 観測された退行・曖昧さ・矛盾を candidate に反映する。分岐や既定を変えたら、その点が意図どおり働くか再テストする。**改善が実挙動で観測できなければ採用しない**
7. **記録**: 試した題材タスク・期待した質・実際の質・判定（採用 / 不採用）を、その変更の PR またはレビュー報告に残す

## このスキル自体の改善（自己改善）

このスキルを使って検証を回す過程で、このスキル自体の改善点（題材タスクの選び方・judge の観点・手順の過不足など）に気づくことがある。

- 気づいた改善点はそのつどメモに残す（`.plan/` 配下の作業メモ等）
- 検証作業そのものとは混ぜず、溜まった改善点は最終的に**このスキルの自己改善 PR** として別途起票する

## 責務の境界

- 変更の正しさ（バグ・設計・セキュリティ）の指摘は `km:review` の責務。本スキルは「変更で開発の質が上がるか」の A/B 運用テストに絞る
- A/B と judge に使うサブエージェントは実環境の subagent 機構（Claude Code の Task tool 等）を使う
