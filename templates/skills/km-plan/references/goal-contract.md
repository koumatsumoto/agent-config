# 設計ブリーフの書き方

`.plan/` に書き出す本文（= GitHub issue 本文）に何を入れるか。固定テンプレートではなく、節名・順序・粒度は計画ごとに決める。ただし該当する情報を意図なく落とさない — 読み手は会話を知らない他 AI か未来の自分で、**issue 単体で設計判断を再利用でき、実装経路だけを自分で選べる**状態にする。

## 入れるもの

- **ゴール** — 達成すること（満たすビジネス価値・要件）/ やらないこと（scope 境界）/ 完了条件。完了条件は今回固有のものだけ書き、repo 全般の規範・delivery 一般条件は再掲しない。計画を左右する非機能（性能・サイズ・保守性・トークン効率）があればその合否条件も入れる
- **背景・問題構造** — 何が起きているか、なぜ問題か、放置するとどうなるか、なぜ今扱うか
- **現在地・依拠する事実** — 現在の構造・責務・data flow、関係するファイル / interface / 設定 / 外部契約、load-bearing な制約・依存・前提。設計方針・scope・feasibility・完了条件を左右する事実には出典（`file:line`・コマンド出力の要点）を付け、最新性が要るものは確認時点も残す。すべての記述に出典は要らない
- **設計方針** — どの層で何をどう変えるか、target state の構造と flow、維持するもの、なぜこの粒度・境界で解くか。**課題に対して過剰な仕組みを持ち込んでいないか**をここで説明できないなら、方針がまだ決まっていない
- **主要な設計判断** — 決定 / 理由 / 根拠・制約 / 現実的な代替案と不採用理由 / 影響・trade-off / この計画で固定する範囲 / 実装者に残す自由度 / 再検討する条件。省くと実装者が別の方向へ進みやすい判断だけを書き、小さな選択すべてにこの形式を強制しない
- **変更 map** — ファイル・コンポーネント・契約ごとに、現在の責務 / 変更後の責務 / 具体的に変える内容 / 波及先 / 維持する不変条件。単なるファイル一覧にせず、「どこを・何のために・どこまで」が分かる形にする
- **実装 slice** — 手順書ではなく成果単位の列。各 slice に 得る成果 / 対象 file・component・contract / 具体的な変更 / 依存と順序制約 / completion evidence / 関連する実装時確認事項。内部関数単位の microtask にしない。小さい変更は 1 slice でよい。1 issue を複数 PR に割るなら切れ目も示す
- **検証** — どの完了条件を、何を実行・観測して、どう合否判定するか（テスト・静的解析・手動確認）
- **risk・trade-off** — risk / 影響 / 緩和 / 残す理由 / 再評価条件。レビューで受け入れたリスクもここに書く（書かずに残すと次のレビューで再提起される）。severity enum は必須にしない
- **実装時確認事項** — 下記

作業ログ・レビューの往復・過去版の変遷は本文に書かない。

## 言葉より参照が強いとき

説明を書くより**指させるほうが高精度**なら指す。移植元の実装、完了条件を体現する失敗テスト、既存の類似実装、HTML モック、判断基準そのものを書いた rubric。散文で再現すると劣化コピーになる。ただし GitHub の読者が開けるものに限る（`.plan/` のローカルパスは参照先にしない）。

architecture・data / control flow・状態遷移・責務境界が文章だけでは誤読されるなら Mermaid を使う。コンポーネント数では決めず、図が判断と handoff の精度を上げるかで決める。

## 書き出し前の lint

- **決定情報が足りているか** — 背景・現在地・判断理由・変更 map から、実装者が調査をやり直さず、別の設計方向へ逸れずに着手できる。current state と target state の差が具体的か
- **過剰に拘束していないか** — 内部構造・全 edge case・全 test case・逐次手順を固定していない。実装 slice が microtask 化していない
- **設計方針が課題に見合っているか** — 方針の複雑さ自体が主要な判断なら、より単純な代替とそれを採らない理由を書く。過剰な仕組みは実装後に最も高くつく
- **完了条件が反証可能か** — 第三者が具体的な evidence で合否を判定でき、**「これで不合格になる具体入力」を 1 つ挙げられる**。数値閾値は数値そのものに意味があるとき（ユーザ要求・公開契約・性能 budget）だけ使い、偽の数値を発明しない。質的な成果は観測手続きと不合格条件で反証可能にする
- **判定と責任境界が曖昧でないか** — ヘッジ表現（十分 / 適切に / なるべく / 一定の 等）が合否や担当の境界をぼかしていないか。語の有無でなく、判定できるかで見る
- **ゴールが内部整合しているか** — 完了条件がゴールに無い変更・撤去を要求していない。ゴールの約束をどの完了条件も担っていない欠けがない
- **outcome に経路があるか** — 各主要 outcome に実装 slice と検証があり、どの outcome にも紐づかない slice が無い。例外は km-github-workflow へ委譲する PR 作成・ブランチ操作・報告
- **one-way door を暗黙に決めていないか** — 公開契約・schema・migration・trust boundary・不可逆操作を、判断として明示せず本文へ埋めていない
- **実装時確認事項に blocker を逃がしていないか**
- **出典が生きているか** — 出典付き主張は書き出し時点で引用先を開き、行番号・内容の一致を確認する（誤引用をレビューまで生き残らせない）

## issue 全文ミラーの前提

- `<!-- km:plan:managed -->` を本文先頭近く（タイトル直下など）に 1 行置く。km-plan 管理 issue の識別子
- issue URL の placeholder を本文に用意する（作成後に書き込んで再同期する）。issue title 案は本文に埋め込まず、`gh issue create --title` に渡す値としてチャットで提示する
- skill 内部の用語・段階名を本文に書かない（読者は skill を知らない）。画像・リンクは GitHub 上で開けるものだけ。コードブロックには言語 tag を付ける

## 実装時確認事項

可逆性で「実装時に詰めるほうが安く正確」と判断した項目の申し送り。計画時点で論証しない。

節名は「実装時確認事項」で固定する — km-github-workflow が issue 本文をこの節名で読んで各項目の消化を確認するため、名前を変えると確認が黙って外れる。

各項目に次を持たせる。

- 確認・決定する事項
- 計画時に固定せず後ろ倒しする理由
- どの slice・実装時点で消化するか
- 判断に使う evidence または decision rule
- 必要なら安全な default / fallback

planning blocker、ユーザ所有の trade-off、one-way door はここへ落とさず計画時に詰める。
