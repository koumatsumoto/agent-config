# ゴール契約の書き方

`.plan/` に書き出す本文（= GitHub issue 本文）に何を入れるか。固定テンプレートではなく、節名・順序・粒度は計画ごとに決める。読み手は他 AI か未来の自分で、**issue 単体で「何を達成すべきか・何に依拠してよいか・何を守るべきか・どうなれば完了か」が分かれば、実装経路は読み手が選べる**。手順の逐一指定は契約の一部ではない。

## 入れるもの

- **Anchor（冒頭 1 ブロック。以降の手順・検証・レビューすべてがここを参照する）**
  - **Goal** — 達成すべきビジネス価値・要件（目的・対象）
  - **Non-goal** — 今回やらないこと（スコープ境界）
  - **Definition of Done** — Goal を満たしたと言える受け入れ条件を、合否判定でき反証可能な形で。今回の変更に固有のものだけ書く（repo 全般の規範・delivery 一般条件は再掲しない）。計画を左右する非機能（性能・サイズ・保守性・トークン効率）があれば、その合否条件も DoD に入れる。主要トレードオフは anchor でなく「設計判断」「却下案」へ落とす
- **背景** — なぜこの計画が必要か（問題・きっかけ）
- **依拠する事実と前提** — 調査で分かった現状・制約・依存。各事実に出典（`file:line`・コマンド出力の要点）を付け、最新性が要るものは確認時点も残す
- **設計判断と却下案** — それぞれ理由付きで。実装者が同じ分岐で迷わない・別の道へ逸れないための制約
- **作業単位** — 手順書ではなく「独立に検証できる単位」の列。各単位に受け入れ条件（**成果水準**で書く。エッジケースの網羅列挙はせず個別の異常系は実装時確認事項へ）・検証・依存順を付け、どの DoD を満たすかを紐付ける。1 issue を複数 PR に割るなら切れ目も示す
- **検証** — 何を動かしどう確認して DoD を証明するか（テスト・静的解析・手動確認）
- **リスク・未決事項** — 受け入れ済みリスクと実装時確認事項

意図して落とすのは構わない。落ちていることに気づかないのが問題。

## 言葉より参照が強いとき

説明を書くより**指させるほうが高精度**なら指す。移植元の実装、DoD を体現する失敗テスト、既存の類似実装、HTML モック、判断基準そのものを書いた rubric。散文で再現すると劣化コピーになる。ただし GitHub の読者が開けるものに限る（`.plan/` のローカルパスは参照先にしない）。

## DoD の lint（書き出し前に当てる）

- **測定手続きが一意か** — 各 DoD が「何をどう実行して合否を判定するか」と一意な閾値を持つ。第三者の反証者のつもりで読み、**「これで不合格になる具体入力」を 1 つ挙げられなければ**ヘッジ扱い
- **ヘッジ語を含めない** — 約 / おおむね / ほぼ / 十分 / 適切に / なるべく / 可能な限り / 基本的に / 一定の / 程度。閾値をぼかして反証を不能にする語。数量は境界値で書く（「50 文字以下」であって「約 50 文字」でない）
- **Goal と DoD が内部整合しているか** — DoD が Goal に無い変更・撤去を要求していない。Goal の約束をどの DoD も担っていない欠けがない
- **DoD ↔ 作業単位が双方向か** — すべての DoD に担当作業単位があり、すべての作業単位が少なくとも 1 つの DoD か delivery 規約を参照する。DoD 非参照で正当な例外は km-github-workflow へ委譲する PR 作成・ブランチ操作・報告に限る。準備・調査だけの単位も、成果が下流の DoD に紐づくならその DoD を参照する
- **出典が生きているか** — 出典付き主張は書き出し時点で引用先を開き、行番号・内容の一致を確認する（誤引用をレビューまで生き残らせない）

## issue 全文ミラーの前提

- `<!-- km:plan:managed -->` を本文先頭近く（タイトル直下など）に 1 行置く。km-plan 管理 issue の識別子
- issue URL の placeholder を本文に用意する（作成後に書き込んで再同期する）。issue title 案は本文に埋め込まず、`gh issue create --title` に渡す値としてチャットで提示する
- skill 内部の用語・段階名を本文に書かない（読者は skill を知らない）。画像・リンクは GitHub 上で開けるものだけ。コードブロックには言語 tag を付ける
- 3 コンポーネント以上・時系列のやり取り・状態遷移・責務境界が絡むなら Mermaid 図を検討する

## 受け入れ済みリスク

レビューで出た `MEDIUM` / `LOW` を意図的に残す場合、**重大度・残す理由・いつ再評価するか**を記録する。これを書かずに残すとレビュー loop で再提起される。

## 実装時確認事項

可逆性で「実装時に詰めるほうが安い」と判断した項目の申し送り。計画時点で論証しない。

- 1 行の確認事項 + 手戻りが小さい根拠 1 行
- 既定は各項目を該当する作業単位の検証へ紐付ける（単位が実行されれば消化される保証パス）。紐付けられないものは Report でユーザへ明示し、実装 PR の報告で消化結果を残す
- 計画が破綻する / 前提が揺らぐ級はここへ落とさず計画時に詰める
