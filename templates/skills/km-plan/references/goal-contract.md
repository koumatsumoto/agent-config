# 設計ブリーフの書き方

`.plan/` に書き出す本文（= GitHub issue 本文）に何を入れるか。固定テンプレートではなく、節名・順序・粒度は計画ごとに決める。ただし該当する情報を意図なく落とさない — 読み手は会話を知らない他 AI か未来の自分で、**issue 単体で設計判断を再利用でき、実装経路だけを自分で選べる**状態にする。

## 入れるもの

- **ゴール** — 達成すること（満たすビジネス価値・要件）/ やらないこと（スコープ境界）/ 完了条件。完了条件は今回固有のものだけ書き、repo 全般の規範・delivery 一般条件は再掲しない。計画を左右する非機能（性能・サイズ・保守性・トークン効率）があれば、その合否条件も入れる
- **背景** — 何が起きているか、なぜ問題か、放置するとどうなるか、なぜ今扱うか
- **現在地** — いまの構造・責務・データの流れ、関係するファイル・interface・設定・外部契約、計画が依拠する制約と前提。設計方針・スコープ・実現可能性・完了条件を左右する事実には出典（`file:line`・コマンド出力の要点）を付ける。すべての記述に出典は要らない
- **設計方針** — どの層で何をどう変えるか、変更後の構造、維持するもの、なぜこの粒度で解くか。**課題に対して過剰な仕組みを持ち込んでいないか**をここで説明できないなら、方針がまだ決まっていない
- **主要な判断** — 決定 / 理由 / 根拠と制約 / 現実的な代替案と不採用理由 / 影響とトレードオフ / 実装者に残す自由度 / 見直す条件。省くと実装者が別の方向へ進みやすい判断だけを書き、小さな選択すべてにこの形式を強制しない
- **変更対象** — どのファイル・コンポーネント・契約の責務がどう変わり、どこへ波及し、何を不変に保つか。分割が要るなら成果の単位で切り、依存順と PR の切れ目を示す。単なるファイル一覧にも、内部関数単位の作業手順にもしない
- **検証** — どの完了条件を、何を実行・観測して、どう合否判定するか
- **リスクとトレードオフ** — 何が起きうるか / 影響 / 緩和 / 残す理由 / 再評価条件。レビューで受け入れたリスクもここへ書く（書かずに残すと次のレビューで再提起される）
- **実装時確認事項** — 下記

作業ログ・レビューの往復・過去版の変遷は本文に書かない。

## 言葉より参照が強いとき

説明を書くより**指させるほうが高精度**なら指す。移植元の実装、完了条件を体現する失敗テスト、既存の類似実装、HTML モック、判断基準そのものを書いた rubric。散文で再現すると劣化コピーになる。ただし GitHub の読者が開けるものに限る（`.plan/` のローカルパスは参照先にしない）。

構造・データや制御の流れ・状態遷移・責務境界が文章だけでは誤読されるなら Mermaid を使う。コンポーネント数では決めず、図が判断と引き継ぎの精度を上げるかで決める。

## 書き出し前の lint

- **判断材料が足りているか** — 背景・現在地・判断理由・変更対象から、実装者が調査をやり直さず、別の設計方向へ逸れずに着手できる。いまの状態と変更後の差が具体的か
- **過剰に拘束していないか** — 内部構造・個別の異常系・全テストケース・逐次手順を固定していない
- **より単純な方針を潰せているか** — 方針の複雑さ自体が主要な判断なら、単純な代替とそれを採らない理由を書く。過剰な仕組みは実装後に最も高くつく
- **完了条件が反証可能か** — 第三者が具体的な根拠で合否を判定でき、**「これで不合格になる具体入力」を 1 つ挙げられる**。数値は数値そのものに意味があるとき（ユーザ要求・公開契約・性能予算）だけ使い、意味のない数値を発明しない。質的な成果は観測手続きと不合格条件で書く。「十分」「適切に」のような語で合否や担当の境界をぼかさない
- **ゴールが内部整合しているか** — 完了条件がゴールに無い変更を要求していない。ゴールの約束をどの完了条件も担っていない欠けがない。各成果に実装と検証の経路があり、どの成果にも紐づかない作業が無い
- **戻せない選択を暗黙に決めていないか** — 公開契約・schema・移行・信頼境界・不可逆操作を、判断として明示せず本文へ埋めていない。実装時確認事項に blocker を逃がしていない
- **出典が生きているか** — 出典付き主張は書き出し時点で引用先を開き、行番号・内容の一致を確認する（誤引用をレビューまで生き残らせない）

## issue 全文ミラーの前提

- `<!-- km:plan:managed -->` を本文先頭近く（タイトル直下など）に 1 行置く。km-plan 管理 issue の識別子
- issue URL の placeholder を本文に用意する（作成後に書き込んで再同期する）。issue title 案は本文に埋め込まず、`gh issue create --title` に渡す値としてチャットで提示する
- skill 内部の用語・段階名を本文に書かない（読者は skill を知らない）。画像・リンクは GitHub 上で開けるものだけ。コードブロックには言語 tag を付ける

## 実装時確認事項

可逆性で「実装時に詰めるほうが安く正確」と判断した項目の申し送り。計画時点で論証しない。

節名は「実装時確認事項」で固定する — km-github-workflow が issue 本文をこの節名で読んで各項目の消化を確認するため、名前を変えると確認が黙って外れる。

各項目に、確認・決定する事項 / 後ろ倒しする理由 / どこで消化するか / 判断に使う根拠か決め方 / 必要なら安全な既定値 を持たせる。

blocker、ユーザ所有のトレードオフ、戻せない選択はここへ落とさず計画時に詰める。
