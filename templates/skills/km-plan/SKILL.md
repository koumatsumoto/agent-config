# Plan

計画は、実装担当AIへ渡す設計案であり、達成すべき目的と完了条件を定める。読み手は会話を知らない別のAIか未来の自分で、issue単体から方向、現在地、変更範囲、完了条件を再調査なしに把握できるようにする。

固定するのは**判断**であって手順ではない。背景・現在地・採用理由・代替案の不採用理由・トレードオフ・変更対象は厚く残し、内部構造・個別の異常系・逐次手順は固定しない。順序を書くのは、順序自体が正しさ・互換性・安全性・依存の制約になるときだけ。

省略した場合に、実装担当が再調査する、異なる設計を選ぶ、または重要な制約を見落とす情報だけを残す。それ以外は実装時に決める。

## 進め方

**確認、文書化、レビュー、公開、報告の順に進める。**

### 確認

要求とリポジトリを計画の規模に見合う深さで調べる。設計方針・スコープ・実現可能性・完了条件を左右する事実は直接確認し、出典（`file:line`・コマンド出力の要点）を残す。

ユーザーに聞くのは次だけ。選択肢と推奨案を添える。

- ゴール・スコープ・完了条件が変わる
- 後から戻すコストが高い選択
- ユーザーが持つ重要なトレードオフ（コスト・優先度・対外的影響）
- リポジトリと一次情報から確定できず、外すと高くつく前提

それ以外の可逆な分岐は、既存パターンと最小の方針を自分で選ぶ。リポジトリ・コード・一次情報で答えの出る事実は、聞く前に確認する。不慣れな領域では「何を知らないか」を 1 パス洗い出し、上に該当するものだけ質問へ上げる。

着手前に、理解した問題・採る方向・実装者へ残す自由度・実装時確認事項へ送る未決を数行で宣言して進む（返答は待たない）。**上に該当する未決を宣言で代替しない。**

### 文書化

`references/goal-contract.md` を読み、本文を組み立ててから `.plan/YYYYMMDD-<slug>.md` へ書き出す。

- 書き出す前に `.plan/` が git に追跡されないことを確かめる。未追跡かつ未 ignore なら `.gitignore` に `.plan/` を足す。すでに追跡済みならリポジトリ方針と衝突するので、勝手に直さずユーザーに確認して止まる
- 書き出す前に goal-contract.md の点検項目を本文へ当てる

### レビュー

**メイン担当が先に反証・修正する。それでも残る具体的な不確実性にだけ、独立レビュアを 1 名使う。**

1. **反証して直す** — 少なくとも次を崩しにいき、崩れたところを直す
   - ゴールと設計方針が対応しているか
   - 設計を左右する前提が、リポジトリ・一次情報と一致しているか
   - 高コストな誤方向や戻しにくい判断を、判断として明示せず暗黙に決めていないか
   - 完了条件で目的の達成を判定できるか
   - 実装時に決めればよい細部を過剰に固定していないか
2. **残る不確実性を言語化する** — 修正後もなお残るものを、反証できる命題として書く
3. **起動条件に当てる** — 次を**すべて**満たす命題だけ独立レビューへ回す
   - **未解決** — リポジトリ・一次情報・通常の推論でメイン担当が決着できていない
   - **高コスト** — 誤るとゴール不達・広い手戻り・戻せない設計・不可逆な事故になり、実装前に止める価値がある
   - **独立検証で変わりうる** — 別コンテキストが根拠を検証すれば結論が変わりうる

   公開 API・スキーマ・移行・認証・認可・security・framework 導入・大規模変更といった**変更カテゴリやファイル種別・規模は起動理由にならない**。メイン担当が注意深く確認する材料であって、独立レビューを必須にする条件ではない
4. **1 名に渡す** — 満たす命題が複数あれば最重要の 1 つに絞る。`references/reviewer.md` と計画ファイルを**絶対パス**で、担当する不確実性を反証命題として渡す。メイン担当の所見・修正履歴・暫定判定は渡さない。読めないファイルがあれば憶測せずパスを報告して終えさせる。**絞らなかった命題と、レビュアが失敗・無応答で結論を返さなかった命題は未解決として残る**
5. **指摘を検証する** — 完了を妨げる問題の条件（`references/reviewer.md`）をメイン担当が再検証し、成立するものだけ計画へ反映して解消を確認する。レビュアが判定を保留したものは却下せず、リポジトリ・一次情報で決着させる。決着できず計画の土台に関わるなら完了を妨げる問題として扱う。**同じ指摘の解消確認のために新しいレビュアを起動しない。** 修正が起動条件を改めて満たす別の重大な不確実性を生んだときだけ、例外的にもう 1 名使う

条件を満たさない指摘は振り分ける。**逆に、条件を満たす問題を判定を通すためにここへ降ろさない。**

- **実装時確認事項** — 実装時に情報が増えてから安く決まる。本文の該当節へ送る
- **受け入れ済みリスク** — 重要だが、ユーザーが理由と再評価条件を了解して残す。受諾が取れるまでは未解決として扱う
- **却下** — 重複・根拠不足・スコープ外・一般論・極端な将来仮説・好み

未解決のものはメイン担当がリポジトリ・一次情報で決着させ、決着できずユーザー判断が要るなら選択肢と推奨を添えて確認する。未解決が無くなれば公開へ進む。**完了を妨げない指摘のために独立レビューを起動・再実行しない。**

### 公開

GitHub管理リポジトリでだけ実行する。手順と既存 issue の更新規約は `references/issue.md`。明示が無い限り**新規 issue** を作る（類似 open issue の自動探索・再利用はしない）。

### 報告

`.plan/` パス、issue URL、実装時確認事項（どこで消化されるか）、受け入れ済みリスク、ユーザー判断が必要な未決、未同期があればその旨。issue はそのまま km-github-workflow の実装タスク列になる。

## 計画を直すとき

要求の変化・外部レビュー・前提の誤りが届いたら、**ゴール（達成すること / やらないこと / 完了条件）が動くか**で分ける。

- **動く** — ゴールを先に改版し、背景・現在地 → 設計方針 → 主要な判断 → 変更対象 → 検証 → リスク → 実装時確認事項へ順に伝播させる。下流から入れると宙に浮いた完了条件・作業が残る
- **動かない** — 該当箇所への局所反映に留める

どちらも、改版した範囲へ反証を当て直す。届いた指摘は 1 件 = 1 判断へ分解して振り分ける。最終本文には**現在の判断理由だけ**を残し、改版の履歴とレビューの往復は commit / PR / issue comment へ置く。

## 不変条件

- **issue body は全文ミラー**: `.plan/` と同じ markdown を `--body-file` で渡す。要約・抜粋・heredoc での再構成・`--body "..."` は不可（backtick / `$(...)` が展開される）
- **`.plan/` は一時作業場**: 共有成果物（issue / PR / comment）から `.plan/` のファイルを参照先として書かない。正本は issue / PR の URL
- **`gh` の失敗を成功扱いしない**: issue 未作成と「作成済みだが URL 未同期」を区別して報告する
