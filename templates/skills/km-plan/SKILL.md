# Plan

会話を知らない実装担当者が、目的・設計判断・変更範囲・完了条件を理解して着手できる計画を作る。

## 計画を作る

要求とリポジトリを調べる。ユーザーの回答でゴール・スコープや重要なトレードオフが変わる場合は確認し、可逆な実装判断は既存設計と最小方針から決める。

計画には着手に必要な情報を揃える。見出し名・順序・粒度は計画に合わせる。

- 達成したい価値・要件と今回の変更範囲
- 変更理由、現在の責務・制約、設計を左右する事実と確認可能な参照
- 変更後の責務・流れ、維持するもの、採用理由と重要なトレードオフ
- 対象ファイル・公開契約・必要なコード例。実装者が迷う境界は具体化し、容易に決められる細部は固定しない
- 何を実行・観測すれば目的を達成したと判断できるか

残るリスクや実装時に確認する事項は、必要な場合だけ内容・理由・確認先を添える。重要な要件や戻すコストが高い判断は実装前に決める。

本文用の一時ファイルを用意する。 `<skill-directory>` はこの `SKILL.md` のあるdirectory。

```text
node "<skill-directory>/scripts/prepare-plan.js"
```

返されたMarkdownファイルに計画本文を書く。

## 計画を見直す

ゴールを達成できるか、根拠が十分か、不要な複雑性を持ち込んでいないかを確認する。

自分だけでは解消できない重要な不確実性が残り、別視点の検証で判断が変わりうる場合だけ独立レビューを使う。指摘の根拠を確認し、必要な修正だけを計画へ反映する。

## Issueへ反映する

更新対象のIssueが指定されている場合は現在の本文を読み、依頼範囲を反映した**更新後の本文全体**をMarkdownファイルへ書く。指定されていなければ新規Issue用の本文を書く。

```text
gh issue create --title "<title>" --body-file "<plan-file>"
gh issue edit <issue-number> --body-file "<plan-file>"
```

既存Issueの更新では、依頼と無関係な既存内容を意図せず落とさない。

成功したらIssue URLと重要な残存事項を報告する。反映できなければ成功扱いせず、その旨を報告する。
