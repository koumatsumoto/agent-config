# Plan

計画は**実装 agent へのゴール契約**である。何を達成すべきか（Goal / Non-goal / 反証可能な DoD）、何に依拠してよいか（出典付きの事実）、何を守るべきか（設計判断・制約）、どうなれば合格か（検証）を規定し、**実装経路は実装者に委ねる**。経路を縛るのは、それ自体が制約（不可逆・依存順・設計判断）であるときだけ。

計画時点はプロジェクトで最も情報が少ない。だから**何を今詰めるかは詳細度でなく可逆性で決める**。覆すのが高コストな判断（公開契約・データモデル・スキーマ・セキュリティ境界）は今詰め、実装後に安く直せる詳細は実装時へ送る。

## 進め方

**Clarify → Materialize → Review → Publish → Report。**

Plan Mode 中、または materialize / issue 化が明示されていないときは Clarify で止め、`<proposed_plan>` を提示して「`.plan` に出して」「計画を issue にして」と依頼するよう案内する。合意済みの計画を materialize する依頼なら、再設計せず骨子の未決だけ確かめて Materialize へ入る（会話から復元できなければ推測で書き出さず計画内容を再確認する）。

### Clarify

要求と repo を、計画の規模に見合う深さで調べる。事実には出典（`file:line`・コマンド出力の要点）を付け、レビュアと実装者が再調査せず真偽を検証できる形にする。

- **未決を潰す** — Goal / Non-goal / DoD / 主要トレードオフを動かす未決だけをユーザに確認する。選択肢 + 推奨案を添えてまとめて 1 回。妥当な前提で進められるものは聞かない。計画を左右する非機能（性能・サイズ・保守性）が争点になるならここで固める
- **盲点を洗う** — 不慣れな領域では「何を知らないか」を 1 パス洗い出す。未知のままでは DoD を書けない箇所は上の質問へ格上げする
- **前提を宣言する** — 置いた前提とスコープ判断を数行で宣言して進む（返答を待たない）。宣言してよいのは「どの妥当な解を選んでも DoD が変わらない前提」だけ。DoD・スコープ・主要トレードオフを左右する不確実性は宣言でなく質問へ回す

### Materialize

`references/goal-contract.md` を読み、本文をメモリ上で組み立ててから `.plan/YYYYMMDD-<slug>.md` へ書き出す。

- 書き出す前に `.plan/` が git に追跡されないことを確かめる。未追跡かつ未 ignore なら `.gitignore` に `.plan/` を足す。すでに追跡済みなら repo 方針と衝突するので、勝手に直さずユーザに確認して止まる
- 書き出す前に **Secret Check** と goal-contract.md の DoD lint を本文に当てる。修正で本文が変わったら Secret Check を当て直す

### Review

著者は自分の計画を「正しい」と読んでしまう。**著者でない目を通してから公開する。**

- **起動** — 中規模以上は subagent 1 名（既定）。小規模・可逆・低リスクなら著者バイアスを自覚した self-review。高リスク領域（security / 公開契約・スキーマ / データ移行 / 不可逆操作）に触れるなら該当レンズのレビュアを足す。迷ったら一段上へ
- **渡すもの** — 判定基準 `references/reviewer.md` と計画ファイルを**絶対パス**で渡して両方を読ませる（相対パスや未展開の `~` は working directory 依存で読み取りに失敗する）。「本文は書き換えず指摘だけ返す」ことと、読めなかったファイルがあれば憶測でレビューせずパスを報告して終えることを伝える。他レビュアの所見は渡さない
- **収束** — 未解決 `CRITICAL` / `HIGH` がゼロになるまで回す（2 周目以降は未解決分の解消確認だけに絞る）。3 周で収束しない、レビュー結果が空、対象ファイルを読めていない、のいずれでも issue 化せず、未収束の指摘とともにユーザへ委ねる
- **反映** — 重大度付きの指摘は本文へ反映するか、`MEDIUM` / `LOW` に限り受け入れ済みリスクとして残す。grade 済みの指摘を「実装時確認事項」へ落とし直さない（レビュアの可逆性トリアージを無効化する）。重大度なしの「実装時確認事項候補」は、高影響カテゴリに触れないことを確かめてから本文へ転記する。採否の往復は本文に残さない（共有したいなら issue 化後の comment へ）

### Publish

GitHub 管理 repo でだけ実行する。手順と既存 issue の更新規約は `references/issue.md`。明示が無い限り**新規 issue** を作る（類似 open issue の自動探索・再利用はしない）。

### Report

`.plan/` パス、issue URL、受け入れ済みリスク、実装時確認事項（どこで消化されるか）、未同期があればその旨を報告する。issue はそのまま km-github-workflow の実装タスク列になる。

## 計画を直すとき

要求の変化・外部レビュー・前提の誤りが届いたら、**anchor（Goal / Non-goal / DoD）が動くか**で分ける。

- **動く** — anchor を先に改版し、下流（設計判断 → 作業単位 → 検証 → リスク）へ順に伝播させる。下流から入れると宙に浮いた DoD・作業単位が残る。削除した DoD を参照する単位が残っていないか、新しい DoD に担当単位があるかを点検する
- **動かない** — 該当する作業単位・検証への局所反映に留める

どちらも変更範囲に Review を当て直す。外部レビューの指摘は 1 件 = 1 判断に分解して個別に採否を決める（まとめて確認すると落ちる）。外部指摘には重大度が付いていないので、可逆性で見て 反映 / 受け入れ済みリスク / 実装時確認事項 へ振り分ける。公開済み issue への再同期は `references/issue.md`。

## Secret Check

計画は issue へ全文ミラーされるため、混入は即公開になる。**本文が外へ出る全経路の直前**で本文と title を走査する — `.plan/` への書き出し、`gh issue create`、`gh issue edit`（URL 同期・既存更新・修正後の再同期）。`.plan/` に入れば後続の全経路がそれを引き継ぐので、issue 経路だけでは足りない。

見るもの: 認証情報・鍵・トークンの値そのもの、`.env*` / `*.pem` / `*.key` / credential ファイルへの参照、貼り付けたログやスタックトレースに紛れ込む社内ホスト名・ユーザー名・内部 URL。**検出が不確かでも止めてユーザに確認する。** `.plan/` の自動削除はしない。

## 不変条件

- **Plan Mode 中は `.plan/` / `.gitignore` / GitHub issue を一切変更しない**
- **issue body は全文ミラー**: `.plan/` と同じ markdown を `--body-file` で渡す。要約・抜粋・heredoc での再構成・`--body "..."` は不可（backtick / `$(...)` が展開される）
- **`.plan/` は一時作業場**: 共有成果物（issue / PR / comment）から `.plan/` のファイルを参照先として書かない。正本は issue / PR の URL
- **`gh` の失敗を成功扱いしない**: issue 未作成と「作成済みだが URL 未同期」を区別して報告する
