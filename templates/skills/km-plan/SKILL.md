# Plan

計画は**実装 agent への設計ブリーフ兼ゴール契約**。読み手は会話を知らない別の AI か未来の自分で、issue 単体から「なぜこの方向か・いまどうなっているか・何をどこまで変えるか・どうなれば完了か」を再調査なしに掴める必要がある。

固定するのは**判断**であって手順ではない。背景・現在地・採用理由・代替案の不採用理由・トレードオフ・変更対象は厚く残し、内部構造・個別の異常系・逐次手順は固定しない。順序を書くのは、順序自体が正しさ・互換性・安全性・依存の制約になるときだけ。

迷ったら **「省くと、能力のある実装者でも調査をやり直す・別の設計方向を選ぶ・制約を見落とすか」**。Yes なら書く。No なら実装時へ送る。

## 進め方

**Clarify → Materialize → Review → Publish → Report。**

### Clarify

要求と repo を計画の規模に見合う深さで調べる。設計方針・スコープ・実現可能性・完了条件を左右する事実は直接確認し、出典（`file:line`・コマンド出力の要点）を残す。

ユーザに聞くのは次だけ。選択肢と推奨案を添える。

- ゴール・スコープ・完了条件が変わる
- 後から戻すコストが高い選択
- ユーザが所有する重要なトレードオフ（コスト・優先度・対外的影響）
- repo と一次情報から確定できず、外すと高くつく前提

それ以外の可逆な分岐は、既存 pattern と最小の方針を自分で選ぶ。repo・コード・一次情報で答えの出る事実は、聞く前に確認する。不慣れな領域では「何を知らないか」を 1 パス洗い出し、上に該当するものだけ質問へ上げる。

着手前に、理解した問題・採る方向・実装者へ残す自由度・実装時確認事項へ送る未決を数行で宣言して進む（返答は待たない）。**上に該当する未決を宣言で代替しない。**

### Materialize

`references/goal-contract.md` を読み、本文を組み立ててから `.plan/YYYYMMDD-<slug>.md` へ書き出す。

- 書き出す前に `.plan/` が git に追跡されないことを確かめる。未追跡かつ未 ignore なら `.gitignore` に `.plan/` を足す。すでに追跡済みなら repo 方針と衝突するので、勝手に直さずユーザに確認して止まる
- 書き出す前に goal-contract.md の lint を本文へ当てる

### Review

著者は自分の計画を「正しい」と読む。**main が先に反証・修正し、それでも残るリスクにだけ独立レビュアを 0〜2 名使う。**

1. **反証して直す** — ゴール・スコープ・完了条件を固定し、現在地と設計方針の対応・戻せない選択・計画が依拠する事実を崩しにいく。情報不足と過剰な手順固定を直す
2. **残るリスクを言語化する** — 修正後もなお、高コストな誤方向につながりうる未検証のもの
3. **選んで起動する** — 下の基準で 0〜2 名。`references/reviewer.md` と計画ファイルを**絶対パス**で渡し、担当する観点と選んだ理由を添える。main の所見・修正履歴・暫定判定・他レビュアの報告は渡さない。読めないファイルがあれば憶測せずパスを報告して終えさせる
4. **統合して判定する** — main が blocker の条件を再検証して分類する。レビュアが判定を保留したものは却下せず、main が repo・一次情報で検証する。決着できず計画の土台に関わるなら blocker として扱う

#### 何名に当てるか

判断材料は**修正後に残るリスク**。計画の長さ・docs-only・規模では決めない。

- **0 名** — ゴール・スコープ・完了条件が明確で、設計方針が既存 pattern の直接適用で、下の「必ず 1 名通す変更」に当たらず、main review のあとに高コストな誤方向へつながる未検証のものが残らない
- **1 名** — 残るリスクが一つの観点に集約できる。観点の例: ゴール・スコープ / 構造と実現可能性 / 公開契約と移行 / 信頼境界と不可逆操作 / 判断材料の引き継ぎ / 完了条件
- **2 名** — 直交する 2 つのリスクが具体化し、片方の確認が他方を代替できないときだけ。観点ごとに選んだ理由を 1 行残す

**1 ラウンド最大 2 名。** レビュー中に第三のリスクが具体化したら、同じラウンドへ足さず次のラウンドで 1 名を走らせる。

**必ず 1 名通す変更** — 公開 API / CLI / protocol / identifier / 長寿命な設定、schema・永続化形式・データの所有、移行・削除・復元不能な変換、認証・認可・権限境界・秘密情報・外部入力から実行への信頼境界、本番権限・課金・送信・公開のような不可逆または高影響の副作用、repo 横断で複製される pattern・依存方向・framework 導入。字面でなく**戻しにくさと影響範囲**で判定する。

#### 収束

正式な指摘は blocker だけ（条件は `references/reviewer.md`）。満たさないものは分ける。

- **実装時確認事項** — 実装時に情報が増えてから安く決まる。本文の該当節へ送る
- **受け入れ済みリスク** — 重要だが、ユーザが理由と再評価条件を了解して残す。受諾が取れるまでは未解決の blocker として扱う
- **却下** — 重複・根拠不足・スコープ外・一般論・極端な将来仮説・好み

レビュアの指摘が条件を満たさなければ main がこの 3 つへ振ってよい。逆に、**条件を満たす blocker を、判定を通すためにこの 3 つのどれかへ降ろさない。**

- `READY` — 必要なレビューが済み、未解決の blocker が無い。実装時確認事項が残っていてよい
- `BLOCKED` — 未解決の blocker がある / 必要なレビュアが失敗した / 必ず通すべき確認を完了できない

`BLOCKED` の間だけ、blocker を直して新しいレビュア 1 名に確認させる。渡すのは対象の blocker と修正箇所（初回の非共有はここでは適用しない）。見るのはその解消と、修正が持ち込んだ新しい blocker だけ。**それ以外のために再実行しない。** 収束しなければ未解決の論点と選択肢をユーザへ委ねる。

### Publish

GitHub 管理 repo でだけ実行する。手順と既存 issue の更新規約は `references/issue.md`。明示が無い限り**新規 issue** を作る（類似 open issue の自動探索・再利用はしない）。

### Report

`.plan/` パス、issue URL、レビュア構成と選んだ理由、`READY` / `BLOCKED`、受け入れ済みリスク、実装時確認事項（どこで消化されるか）、未同期があればその旨。issue はそのまま km-github-workflow の実装タスク列になる。

## 計画を直すとき

要求の変化・外部レビュー・前提の誤りが届いたら、**ゴール（達成すること / やらないこと / 完了条件）が動くか**で分ける。

- **動く** — ゴールを先に改版し、背景・現在地 → 設計方針 → 主要な判断 → 変更対象 → 検証 → リスク → 実装時確認事項へ順に伝播させる。下流から入れると宙に浮いた完了条件・作業が残る
- **動かない** — 該当箇所への局所反映に留める

どちらも変更範囲へ Review を当て直す。外部レビューの指摘は 1 件 = 1 判断へ分解して振り分ける。最終本文には**現在の判断理由だけ**を残し、改版の履歴とレビューの往復は commit / PR / issue comment へ置く。

## 不変条件

- **issue body は全文ミラー**: `.plan/` と同じ markdown を `--body-file` で渡す。要約・抜粋・heredoc での再構成・`--body "..."` は不可（backtick / `$(...)` が展開される）
- **`.plan/` は一時作業場**: 共有成果物（issue / PR / comment）から `.plan/` のファイルを参照先として書かない。正本は issue / PR の URL
- **`gh` の失敗を成功扱いしない**: issue 未作成と「作成済みだが URL 未同期」を区別して報告する
