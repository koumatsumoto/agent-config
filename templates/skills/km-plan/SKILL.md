# Plan

会話を知らない別のAIが、目的・現在地・設計判断・変更範囲・完了条件を再調査せず理解し、正しい方向で実装を始められる計画を作る。
固定するのは判断であって実装手順ではない。省くと再調査・別設計・重要な制約の見落としにつながる情報だけを残し、実装時に安く決められることは固定しない。

## Workflow

1. **確認**: 要求とリポジトリを調べ、ゴール・設計方針・変更範囲・完了条件を決める。ユーザー判断が必要な事項は選択肢と推奨案を添えて確認する
2. **文書化**: `references/goal-contract.md`に従って計画を作り、実行ごとの一時ディレクトリへ書き出す
3. **レビュー**: メイン担当が計画を反証して修正し、必要な場合だけ独立レビューを1名使う
4. **公開**: `references/issue.md`に従ってGitHub issueへ反映する
5. **報告**: issue URL、実装時確認事項、重要な残存リスクを報告する

### 確認

設計方針・スコープ・実現可能性・完了条件を左右する事実を直接確認し、出典（`file:line`・コマンド出力の要点）を残す。
ユーザーに聞くのは、回答によって次のいずれかが実質的に変わる場合だけ。

- ゴール・スコープ・完了条件が変わる
- 後から戻すコストが高い選択
- ユーザーが決める重要なトレードオフ（コスト・優先度・対外的影響）
- リポジトリと一次情報から確定できず、外すと高くつく前提

それ以外の可逆な判断は、既存設計と最小方針から自分で決める。

### 文書化

`references/goal-contract.md` を読み、本文を組み立てて一時ファイルへ書き出す。

作業ファイルはリポジトリ内に作らず、OSまたは実行環境が提供する一時領域へ、実行ごとに一意なディレクトリを作成して置く。固定パスや特定OSのパスを前提にしない。サブエージェントや外部コマンドへ渡す場合は絶対パスを使う。

### レビュー

メイン担当が以下を反証して計画を修正する

- ゴールと設計方針が対応しているか
- 設計を左右する前提が、リポジトリ・一次情報と一致しているか
- 後から戻すコストが高い判断を暗黙に決めていないか
- 不要な複雑性や長期的なアーキテクチャ負債を持ち込んでいないか
- 完了条件で目的の達成を判定できるか
- 実装時に決めればよい細部を過剰に固定していないか

修正後にも、次をすべて満たす具体的な不確実性が残る場合だけ独立レビュアを1名使う。

- メイン担当だけでは決着できない
- 誤るとゴール不達、高コストな手戻り、戻しにくい設計、過剰な複雑性、長期的な保守性・アーキテクチャ負債、不可逆な事故につながる
- 独立した検証によって判断が変わりうる

独立レビューでは最重要の不確実性を1つ選び、計画本文、`references/reviewer.md`の内容、反証命題を渡す。メイン担当の結論は渡さない。
変更規模や、API・スキーマ・移行・securityなどのカテゴリ自体は起動理由にしない。
指摘はメイン担当が根拠を再確認して採否を決める。実装時に安く決められるものは実装時確認事項へ送る。同じ指摘の確認だけを目的にレビュアを再実行しない。
実装前に解くべき重大な未決がなくなったら公開へ進む。
レビューによりゴール・スコープ・完了条件が変わる場合は、そこから設計方針と下流へ反映する。それ以外は該当箇所だけを直す。
最終本文には改版やレビュー修正の経緯は残さない。

### 公開

GitHub管理リポジトリでだけ実行する。`references/issue.md`に従い、明示がない限り新規issueを作る。

### 報告

issue URL、実装時確認事項、重要な残存リスクを報告する

## Contract

- 一時ファイルはセッションをまたぐ正本とせず、共有上の正本はGitHub issueとする
- issue本文は一時ファイルと同じMarkdownを`--body-file`で反映し、`--body`や本文の再構成を使わない
- GitHubへの反映に失敗した場合は成功扱いしない
