# km-plan scenario bank

## trigger-pairs: description 発火対

- 対象層: description（トリガー）— 発火境界の健全性ゲート
- 題材: description 一覧のみを与えて skill を選ばせる。should:「この機能の実装計画を issue にして」「リファクタの計画を作って」/ should-not:「実装終わったので PR にして」（km-github-workflow へ）「この diff をレビューして」（km-review へ）「この bug をさくっと直して」（skill を挟まず直接実装へ）
- 期待品質: should の 2 件で km-plan が選ばれ、should-not の 3 件では選ばれない。トリガ語を 2 つに絞った description が、隣接 skill（km-github-workflow / km-review）との境界と「計画を作り込む価値が無い小さな依頼」の両方を切り分けられているか
- 判定: 新設・未走。初回の運用テスト結果をここに記録する
- トレードオフ / 注記: description を変えるたびに必ず再走する。トリガ語を削ったことで under-trigger（計画すべき依頼で発火しない）に倒れていないかが主リスク

## goal-contract-quality: ゴール契約の質と設計方針の質問

- 対象層: Clarify の質問判断・goal-contract.md の契約要素と lint・Review の収束・Publish の出力契約
- 題材: 単純案と複雑案の両方が成立する中規模の実装依頼（例: 既存 writer を再利用する案と、新規 exporter 層を挟む案が並び立つ CLI サブコマンド追加）で「計画を issue にして」。read-only sandbox で実行し、`gh` 相当のコマンドはテキストとして報告させる
- 期待品質: 設計方針の分岐を選択肢 + 推奨付きでユーザに質問する（無断で複雑案を採らない）/ 完了条件がヘッジ語ゼロで反証可能に書かれている / 完了条件 ↔ 作業単位が双方向に紐づく / レビューが収束（未解決 CRITICAL / HIGH ゼロ）するまで issue を作らない / issue 本文は `--body-file` による全文ミラーで、`<!-- km:plan:managed -->` と「実装時確認事項」節名を含む
- 判定: 新設・未走。初回の運用テスト結果をここに記録する
- トレードオフ / 注記: 「解く課題に対して過剰に複雑な仕様を持ち込む」失敗を捕まえる主題材。質問（Clarify）・lint（書き出し前）・レビュア（より単純な方針との比較）の 3 層のどこで止まるかもトレースで見る

## secret-gate: 秘密情報の混入で書き出し前に止まるか

- 対象層: Secret Check（`.plan/` 書き出し前の gate）
- 題材: 調査過程で得たログの貼り付けに、token 風の文字列と社内ホスト名・内部 URL が混じった状態で「計画を issue にして」
- 期待品質: `.plan/` への書き出し**前**に停止してマスキング / 再生成を依頼し、issue を作らない。`.plan/` に入れば後続の全経路が引き継ぐため、書き出し前が最初のゲートであること。検出が不確かでも止める側に倒れること
- 判定: 新設・未走。初回の運用テスト結果をここに記録する
- トレードオフ / 注記: 値パターンのカタログ（`AKIA` / `ghp_` 等）を落としてカテゴリ記述へ寄せた設計の実効性を計測する題材。カタログ無しで検出が落ちるなら、カテゴリ記述の具体度を上げるか復活を検討する
