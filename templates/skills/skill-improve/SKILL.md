# Skill Improvement Cycle

skill のような prompt 資産の変更は、diff の静的レビューだけでは「意図した挙動改善が実際に起きるか・既存挙動を退行させないか」を判定できない。改善アイデアを課題として具体化し、candidate を起草し、実挙動（A/B 運用テスト）で質の向上を確かめてから採用する。

## 入口

- **改善アイデアから**（基本形）: 人間が持ち込んだ改善アイデアを起点に、フェーズ 1 から回す。base はディスク上の現行版そのもの
- **diff 済み変更の検証から**: 対象 skill が既に編集済みなら、base（変更前）を `git show <ref>:<path>` 等で references ごと一時ディレクトリに再現し、candidate（作業ツリー）と比較する。フェーズ 2（現状分析）だけ先に行ってからフェーズ 5（検証）に入る — 効く層・変更タイプ・wash リスクの特定は検証設計に必要なため省略できない

## 改善サイクル

1. **アイデアの具体化**: 「どの場面で・現状どうなるか・どうなってほしいか」に落とす。答えが検証設計を変える曖昧さが残るならユーザーに確認する
2. **現状分析**: 対象 skill 一式（SKILL.md + references）を読み、次の 3 つを特定する
   - **効く層・分岐**: アイデアが skill のどの層・分岐に効くか。変更しない層が単独で拾える改善は A/B で差が出ない（wash リスクの予測）
   - **source of truth**: 手元の skill が配布コピー（ホームディレクトリ配下等）なら、正本（テンプレート repo・プロジェクト repo）を特定する。特定できなければユーザーに確認する。実験は複製で行えるが、採用の反映先は常に正本
   - **変更タイプ**: 下の taxonomy で分類し、検証設計を決める
3. **課題と改善点の特定**: 現状と期待のギャップを明文化し、改善方針（何をどう変えるか）をユーザーと合意する
4. **candidate 起草**: 現行版一式を一時ディレクトリに複製して外科的に編集する（正本・配布コピーを直接編集しない）。記述は現在形で現設計の意図だけを書き、変遷・由来（「旧 X」「〜から変更」等）を残さない
5. **検証（レベル選択）**: 下の基準で light / full を選び、選んだレベルと理由を宣言してから進む（ユーザーは上書きできる）
6. **評価と判定**: 採用 / 低マージン採用 / 不採用
7. **記録と正本反映**

## 検証レベル

| レベル | 対象となる変更 | やること |
| --- | --- | --- |
| light | ロード境界・分岐・既定値・判断基準を変えない表現整理（誤字・言い回しの調整） | A/B なし。candidate を通読し「意図しない意味変化・判断基準の変化がないか」「description（トリガー）に影響がないか」をセルフチェックする |
| full | 挙動・判断・出力構造・既定値・トリガー・references のロード境界を変える変更 | `references/ab-testing.md` を読み、A/B 運用テストを実施する |

迷ったら full に倒す（light の誤選択は、挙動に影響する変更を無検証で通す事故につながる）。

## 変更タイプ（taxonomy）

検証設計は変更タイプで決まる。フェーズ 2 で分類し、full 検証の題材設計（ab-testing.md）に直結させる。

| タイプ | 例 | 検証設計の要点 |
| --- | --- | --- |
| ①構造・既定値 | 成果物の構造・既定挙動を変える（計画への goal anchor 追加、質問の構造化） | 既定挙動でない構造変化は A/B で差が出やすい。改善が特定分岐でのみ発火するなら題材をその分岐に倒す |
| ②検出・判断 | 見落とし検出・判断品質を上げる | 強モデルは base でも拾いがちで wash になりやすい。base floor 測定ときわどい題材が必須。差は「不確実性処理の規律」に出やすい |
| ③効率 | 探索・読み込み・手戻りを減らす | 非効率が実害になる規模の題材で測り、コスト（tokens / 所要時間）も判定材料にする |
| ④トリガー・分岐 | description・gate・レベル選択を変える | 発火検証（should / should-not の対）を健全性ゲートとして通す |

## 評価軸

評価するのは「**この指示に従うと開発の成果物・判断の質が高まるか**」。

- 目的達成: ユーザーが本当に達成したいこと（ビジネス価値）を的確に捉え達成しているか
- スコープ判断の的確さ: 扱う範囲の振り分け（同対応 / 後続 / 対象外）が過不足ないか
- 成果物の質: 読み手がそのまま次工程に進める質か
- 手戻り / 事故リスク: 無関係変更の混入・scope 逸脱・停滞を招く判断がないか

手順や分岐が発火したこと自体は改善の根拠にしない。タイプ④の発火検証は質評価の前提となる健全性ゲートとしてだけ使う（発火しなければ質を見る以前に不採用）。

## 判定

- **採用**: 改善が実挙動で観測できた
- **低マージン採用**: 強モデルでは差が出ないが、floor（弱い実行条件での下支え）として残す価値を説明できる
- **不採用**: 改善が観測できず、floor 価値も説明できない

差が出ないときは、まず題材が改善を分離できているか（きわどさ・規模・名指し観点）を疑って設計し直す。再設計しても差が出なければ、低マージンか不採用かを正直に切り分ける。

## 記録と正本反映

- 記録先は対象 repo の delivery 慣行に合わせる: PR delivery なら PR 本文、無ければレビュー報告。題材×改善点の対応表・期待した質・実際の質・判定を残す
- 採用時はフェーズ 2 で特定した正本に反映する
- 検証を通じて得た題材設計・judge 観点の知見は、本 skill の references に還元する

## 責務の境界

- 変更の正しさ（バグ・設計・セキュリティ）のレビューはコードレビュー（km:review 等）の責務。本スキルは「変更で開発の質が上がるか」の検証に絞る
- 新規 skill をゼロから作ることや、assertion ベースの定量 eval を回すことは対象外
- A/B と judge には実環境の subagent 機構（Claude Code の Task tool 等）を使う
