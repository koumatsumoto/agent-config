# Skill Improvement System

skill のような prompt 資産は agent の挙動を方向づける事前分布であり、その変更は diff の静的レビューだけでは「意図した挙動改善が実際に起きるか・既存挙動を退行させないか」を判定できない。本 skill は、改善シグナルを**実挙動の証拠**に変換して採否を決め、使った題材と判定を**記憶（scenario bank）**として蓄積する改善システムである。単発の検証パイプラインではなく、回すたびに対象 skill の検証資産が増え、次の改善が安く・鋭くなるループとして運用する。

**コスト原則**: 検証コストは変更の残存リスクに比例させる。軽い変更に重い検証を積まず、重い変更を無検証で通さない。計測器・モデル・ラウンド数はユーザーの明示指定が常に優先。

## シグナル（何が改善を起動するか）

改善はアイデアの持ち込みだけでなく、実挙動の証拠から始まる。次のいずれも一級の入口として扱う:

- **ユーザーの改善アイデア**（基本形）: フェーズ 1 から回す。base はディスク上の現行版そのもの
- **実走の観察**: 対象 skill を実際に使ったセッションで観測した欠陥 — 指示が働かなかった箇所・毎回手作りで補った手順・読まれなかった reference・誤読された分岐。転写できる観察はそのまま題材の種になる（最も安く・最も現実に接地したシグナル）
- **kaizen 記録・レビュー指摘**: `.kaizen/` の capture や PR レビューで露見した skill 起因の問題
- **剪定シグナル**: A/B の wash が続く・skill が肥大して標準ケースの遵守率が下がった疑い。削る改善も改善として同じループで扱う
- **diff 済み変更の検証依頼**: 対象 skill が既に編集済みなら、base（変更前）を `git show <ref>:<path>` 等で references ごと一時ディレクトリに再現して candidate（作業ツリー）と比較する。フェーズ 2（診断）から入る — 効く層・変更タイプ・wash リスクの特定は検証設計に必要なため省略できない

## 改善ループ

1. **シグナルの具体化**: 「どの場面で・現状どうなるか・どうなってほしいか」に落とす。答えが検証設計を変える曖昧さが残るならユーザーに確認する
2. **診断**: 対象 skill 一式（SKILL.md + references）と、あれば**記憶**（対象 skill 正本ディレクトリの `evals/scenarios.md`。様式は `references/scenario-bank.md`）を読み、次を特定する
   - **効く層・分岐**: シグナルが skill のどの層・分岐に効くか。変更しない層が単独で拾える改善は A/B で差が出ない（wash リスクの予測）
   - **source of truth**: 手元が配布コピー（ホームディレクトリ配下等）なら正本（テンプレート repo・プロジェクト repo）を特定する。特定できなければユーザーに確認する。実験は複製で行えるが、採用の反映先と bank の置き場は常に正本
   - **変更タイプ**: 下の taxonomy で分類し、計測器の選択に直結させる
3. **改善方針の合意**: 現状と期待のギャップを明文化し、何をどう変えるかをユーザーと合意する
4. **題材の先行固定（eval-first）**: **candidate を書く前に**、題材タスク・期待品質・名指し観点を確定する（設計要領は `references/instruments.md`）。bank に関連題材があれば回帰題材として組み込み、無い部分は新設計する。起草後に題材を作ると、candidate が通りやすい題材を無意識に選ぶ設計バイアスが入る — 順序自体が blind の一部
5. **candidate 起草と統合・整理**: 現行版一式を一時ディレクトリに複製して編集する（正本・配布コピーを直接編集しない）。**差分の継ぎ足しで終えず、影響範囲を既存記述ごと統合・整理して一つの整合した最終版にする** — 継ぎ足しは重複・矛盾・dangling 参照・設計のドリフトを溜め、差分レビューでは全体の破綻を見逃す。必要なら節構成も再編する。記述は現在形で現設計の意図だけを書く
   - **変異レース（コストゲート付き）**: 構造の再設計を伴うとき、または前ラウンドで candidate が負けたときは、**仮説の異なる candidate を 2 案**（例: 規則列挙型 vs 原則+判断基準型、手順統合型 vs 分離型）起草して同一 A/B でレースしてよい。局所修正の積み重ねでは出られない構成へ跳ぶための計測器。軽微な変更では使わない
6. **証拠測定**: 下の「計測器の選択」で計測器を決め、選択と理由を宣言してから実施する（実施手順・雛形は `references/instruments.md`）
7. **判定**: 採用 / 低マージン採用 / 不採用。採用時は「この変更が**何を犠牲にしうるか**」を 1 行で明記し、それが統制題材・回帰題材で覆われていることを確認する（汎用的な改善は別の挙動を壊しうる — 改善の一般論を無条件に信じない）。レースで負けた案にも特定題材でだけ勝った要素があれば、勝ち案へ**交叉**して採り込み、交叉部分は再測定する
8. **記憶と正本反映**: 判定の根拠になった題材・期待品質・判定・観測されたトレードオフを対象 skill の `evals/scenarios.md` へ書き戻す（`references/scenario-bank.md`）。採用は正本へ反映し、題材設計・judge 観点の一般知見は本 skill の references に還元する

## 計測器の選択

変更の性質で計測器を選ぶ。迷ったら重い側に倒す（軽い側の誤選択は、挙動に影響する変更を無検証で通す事故につながる）。

| 変更の性質 | 計測器 |
| --- | --- |
| ロード境界・分岐・既定値・判断基準を変えない表現整理 | **self-check** のみ: candidate を通読し「意図しない意味変化・判断基準の変化がないか」「description（トリガー）への影響がないか」を確認 |
| 挙動・判断・出力構造・既定値・references のロード境界を変える | **blind A/B**（instruments.md）。タイプ②は base floor、タイプ③はコスト計測、タイプ④は発火対を併用 |
| 内部機構（分類ルーティング・報告永続化・recheck 等、実行の流れ・信頼性を変える変更） | **dogfood** 主: 候補を実際の変更 diff・実タスクに走らせ、機構が働くか（分類・出力契約・統合整合）を観測する。単一実行の質 diff に現れにくく blind A/B では wash しやすい。対象がレビュー系 skill なら候補による自己レビュー、本 skill 自身なら直近の実走で「機構が働いたか・どこを手作りで補ったか」の観察がそのまま dogfood。behavioral な質に劣化リスクがある層は A/B で補完 |
| 剪定（節・機構の削除、圧縮） | **ablation A/B**: 削った版 vs 現行を、bank の回帰題材（当該節が根拠になった題材を優先）で比較し、質が落ちなければ削除を採用 |
| bank を持つ skill への、挙動に触れる後続変更（self-check だけで済む表現整理は除く） | 上のいずれかに加えて**回帰再走**: bank から関連題材を選び candidate で再走し、過去に確立した挙動の退行がないか確かめる |

複数配布先（例: Claude Code と Codex CLI）に配られる skill で強モデル前提の書き方が疑われるときは、弱い側の実行条件でも 1 走確かめる（floor。低マージン判定の根拠にもなる）。

## 変更タイプ（taxonomy）

| タイプ | 例 | 検証設計の要点 |
| --- | --- | --- |
| ①構造・既定値 | 成果物の構造・既定挙動を変える（goal anchor 追加、質問の構造化、雛形・手順の追加） | 既定挙動でない構造変化は A/B で差が出やすい。改善が特定分岐でのみ発火するなら題材をその分岐に倒す |
| ②検出・判断 | 見落とし検出・判断品質を上げる | 強モデルは base でも拾いがちで wash になりやすい。base floor 測定ときわどい題材が必須。差は「不確実性処理の規律」に出やすい |
| ③効率 | 探索・読み込み・手戻りを減らす | 非効率が実害になる規模の題材で測り、コスト（tokens / 所要時間）も判定材料にする |
| ④トリガー・分岐 | description・gate・レベル選択を変える | 発火検証（should / should-not の対）を健全性ゲートとして通す |

## 評価軸

評価するのは「**この指示に従うと開発の成果物・判断の質が高まるか**」。

- 目的達成: ユーザーが本当に達成したいこと（ビジネス価値）を的確に捉え達成しているか
- スコープ判断の的確さ: 扱う範囲の振り分け（同対応 / 後続 / 対象外）が過不足ないか
- 成果物の質: 読み手がそのまま次工程に進める質か
- 手戻り / 事故リスク: 無関係変更の混入・scope 逸脱・停滞を招く判断がないか

手順や分岐が発火したこと自体は改善の根拠にしない。タイプ④の発火検証は質評価の前提となる健全性ゲートとしてだけ使う（発火しなければ質を見る以前に不採用）。

## 判定

- **採用**: 改善が実挙動で観測できた
- **低マージン採用**: 強モデルでは差が出ないが、floor（弱い実行条件での下支え）として残す価値を説明できる
- **不採用**: 改善が観測できず、floor 価値も説明できない

差が出ないときは、まず題材が改善を分離できているか（きわどさ・規模・名指し観点）を疑って設計し直す。再設計しても差が出なければ、低マージンか不採用かを正直に切り分ける。

- **wash は剪定の合図**: 題材を設計し直しても base ≒ candidate なら、その変更は「不要ルールの疑い」が濃い。挙動に現れない重い機構は本質だけ残して compact 化し、指示過多（標準ケースの遵守率・出力品質を下げる）を避ける — 継ぎ足しの累積そのものが劣化要因になる。肥大が疑われる既存節には、wash を待たず ablation を能動的に当ててよい
- **A/B は採用ゲートに留めず改善のドライバーとして使う**: 劣り / wash の失敗モードをトレース（挙動要約）から特定して該当改善を作り直し再検証する（instruments.md「unblind 敗因分析と差し戻しラウンド」）。合否判定に留めず、観測した欠陥クラスを改善へ還元して質を引き上げる

## 責務の境界

- 変更の正しさ（バグ・設計・セキュリティ・不変条件）のレビューは km:review の責務。本スキルは「変更で開発の質が上がるか」（behavioral）の検証に絞る。**二層は相補的**で、A/B を通過しても km:review が静的な不変条件の綻び（例: 統合・圧縮で落ちた load-bearing な gate）を捕捉することがある。skill 改善の採用前に both を通す。A/B で gate 遵守を既に観測済みの層は correctness 側を軽量チェックに留めてよい（コスト原則）
- 新規 skill をゼロから作ることや、assertion ベースの定量 eval を回すことは対象外
- A/B と judge には実環境の subagent 機構（Claude Code の Task tool 等）を使う
