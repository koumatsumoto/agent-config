# Blind Judge 雛形

A/B 成果物の質を判定する第三の subagent へ渡すプロンプトの雛形。都度ゼロから組み立てると観点の渡し方がぶれて判定の再現性が下がるため、この雛形の `<...>` を埋めて使う。

## 使い方

- 2 成果物は「A」「B」とだけラベルし、どちらが base / candidate かを伝えない
- A / B への割り当ては任意に選ぶ（毎回 base = A に固定しない）
- 名指し観点には「この改善が狙う具体挙動」を書く。judge の総合評価に埋もれると、狙った改善の有無が判定に現れない

## プロンプト雛形

```
あなたは skill の A/B 運用テストの independent judge です。2 つの成果物 A / B は、同一タスクを異なる指示書で処理した結果です。どちらがどの版かは伏せられており、提示順にも意味はありません。成果物の質だけで判定してください。

## 題材タスク
<タスク本文>

## 対象 skill の目的
<対象 skill が何のための skill か 1-2 行>

## 成果物 A
<成果物 A>

## 成果物 B
<成果物 B>

## 評価軸
- 目的達成: ユーザーが本当に達成したいことを的確に捉え達成しているか
- スコープ判断: 扱う範囲の振り分け（同対応 / 後続 / 対象外）が過不足ないか
- 成果物の質: 読み手がそのまま次工程に進める質か
- 手戻り / 事故リスク: 無関係変更の混入・逸脱・停滞を招く判断がないか

## 名指し観点（重点比較）
<この改善が狙う具体挙動を列挙する。例:
- 検出・判断系: 仕込んだ欠陥（<欠陥の内容>）への言及の有無と扱いの質 / 過剰検出（無関係な指摘の量産・過剰なブロック判定）の不在 / 不確実性処理の規律（確定できない懸念を曖昧に hedge するか、覆す条件を名指しした構造化された保留にするか）
- 構造系: <期待する構造要素> の有無と質>

## 出力形式
1. 評価軸ごとの優劣と根拠（成果物からの具体的な引用・参照を必ず添える）
2. 名指し観点の比較結果（観点ごとに A / B / 同等）
3. 総合判定: A / B / 僅差。優劣を根拠をもって示せないときは無理に勝敗を付けず「僅差」と申告する
4. 各版の長所・短所

どちらの版がどの指示書によるものかの推測はしない。判定は成果物の質のみで行う。
```

## 判定の読み方

- 「僅差」申告は再走のトリガーとして扱う（ab-testing.md「判定と再走」）
- 名指し観点で candidate 側が勝ち、総合が僅差の場合、狙った改善は「観測できた」と扱ってよい（総合は他要因のゆらぎを含む）。逆に総合で勝っても名指し観点に差が無ければ、狙った改善の証拠にはならない
