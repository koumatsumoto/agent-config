# scenario bank（検証の記憶）

skill ごとに、検証で使った題材と確立した期待品質を蓄積するファイル。改善のたびに題材をゼロから設計し捨てる状態をやめ、後続の変更で回帰題材として再利用する（instruments.md「回帰再走」「ablation」の入力源）。bank は「この skill が満たし続けるべき挙動」の実行可能な仕様集として機能する。

## 置き場

対象 skill の**正本**ディレクトリ直下の `evals/scenarios.md`（例: `templates/skills/<name>/evals/scenarios.md`）。配布コピー側の bank は編集しない。bank が無い skill への初回検証で、判定の根拠になった題材があれば新規作成する。

## エントリ様式

1 題材 = 1 エントリ。判定に使わなかった思いつきは書かない（bank の信頼性が回帰の価値を決める）。

```markdown
## <短い題材名>

- 対象層: <この題材が検証する skill の層・分岐>
- 題材: <タスクプロンプトの要旨と実行条件（sandbox・与える repo / diff・実行時前提）。再現に足る具体度で>
- 期待品質: <合否を判定できる形の期待挙動・名指し観点。「〜が成果物に含まれる / 〜へ倒れない」>
- 判定: <最終判定と日付。例: 採用の根拠（2026-07-17, PR #138）/ 統制として維持>
- トレードオフ / 注記: <この題材で観測された揺らぎ・犠牲にしうるものへの注記。無ければ省略>
```

## 運用

- **読む**: 診断（SKILL.md フェーズ 2）で必ず確認する。効く層と重なるエントリが、回帰題材・ablation 題材の第一候補
- **書く**: 記憶フェーズ（SKILL.md フェーズ 8）で、今回の判定の根拠になった題材を追記する。既存エントリと同じ層を検証する題材は統合し、エントリの重複を作らない
- **更新・退役**: 設計判断が変わり期待品質が陳腐化したら、エントリを現行の期待に書き換えるか削除する。過去の判定履歴の保全は commit / PR に任せ、bank には「現在も成立すべき期待」だけを残す
- **規模**: 1 skill あたり数エントリ〜十数エントリに保つ。回帰再走のコストは bank の規模に比例するため、層の代表題材だけを残し、同一層の細かい変種は統合する
