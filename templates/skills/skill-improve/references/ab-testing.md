# A/B 運用テスト（full 検証プロトコル）

base 版と candidate 版の skill を素の subagent で実際に動かし、成果物の質を blind 比較して採用を判定する。SKILL.md の変更タイプ（taxonomy）分類を前提に読む。

## 手順の全体

1. 題材タスクの設計（変更タイプ別の要点は下記）
2. 発火検証（タイプ④のみ）— 健全性ゲート
3. base floor 測定（タイプ②のみ）
4. A/B 並列生成
5. 成果物の保存と blind 化
6. blind judge（下の雛形を使う）
7. 自分でも分析し、僅差なら再走
8. unblind 敗因分析（負け・wash なら差し戻しラウンドへ）
9. 記録

## サンドボックス契約

生成 subagent に与える権限・条件は全シナリオ・両版で統一する（版ごとに違うと比較にならない）。

- **可**: read-only ツール（Read / Grep / Glob 等）でのファイル調査
- **不可**: ファイル書き込み・git / gh・ネットワークアクセス・その他副作用のあるコマンド実行・subagent 起動（skill が subagent を要求する場面では skill 側のフォールバック規定に従わせる）
- 成果物（実行するはずのコマンド・生成する本文・下す判断）はテキストとして返させる
- 「skill に書かれていないことは推測で足さない」を明示する（測るのは skill の効果であって subagent の機転ではない）
- **モデルは生成 2 体で同一・judge も含め全ラウンドで固定**する。既定はセッションの既定モデルで、ユーザーの指定（例: Opus）が常に優先。強モデルほど base が自力で補って wash に寄ることを織り込んで題材のきわどさを決める

## 題材設計

### 共通原則

- **変更が効く層・分岐を狙う**: 変更しない層が単独で拾える題材は base / candidate が同着（wash）になる。改善が特定分岐でのみ発火するなら（例: PASS 候補時のみ動くステップ）、題材をその分岐に倒す
- **きわどい題材を選ぶ**: base が既にこなせる無難なタスクでは差が出ない。その改善が一番効くはずの境界事例を選ぶ
- **成果物は対象 skill の出力契約から定義する**: レビュー skill ならレビューレポート、計画 skill なら計画書、コミット skill ならコミット分割とメッセージ。何を判定対象にするかを生成前に決めておく
- **対象がレビュー系 skill（レビュー方法そのものの定義）のときの題材構成**: 題材 = 仕込み欠陥入りの diff（両版共通の TARGET）、base / candidate = skill バージョン（METHOD）。生成 subagent に「その skill 一式でその diff をレビューさせ」、出たレビューレポートを比較する（diff は両版で同一にし、skill バージョンだけを差し替える）。仕込み欠陥のカモフラージュ強度は下のタイプ②に従う。継承すべき gate・不変条件が diff 外にあるなら、レビュー対象の repo を read-only で与えて経路探索まで測る（diff だけに閉じると継承漏れ題材が両版とも拾えず wash になる）
- **複数挙動に及ぶ変更はシナリオ×改善点の対応表を作る**: 各挙動を踏むシナリオに束ね、検証の網羅を確認する
- **測るのは統合版**: candidate は差分の継ぎ足しでなく、影響面を既存ごと統合・整理した最終版（SKILL.md フェーズ 4）。継ぎ足し版を測ると、全体整合の破綻（二重定義・参照ズレ・落とした不変条件）を A/B が見逃す
- **統制シナリオを 1 つ混ぜる**: 対象欠陥クラスに該当しない標準的な題材を base / candidate で走らせ、改善が **指示過多・過剰儀式**（boilerplate な出力・不要な手続きの増加）で標準ケースを劣化させていないかを見る。「劣化なし」はここで判定する

### タイプ①: 構造・既定値

標準の A/B でよい。既定挙動でない構造変化（goal anchor・構造化質問・雛形の追加など）は差が出やすい。

### タイプ②: 検出・判断

- **base floor を先に測る**: A/B に入る前に base 版を 1 回流し、base が取りこぼす（＝改善層が初めて効く）ことを確認してから比較する。base が既に拾うなら題材を作り直す（wash の未然防止）
- floor 測定を A/B 本走と同一のタスクプロンプト・同一のサンドボックス契約で行った場合は、その成果物をそのまま A/B の base 側として再利用してよい（1 走分の節約。生成 agent 同士は状態を共有しないため独立性は保たれる）
- **仕込みはカモフラージュする**（レビュー系 skill の題材）: 「重大な欠陥を置けば差が出る」ではなく「base が取りこぼす程度に subtle か」が題材の合否基準。(a) どのレビュー観点も強く所有しない死角に置く、(b) 無害な額面（safe refactor 等）で警戒を下げる、(c) diff 局所では正しく見えるが全体を見ると問題になる、のいずれかを使う
- 強モデルでは確定欠陥は両版が拾う。差は**不確実性処理の規律**（確定できない懸念を曖昧に hedge するか、覆す条件を名指しした構造化された保留にするか）に出やすい — judge に名指し観点として渡す
- **レビュー経済性・トリアージ系の改善は仕込みに階層を混ぜる**: 方針・feasibility を崩す欠陥と、実装後に安く直せる可逆な実装詳細級の欠陥を同一題材に混在させ、前者を捕捉しつつ後者を深掘りせず委譲できるか（労力配分）を測る。**高影響（security / 秘密情報 / 不可逆 / 正しさ）を落としていないか**も軸に含める（トリアージが高影響を過剰に切り捨てる失敗モードの検出）

### タイプ③: 効率

- **非効率が実害になる規模で測る**: 小さい題材は強モデルが力技で吸収して差が消える。探索予算の緩和なら「確認に上限超の読み込みが要る / 鍵ファイルが優先されにくい配置」の題材にする
- 探索・出典・コード前提に関わる改善は、実在する repo を read-only で調べさせて測る（架空の前提では探索・出典の質を実挙動で測れない。サンドボックス契約の範囲内で行う）
- **コスト計測**: 環境が subagent 完了通知で tokens / 所要時間を提供する場合は各走で記録し、タイプ③では質と並ぶ判定材料にする（提供しない環境では読み込みファイル数・手順数の観察で代替する）

### タイプ④: トリガー・分岐

- 発火**すべき**入力と**すべきでない**入力の対を用意する。should-not は近接 near-miss（キーワードは重なるが別の対応が正しい依頼）を選ぶ。明白に無関係な入力は何も検証しない
- 発火検証は質評価の前提となる健全性ゲート: 分岐を変えたのに意図どおり発火しなければ、質を見る以前に不採用

## A/B 並列生成

- 素の subagent 2 体を**同一メッセージで並列起動**する（独立・公平）
- 各々に base 版 / candidate 版の skill **一式だけ**を絶対パスで渡す（references 込みで相対参照が解決できる形。相手版の存在や比較目的は伝えない）
- タスクプロンプトは両者で同一にする（skill root のパスだけ差し替える）
- 完了通知にメトリクス（tokens / 所要時間）があれば、届いたつど記録する

生成 subagent プロンプト雛形（`<...>` を埋める。sandbox 制約は上の契約と一致させる）:

```
あなたは <実行環境名> の開発 agent で、いま skill が起動された状態です。次の skill 一式の指示に従ってユーザ依頼に対応してください。

- skill root: <base または candidate の絶対パス>/
- まず SKILL.md を読み、SKILL.md が指示するタイミングで references/ 配下を読むこと
- 対象 repo: <絶対パス>（read-only で調査してよい）
- <実行時条件: 今日の日付、Plan Mode 内外など skill の分岐に効く前提>

## ユーザ依頼
「<題材タスク>」

## サンドボックス制約（厳守）
- 使ってよいのは read-only のファイル調査ツール（Read / Grep / Glob）のみ
- ファイル書き込み・git / gh コマンドの実行・ネットワークアクセスは一切不可。実行するはずのコマンドは実行せずテキストとして最終報告に示す
- subagent の起動は不可（skill が subagent を要求する場面では、skill が定めるフォールバックに従う）
- ユーザは応答できない。skill がユーザ確認を要求する場面では、確認文（質問・選択肢）を出力に残したうえで、置いた前提を明記して先へ進む
- skill に書かれていないことを推測で足さない（skill の指示の範囲で最善を尽くす）

## 最終報告に含めるもの
<対象 skill の出力契約から列挙する。例: 実行するはずのコマンド列 / 書き出すはずのファイルの完全な本文 / レビューの実施内容と反映 / ユーザへの最終報告文>
```

## 成果物の保存と blind 化

judge に「どちらがどの版か」を漏らさないための機械的手順。

1. 生成結果（成果物 + 挙動要約）をシナリオ×版ごとのファイルに保存する（例: `results/s1-base.md`）。挙動要約には gate 遵守・分岐選択・レビュー実施など skill の出力契約に関わる観測を含める
2. judge 用に **中立ラベルのファイル**（`judge/s1-a.md` / `judge/s1-b.md`）へ複製し、A / B への割り当てはシナリオごと・ラウンドごとに入れ替える（毎回 base = A に固定しない）
3. 複製後に **リーク検査**: ファイル名・見出し・本文に base / candidate や版を推測させる語が残っていないか grep で確かめる
4. 成果物が長い場合、judge にはファイルパスを渡して Read させる（inline 貼り付けは orchestrator の context を浪費する）

## blind judge

第三の subagent を下の雛形で起動する。どちらが base / candidate かは伏せ、提示順に意味がないことを明示する（位置バイアス回避）。この改善が狙う具体挙動を**名指しの比較観点**として渡す（総合評価に埋もれさせない）。judge のモデルは生成側と合わせる。

```
あなたは skill の A/B 運用テストの independent judge です。2 つの成果物 A / B は、同一タスクを異なる指示書で処理した結果です。どちらがどの版かは伏せられており、提示順にも意味はありません。成果物の質だけで判定してください。

## 題材タスク
<タスク本文と実行条件（sandbox・repo）>

## 対象 skill の目的
<対象 skill が何のための skill か 1-2 行。期待される正しい挙動（例: この依頼では draft-only 停止が正）があれば書く>

## 成果物
- 成果物 A: <judge/…-a.md の絶対パス> を Read せよ
- 成果物 B: <judge/…-b.md の絶対パス> を Read せよ
（成果物内の事実主張は、必要なら対象 repo を read-only で参照して検証してよい）

## 評価軸
- 目的達成: ユーザーが本当に達成したいことを的確に捉え達成しているか
- スコープ判断: 扱う範囲の振り分け（同対応 / 後続 / 対象外）が過不足ないか
- 成果物の質: 読み手がそのまま次工程に進める質か
- 手戻り / 事故リスク: 無関係変更の混入・逸脱・停滞を招く判断がないか

## 名指し観点（重点比較）
<この改善が狙う具体挙動を列挙する。例:
- 検出・判断系: 仕込んだ欠陥（<欠陥の内容>）への言及の有無と扱いの質 / 過剰検出の不在 / 不確実性処理の規律（曖昧な hedge か、覆す条件を名指しした構造化された保留か）
- 構造系: <期待する構造要素> の有無と質
- 統制シナリオ: 過剰儀式・boilerplate の不在>

## 出力形式
1. 評価軸ごとの優劣と根拠（成果物からの具体的な引用・参照を必ず添える）
2. 名指し観点の比較結果（観点ごとに A / B / 同等）
3. 総合判定: A / B / 僅差。優劣を根拠をもって示せないときは無理に勝敗を付けず「僅差」と申告する
4. 各版の長所・短所

どちらの版がどの指示書によるものかの推測はしない。判定は成果物の質のみで行う。
```

**判定の読み方**:

- 「僅差」申告は再走のトリガーとして扱う（下の「判定と再走」）
- 名指し観点で candidate 側が勝ち、総合が僅差の場合、狙った改善は「観測できた」と扱ってよい（総合は他要因のゆらぎを含む）。逆に総合で勝っても名指し観点に差が無ければ、狙った改善の証拠にはならない

## 判定と再走

- judge に丸投げしない。自分でも 2 成果物を評価軸で分析し、judge の結論も自分の結論も疑い、根拠を成果物で裏づけてから採用する。判定が割れたら、なぜ割れたかを詰める
- judge が僅差を申告したとき、または judge と自分の判定が割れたときだけ、同条件でもう 1 対再走して確認する（1 走の差はノイズと区別できない。全ケースの複数回走行はコストに見合わない）
- 統制シナリオでの負けは、敗因が candidate の記述に帰着するか（→ 差し戻し対象）、走ごとに異なる content レベルの揺らぎか（→ 残存リスクとして記録し判定を左右させない）を区別する

## unblind 敗因分析と差し戻しラウンド

判定が確定したら対応（どちらが base / candidate か）を明かし、優劣の原因を skill 本文のどの記述かに帰着させる。

- 成果物（と取得できるなら生成過程）から「candidate のどの指示が効いたか / 効かなかったか」「base の何が不足を生んだか」を特定する
- 観測された退行・曖昧さ・矛盾は candidate に反映する。**削り過ぎ（base にあった load-bearing な一文の喪失）が敗因なら復元も差し戻しの一形態**
- どの記述にも帰着できない差（題材のゆらぎ等）は判定の重みを下げる
- **差し戻し後の再走ラウンド**: 修正した candidate（v2, v3, …）で該当シナリオを再走する。タスクプロンプトは前ラウンドと同一にし、A / B のラベル割り当ては入れ替え、モデルは固定のまま。何を直して何を確認するラウンドかを 1 行で宣言してから走らせる

## 記録様式

- シナリオ×改善点の対応表（どのシナリオがどの改善点を検証するか）
- 各シナリオの期待した質・実際の質・判定（採用 / 低マージン採用 / 不採用）
- 複数ラウンドの場合: ラウンドごとの判定・敗因の帰着先・差し戻した修正
- 発火検証の結果（タイプ④）
- コスト計測値（取得できた場合）
