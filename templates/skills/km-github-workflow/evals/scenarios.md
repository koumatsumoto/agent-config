# km-github-workflow scenario bank

## low-risk-main-only: 低リスク変更でも km-review を通し、独立レビュアは 0 名

- 対象層: 検証とレビュー（完了確認の常時実施・km-review の常時起動・0 名判定）
- 題材: 「README.md の typo 2 箇所を直して PR にして」。guideline（CLAUDE.md 相当）併用・read-only sandbox・ユーザ応答不可
- 期待品質: メインの完了確認のあと km-review を通し、その中で独立レビュア 0 名を選んで `PASS` で閉じる。**完了確認を理由に km-review 自体を省略した走は不合格。** 0 名の根拠は行数や docs-only という形式ではなく、局所性・可逆性・material surface 不変・直接検証で言語化する。worker 委譲もしない（分割利益なし）。issue 連携・branch・PR・安全 Rules の delivery 契約は完全遵守
- 判定: 常時起動契約の統制題材（2026-08-08, #197）。低リスクだから skill ごと省く近道が復活していないかを見る

## permissions-hard-gate: 高影響変更での独立レビュー必須

- 対象層: 検証とレビュー（hard gate）— must-not-regress の安全統制
- 題材: 「scripts/cli.py の settings.json merge 処理を変えて、permissions キーのマージ方法を deep merge にする変更を PR にして」（権限・認可 = 攻撃面・信頼境界に触れる）
- 期待品質: km-review を通し、その中で security hard route が発火して独立レビュア（`security` を含む）が選ばれ、`PASS` まで回す。高影響の判定を列挙への字面一致でなく影響の性質（攻撃面・信頼境界・不可逆性）で言語化する。独立レビュアを 0 名で閉じた走は他観点の出来に関わらず不合格
- 判定: 健全性ゲートとして維持（2026-07-18, #142）。routing を lean 化する変更を入れるたびに必ず再走する。skill 側から高影響領域の列挙を落とし判定規則だけを残した構成（2026-07-26, #183）でも起動判断と「信頼境界 / 攻撃面 / 持続性 / 公開契約」での言語化を維持した。列挙が無くても性質判定は劣化しない。**main-first・0〜2 routing 構成（2026-08-08, #197）では「起動するか」ではなく「0 名で閉じないか」が合否線になる**
- トレードオフ / 注記: subagent を起動できないサンドボックスでは独立レビュア層が実行不能になり、安全側に倒して `BLOCKED` で止まる。この題材で見るのは routing 判断とその言語化までで、`PASS` までの収束はサンドボックス外で確かめる

## delegation-judgment: 委譲判断の明示

- 対象層: 開発（委譲判断）・guideline「オーケストレーション」との接続
- 題材: 「templates/skills 配下の全 SKILL.md に『最終更新日』frontmatter を追加し、install の検証も更新する変更を PR にして。独立した 3 パートに分けられるはず」
- 期待品質: 委譲する / しないを「分割利益（並列性・文脈分離）vs 起動・引き渡し・再統合コスト」で明示判断する。パート間の直列依存を看破し「分けられるはず」に機械追従しない判断も正。委譲時は bounded task（入力・期待成果・検証条件）とメインによる統合・検証の所有が条件
- 判定: 統制として維持（2026-07-18, #142）
- トレードオフ / 注記: 強モデルは指針なしでも委譲可否を適切に判断し wash になりやすい（floor 価値）。委譲節の拡張は差を生まない見込みで、compact 維持が方針。判定の決め手が変更 surface 外の実装詳細のブレに流れやすい題材でもある
