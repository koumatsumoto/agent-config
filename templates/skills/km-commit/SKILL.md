# Commit

変更を確認し、一つの目的として説明・検証・取り消しができる単位でコミットする。必要なファイルだけをステージし、明確に分離できる独立した変更はコミットを分ける。
メッセージだけで、変更の意図と重要な判断を`git log` / `git blame`からたどれるようにする。

## メッセージ

- 件名は`type: 日本語の要約`または`type(scope): 日本語の要約`。type / scopeは英語とし、scopeは実在するdirectory / package / skill名をそのまま使える場合だけ付ける。
- 件名には何をどう変えるかと、その効果・意図を書く。「レビュー指摘を反映」「〜修正の修正」など、作業経緯を件名にしない。
- 設計判断がある場合は、問題・判断・理由を本文に書く。差分から自明な説明や、内部タスク・作業ログ・レビュー往復は省く。
- 自明な変更は件名と、必要なら1〜2行で足りる。
- 関連issueがあれば末尾に`Refs #N`を置く。`Closes`はPR本文で使う。

## 禁止事項

- `git add -A` / `git add .`を使わない。
- `git commit --no-verify`を使わない。
- pushは行わない。
