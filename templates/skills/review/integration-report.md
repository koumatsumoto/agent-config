# Review 統合出力フォーマット

km:review Phase 4 (統合) が main コンテキストで生成する統合レポート形式。

## 統合サマリー (必ず冒頭に出力)

```
## 統合レビュー結果

**実行レベル**: standard
**対象スコープ**: uncommitted | pr:123 | a1b2c3d..HEAD | --repo src/api 等
**変更概要**: feat | コード 450行 (8ファイル) + ドキュメント 80行 (3ファイル)
**総検出件数**: CRITICAL: 0 / HIGH: 1 / MEDIUM: 3 / LOW: 2
**コミット判定**: ⚠️ BLOCKED（HIGH 以上の問題あり）
```

## 各 Phase の詳細

各 Phase の結果をセクションごとに表示する。スキップした Phase は見出し + `（スキップ）` を出力 (省略しない)。Phase 3 は中央 dedup 後の所見を表示する。

```
---
### Phase 2: Code Review (generalist)
CRITICAL: 0 / HIGH: 1 / MEDIUM: 1 / LOW: 0

## HIGH: [問題タイトル] [confirmed]
**場所**: src/api/users.ts:42
**問題**: ...
**修正**: ...
---
### Phase 3: 第三者レビュー
CRITICAL: 0 / HIGH: 0 / MEDIUM: 1 / LOW: 0

#### システムアーキテクト
CRITICAL: 0 / HIGH: 0 / MEDIUM: 1 / LOW: 0

## MEDIUM: [問題タイトル] [confirmed]
**場所**: src/api/auth.ts:28
**問題**: ...
**修正**: ...

#### セキュリティ専門家
CRITICAL: 0 / HIGH: 0 / MEDIUM: 0 / LOW: 0
（指摘なし）

#### 敵対レビュア

（指摘なし）

CRITICAL: 0 / HIGH: 0 / MEDIUM: 1 / LOW: 1
```

スキップ / defer の表記例: `### Phase 3: 第三者レビュー\n（スキップ - standard レベルのため）`。doc-review は `### Phase 5: Doc Review\n（defer - コード解消後に実施）` / `（スキップ - test/config/chore のため）` 等。

## 中央 dedup ルール

重複の集約は Phase 4 統合 (main コンテキスト) が一括で行う。各レビュア (Phase 2 / Phase 3) は自分の所見を出すだけでよく、重複回避を予測しない。

判定基準: `(file_path, 影響行範囲 ±5 行, 観点 / 根本原因)` が一致したら重複とみなす。**同一欠陥を別角度から記述したもの** (例: Phase 2「境界チェック欠落」/ architect「不変条件違反」/ security「OOB read」) も意味的に同一群とみなす。タイトルの wording 揺れ (例: 「所有者検証なし」vs「BOLA」) は照合の補助に留める。

集約方針: 重複群からは最も証拠の濃い 1 件 (役割固有の補足や、より高い確信度・重大度を持つもの) を残し、他は drop して残した所見の末尾に併合注記する。

```
## 併合注記
- 併合元: `<drop した指摘タイトル / 場所>`
- 追加情報: 攻撃シナリオ / 不可逆性・波及 / 再現条件のうち該当するもの
```

## 優先順位付きアクションリスト

統合レポート末尾に、全 Phase の所見を対応優先度で並べたアクションリストを出力する。分類基準は SKILL.md「指摘対応の方針」。

```
## アクションリスト
### 1. マージ前必須 (CRITICAL / HIGH)
- [HIGH] <タイトル> — <file:line> / 修正方針: <PASS への最短経路>
### 2. 同一 PR で修正 (MEDIUM / LOW)
- [MEDIUM] <タイトル> — <file:line> / <修正方針>
### 3. PR 目的の外 (follow-up 候補)
- <タイトル> — <理由: なぜこの PR の範囲外か>
### 4. 相互関係
- <同一根本原因でまとめられる指摘群>
```

該当のないカテゴリは見出しを省略してよい。

## 確認推奨ノート (`PASS` を維持したまま付す)

Phase 4 の PASS 反証 (SKILL.md Phase 4-5) で、見落としが潜みうる箇所を **具体的に名指せたが安価には確定できなかった** ものを、`PASS` を覆さない非ブロッキングのノートとして記録する。重大度を付けず、総検出件数にも算入しない。`PASS` だが念のため確認すべき点をユーザに渡すのが目的で、裏づけのない一般的な疑いは書かない。

```
## 確認推奨 (PASS 維持)
- <未カバー surface / 潜伏しうる箇所> — 何が分かれば PASS を覆せるか: <最小の追加情報>
```

確定した (裏づけ済みの) 見落としは確認推奨ノートにせず、正規の所見として扱い判定を `BLOCKED` に更新する。指摘も確認推奨も無い `PASS` のときは本セクションを省略する。

## 受け入れ済みリスク (ユーザ判断で残す場合のみ)

大規模修正・仕様変更・設計トレードオフでユーザ判断を要する指摘を、直さず残すと決めた場合のみ次の形式で明示記録する (好み・様式の指摘や、変更に起因する欠陥はこの形式で残さず直す):

```
## 受け入れ済みリスク
- **重大度**: HIGH
- **残す理由**: <なぜ今 PR で直さないか>
- **後続対応条件**: <いつ / どの条件で対応するか>
```

## 共通ルール

1. 統合サマリーに実行レベル・対象スコープ・変更概要・総検出件数・コミット判定を含める
2. 全 Phase の重大度ごとの件数を合算する。Phase 3 は中央 dedup 後の件数を使う
3. 同一ファイル・近接行の類似指摘の集約 (dedup) は Phase 4 統合が一括で行う (判定基準は本ファイルの「中央 dedup ルール」)
4. コードレビュー層 (Phase 2 + Phase 3) に `CRITICAL` または `HIGH` が残れば `BLOCKED`。doc-review (Phase 5) が CRITICAL/HIGH を出した場合も `BLOCKED` に更新する
5. スキップ / defer された Phase は見出しと理由を出力。セクション自体を省略しない
6. Phase が結果を返さなかった場合は `（実行失敗）` として記録し失敗理由を含める。実行失敗 Phase が 1 つでもあれば全体判定は **安全側に倒して BLOCKED** とする
7. 指摘がゼロの Phase は件数サマリーと `（指摘なし）` を出力
8. レビュー対象がなく Phase 1 で終了した場合は `**コミット判定**: ⏭ NOOP（対象なし）` の単行を出力するだけで Phase 2 以降のセクションは省略してよい
9. PASS 反証 (SKILL.md Phase 4-5) で確定しなかった潜伏候補は「確認推奨ノート」として `PASS` を維持したまま記録し、総検出件数には算入しない。確定した (裏づけ済みの) 見落としは正規所見として `BLOCKED` に反映する
