# Phase 5: Doc Review

km:review orchestrator の **Phase 5**。**Phase 4 統合 (コード判定) の後**、コード/設計が確定した最終状態に対してドキュメント整合を確認する (起動条件・defer 規約は SKILL.md の Phase 5 を参照)。

doc-review は次の 2 つの関心を扱う。どちら (または両方) を実施するかは orchestrator (SKILL.md Phase 5 起動条件) が変更構成に応じて決める。

- **A. コード変更のドキュメント影響**: コード変更が、リポジトリ全体のどのドキュメントの記述を古く / 誤りにするかを **広く確認し、該当ドキュメントを修正する**。
- **B. ドキュメント変更の整合性**: 変更差分の周辺だけでなく、**変更されたドキュメント全体および関連ドキュメントの整合性** (構成・用語・前後関係・他ドキュメントとの矛盾/重複・一次情報との一致) を確認して整える。

レビュー時の行動原則: 違和感があれば関連ドキュメントまで辿る。明確なエラーでなくても、読者を迷わせる構成・古い記述・用語ゆれには敏感になる。

## A. コード変更のドキュメント影響

コード変更がドキュメントに与える影響を **リポジトリ全体のスコープで** 確認する。変更が外部に観測される接点 (下記) を起点に、影響を受けるドキュメントを repo 全体から探す。

影響を生みやすい変更 (起点の例):

- 公開 API / エンドポイント / 関数シグネチャ / CLI フラグ / サブコマンド
- 設定キー / 環境変数 / デフォルト値 / 必須要件
- 観測される挙動・出力・エラーメッセージ・終了コード
- 廃止 / 改名 / 移動 (deprecation・migration を要するもの)
- セットアップ / インストール / 実行手順に影響する依存・前提の変更

確認手順:

1. diff から「外部に観測される接点」を洗い出す (上の起点)
2. それらに言及するドキュメントをリポジトリ全体から探す (`README` / `docs/` / `AGENTS.md` / `CLAUDE.md` / 各 skill・rule doc / 仕様を説明する docstring・コメント)。対象語 (API 名・フラグ名・設定キー・コマンド名) を横断検索する
3. 古い / 矛盾する記述を **修正する**。修正しきれない波及は指摘として残す
4. Codex CLI では `AGENTS.md` が主、`CLAUDE.md` は fallback

## B. ドキュメント変更の整合性

変更されたドキュメント (および docs-only / `--repo` で対象に含まれるドキュメント) を **全体として** 読み、部分的な追記・修正で崩れた整合性を検出して整える。差分の周辺だけを見ない。

### B-1. ドキュメント内整合性

- セクション構成の論理的な流れ (順序・粒度の統一)、目次・見出しと内容の対応
- 用語・表記の統一、強調・リスト・コードブロック言語指定の一貫性
- 前後セクションとの整合 (前提の矛盾、説明の重複・欠落)
- 読者にとっての明瞭性 (専門用語の初出説明、前提知識の明示)

見落としやすいパターン: 部分修正で生じる「浮いたセクション」、見出しレベルの不整合 (h2 直下に h4)、冒頭概要と本体の乖離、手順の番号と実ステップ数の不一致、重要な警告の埋没。

### B-2. ドキュメント間整合性

- 同じ情報の複数ドキュメントへの重複・矛盾、一方更新・他方放置
- 内部リンク (ファイルパス・アンカー) の参照先の存在
- `CLAUDE.md` / `README` / `docs/` 三重管理の不整合、用語定義の揺れ

### B-3. 一次情報による正確性

記述を鵜呑みにせず一次情報まで遡る。優先順位: repo 内の実装・設定・ヘルプ出力 → 外部一次情報。外部リンクは存在確認を基本とし、内容精査はリスクの高いもの (API 仕様・セキュリティ勧告) に限定する。

- システム/API 仕様: 実装コードと一致するか
- 設定・コマンド: 実際の設定ファイルやヘルプ出力と照合
- 鮮度: 非推奨・廃止機能への言及、期限切れ表現

## 偽陽性フィルタリング (出さないもの)

- 今回の変更で導入されていない既存問題
- 単なる文体の好み / 読者層に合わせた意図的な簡略化
- 自動生成コンテンツだけの差分 / 未変更セクションだけへの一般論

構造上の問題や読者を迷わせる構成は、明確なエラーでなくても報告・修正する。

## 判定

重大度は「今すぐ直す重さ」で付ける (`experts/report-format.md` と共通の段階。doc 観点での目安):

- `CRITICAL`: 危険な手順・破壊的な誤情報
- `HIGH`: 明確な事実誤認、一次情報との不一致、構造破綻、コード変更に伴う必須更新の欠落
- `MEDIUM`: 整合性不足、曖昧さ、更新漏れ、読者を迷わせる構成
- `LOW`: 小さな改善

doc-review は Phase 4 のコード判定が `PASS` の最終状態に対して実行され、ここで `CRITICAL` / `HIGH` を出した場合は最終判定を `BLOCKED` に更新する。

## 出力フォーマット

機械可読の件数行 + 個別所見。所見の散文は内容が伝われば長さ・構成はレビュアの判断に委ねる。

```
### Phase 5: Doc Review
CRITICAL: 0 / HIGH: 0 / MEDIUM: 1 / LOW: 1

## MEDIUM: [問題タイトル]
**場所**: docs/architecture.md:42
**問題**: 何が問題か
**修正**: どう直すか
```

指摘ゼロ:

```
### Phase 5: Doc Review
CRITICAL: 0 / HIGH: 0 / MEDIUM: 0 / LOW: 0
（指摘なし）
```
