# Review

**メイン担当が先に確認、反証、修正、再検証し、その最終候補に残る重要なリスクにだけ独立レビュアを0〜2名使う。** 独立性は同じ差分を二重に読むためではなく、メイン担当が見落としたものを別の文脈で拾うために使う。

呼び出し元の完了確認（完了条件・差分・テストの照合）はレビューの代わりにならない。**それを理由に本 skill を省略しない。** 軽微な変更は「独立レビュア 0 名」としてここで閉じる。

判定は `PASS` / `BLOCKED` / `NOOP`。

## 対象

既定は未コミット差分とする。対象が明示された場合はその範囲を使い、対象がなければ`NOOP`とする。

- `--repo <subtree>` — 差分でなく現状コード全体。既存問題・未変更行を除外しない
- `--recheck` — `BLOCKED` 後の限定再確認（`references/recheck.md`）

## レビュー基準を固定する

既存の issue・完了条件・ユーザー指示を基準点として信頼し、要件を再導出・拡張しない。

- **要求意図と期待する成果**
- **対象範囲と対象外**
- **主な利用者と運用者**
- **変更面** — 挙動、公開契約、データ、権限、運用、挙動資産のどこが動くか

## メインレビュー

メイン担当は独立レビュアではなく、変更を統合するレビュー責任者である。

1. **確認する** — issue、完了条件、ユーザー指示、変更面をレビュー基準として固定する
2. **反証する** — 差分内で正しいと仮定しない。判定に必要な呼び出し元、定義元、契約、既存テスト、類似実装を開き、要求意図と変更全体の対応を崩しにいく
3. **修正して再検証する** — 書き込み可能な通常開発では、今回の範囲で直す明確な指摘を修正し、関連検証を再実行する。読み取り専用や外部PRで直せない場合も順序は変えない
4. **記録して割り当てる** — 直した指摘も記録に残す。根拠、現実的な成立条件、重要な影響、最小の修正方針を示せるものだけを載せ、残るリスクから独立レビュアを0〜2名選ぶ

## 独立レビュアを 0〜2 名選ぶ

判断材料は**修正後の候補に残るリスク**。変更行数・ラベル・ファイル種別では決めない。

**0 名（メイン担当のみ）** — 次をすべて満たすときだけ。

1. 局所的で容易に戻せる
2. 利用者向け挙動、公開契約、永続データ、権限、信頼境界、外部副作用、挙動資産の意味を重要な形で変えない
3. 新規経路、非自明な状態遷移、重要な既定値の変更を導入しない
4. 変更を直接確認する検証があり、メインレビュー後に重要な不確実性が残らない

行数が少ない・docs-only・test-only・config-only という**形式だけを理由に 0 名にしない**。0 名なら `references/dispatch.md` も role file も読まない。

**1 名（既定）** — 0 名の条件を満たさず、重要な残存リスクが一つの主要テーマに集約できる。通常の非自明な変更はここ。

**2 名（例外）** — 異なる二つの観点に属する重要な残存リスクがそれぞれ具体化し、片方のレビューが他方を代替できないときだけ。観点ごとに選択理由を 1 行残す。「大規模」「重要」だけを理由にせず、同じ汎用レビューを二重に実行しない。

**1 回のレビューにつき最大 2 名。** レビュー後に具体的で未検証の第三の重要な残存リスクが判明したら、同じ回へ三人目を足さず、次の限定再レビューで該当する観点の 1 名を起動する。未検証の重要な残存リスクを残して `PASS` と判定しない。

| 観点 | 選ぶ残存リスク |
| --- | --- |
| architect | 戻しにくい選択、公開契約、schema、永続化、依存方向、責務境界、複製される構造、課題に不釣り合いな複雑性 |
| product | 利用者、運用者、ビジネス成果、課題と解決策の適合、利用経路全体の成立、必須範囲の欠落、価値を薄める過剰範囲 |
| reliability | 実挙動、回帰、性能・可用性の低下、状態、時間、並行、失敗と復旧、展開と運用。非自明な実行時挙動の変更で他の観点が支配的でない場合の既定候補 |
| security | 攻撃面、信頼境界、権限、tenant、秘密情報、外部入力からの実行、危険な副作用 |

観点を選ぶためにレビュア用ファイルを先読みしない。上の 1 行で選び、選んだファイルだけをサブエージェントへ渡す。

**セキュリティの必須割り当て** — メイン担当の修正後でも、変更が信頼境界または攻撃面を実質的に変えるなら `security` を必ず含める。差分に security という語があるかではなく**変更の意味**で判定する。対象は、認証・認可、tenant / privilege 境界、secret・機密データの流れと出力先、外部入力から query / command / template / tool を実行する経路、CI/CD・本番権限、削除・課金・送信のような高影響の副作用である。

## 走らせて判定する

- 1 名以上を選んだら `references/dispatch.md` に従って起動する
- 統合、`severity` / `blocking` / `status` の確定、レポートは `references/verdict.md` に従う
- 結果はリポジトリの基点にある `.km-review/<scope-slug>/`（引数なしは `.km-review/uncommitted/`。直下へ平坦化しない）へ残す。**セッションをまたいで発見できる固定パス**であることが再確認の要件。書き込み前に、git 追跡済みならユーザーへ確認して止まり、未無視なら `.git/info/exclude` へ `/.km-review/` を追記する（コミット対象の `.gitignore` を汚さない）。これらを `git add` しない
- 最終候補が外部から観測される面（挙動・公開契約・設定・コマンド・運用手順）または文書自体を変えるなら、最終的な `PASS` の前にメイン担当が `references/doc-review.md` を実施する。`BLOCKED` なら保留してレポートに明記する
- `BLOCKED` 後の再確認は `references/recheck.md`

## 収束

`PASS` の条件は**完了を妨げる未解決の問題がないこと**。該当する問題は「未解決のままでは現在の作業を完了できない指摘」で、CRITICAL / HIGH は完了を妨げる問題とする（`references/verdict.md`）。

MEDIUM / LOW や完了を妨げない指摘が残っていても `PASS` にできる。**完了を妨げない指摘をゼロにするためにレビューを再実行しない。** 完了を妨げる未解決の問題がある間だけ、修正と限定再レビューを繰り返す。
