# Review

実装した変更を読み取り専用でレビューし、指摘と品質判定を返す。メイン担当が先に反証・検証し、残存リスクに応じて独立レビュアを0〜2名使う。

レビュー対象のソース・設定・文書は編集しない。対象を書き換えるformatter・snapshot更新、commit・push・PR更新・issue更新も行わない。結果用の一時ファイルと、対象から隔離した検証用コピーは変更してよい。
修正も依頼されている場合、このレビューは指摘と判定を返して終了し、呼び出し元が権限の範囲内で次の実装工程として修正する。

判定は `PASS` / `BLOCKED` / `NOOP`。

## 対象

既定は未コミット差分。対象が指定された場合はその指示を解釈し、対象がなければ `NOOP` とする。
指定された対象を解決できない場合は `NOOP` にしない。明示されたPR・commit・range・subtreeの取得・解決失敗はエラーとして報告する。

- `--repo <subtree>` — 差分ではなく現状コード全体を対象にする
- `--recheck` — `references/recheck.md` に従い、直前のblockerの解消確認に限定する

## メインレビュー

メイン担当は、差分を正しいと仮定せず反証を試みる。
ユーザー指示、issue、完了条件をレビュー基準にし、要件を再発明しない。
差分だけでなく、判定に必要な周辺コード・契約・テストも確認する。

- **目的** — ビジネス上の成果を満たし、必須範囲の欠落や価値に寄与しない過剰範囲がないか
- **設計** — システムの拡張方向・設計が妥当で、不要な複雑性や長期的なアーキテクチャ負債を持ち込んでいないか
- **実挙動** — 正常系、性能、互換性、状態、時間・並行、失敗・部分成功・復旧、既存経路への回帰を見落としていないか
- **安全性** — 信頼境界、権限、テナント分離、秘密情報、未信頼入力、削除・送信・課金・本番反映などの危険な副作用を保全しているか

対象を編集しない範囲で、実行できるテスト、静的検査、最小再現は実際に動かす。机上検証よりも動く結果を優先する。対象を書き換える検証は一時領域のコピーなどで隔離し、生成された変更を対象へ取り込まない。

外部から観測される挙動・公開契約・設定・コマンド・運用手順または文書自体を変えた場合は、`references/doc-review.md` に従って関連文書の不整合を検出する。

## 独立レビュア

人数はメインレビュー後の残存リスクで決める。通常は0〜1名、2名は例外とする。

- **0名** — 変更した主要な挙動を直接検証でき、メインレビュー後に重要な不確実性が解消した
- **1名** — 判定に影響する重要な残存リスクが、一つの観点で確認できる
- **2名** — 二つの観点に具体的で重大な残存リスクがあり、片方では他方を代替できない場合だけ

行数、ファイル種別、大規模・重要などのラベルだけで人数を増やさない。2名を選ぶ場合は観点ごとに理由を1行残す。

以下の要約から最も適した観点を選び、選んだrole fileだけを読む。

- `architect` — 戻しにくい設計、責務境界、依存方向、公開契約、複雑性、保守性
- `product` — 要求意図、利用者・運用者の成果、end-to-endの成立、範囲
- `reliability` — 実挙動、回帰、状態、失敗と復旧、互換性、性能
- `security` — 攻撃面、信頼境界、権限、秘密情報、未信頼入力、危険な副作用

信頼境界または攻撃面を実質的に変える場合は `security` を含める。

1名以上を選んだら `references/dispatch.md` に従う。同じレビューで3人目を追加しない。新たな重大リスクが生じた場合は未検証のまま `PASS` にせず、`BLOCKED` として報告する。

## 統合と判定

指摘事項は `CRITICAL` / `HIGH` / `MEDIUM` / `LOW` の重大度を報告する。分類前に `references/finding-contract.md` を読み、統合、判定、報告は `references/verdict.md` に従う。
このレビュー内では修正や再レビューを繰り返さない。

`references/verdict.md`に従って`integration.md`を残し、同じ内容をユーザーへ報告する。
