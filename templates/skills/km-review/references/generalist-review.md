# generalist レビュー

main context で対象全体を読む。重点は「**いま破綻するか**」。長期の波及は architect の主担当だが、architect が起動しない実行では誰も見ないので、見えた懸念は重大度を付けてここで出す（重複の集約は統合が吸収する）。

読む深さは宣言した深さに合わせる。新規ファイル中心なら類似実装を 1〜3 本読み、設計判断が repo と揃うか確かめる。Conventional 接頭辞も手がかりになる（`refactor:` は振る舞い不変の検証、`fix:` は再発防止テスト、`perf:` は性能特性）。

## 関数 → モジュール → システム境界

3 つの尺度を順に当てる。各尺度の定番の欠陥クラスは既に持っている前提で、労力は次の 2 つへ配分する。

- **能動的に壊す** — エッジケースを受動的に列挙して止めない。変更が暗黙に置く前提・不変条件（入力の形・呼び出し順・状態・並行度）を 1 つ特定し、**それを崩す入力・経路を構築して破綻を試す**
- **境界をまたぐ仮定を疑う** — 非同期・分散・複数サービス間の整合性についての誤った仮定は特に見落としやすい

## diff の外を開く（全深度で無条件）

diff 内で正しいと仮定せず、権威ある定義元・sibling・呼び出し元を開いて照合する。この 2 つは深さ・変更構成・レビュアの起動有無によらず必ず当てる。`test-or-config-or-chore-only` で設計・実装の読みを絞る場合も、この 2 つは残す — CI 権限・デプロイ設定の変更こそ継承漏れが刺さる。

- **不変条件の継承** — 新設・分岐した経路（新しい関数・エンドポイント・設定分岐・手順）が、既存の同種経路が通す gate・検証・権限・エラー処理を継承しているかを**経路列挙で**確認する。継承漏れ（新経路が既存の安全確認を素通り）は最頻の欠陥クラス。新エンドポイントが既存の認可 middleware を継承しない、新しい CI ジョブが既存の権限制限を継承しない、といった形で出る
- **値・契約の drift** — diff が変える識別子・値・契約（path・設定キー・定数・enum・スキーマ列・エラーコード・公開契約）を、権威ある定義元および複製 / 連動箇所（config・スキーマ・呼び出し元・sibling 実装・doc・テスト）と照合し、片側だけ更新して stale になる drift を拾う

## 規約・可読性

`AGENTS.md` / `CLAUDE.md` / repo ルールの実質的制約（重点はコード規約。設計方針・アーキ判断との不整合が見えたらそれも出す）、変更ファイル内の既存コメント・TODO、意図が伝わる命名、不要な複雑性。

出さないものは `reviewers/contract.md` の偽陽性フィルタで決める。本レビュー固有の追加は「シニアレビューとして些末なもの」。重大度と確信度も同ファイルに従う。
