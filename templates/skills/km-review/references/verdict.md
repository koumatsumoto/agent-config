# 統合と判定

メイン担当の強み（ツール実行、長い文脈、自己反証）を「**誤った`PASS`を出さない**」ことに使う。レビュアが付けたラベルを無条件に採用しない。

1. **指摘を統合する** — メイン担当の記録とレビュア報告から、同じ原因と影響を指す指摘を統合する。最も具体的な根拠を持つ指摘を残し、併合元だけが持つシナリオ、波及、再現条件を注記する
2. **根拠を検証する** — 完了阻害要因の候補が対象から具体的に裏づくかを確かめる。呼び出し元と呼び出し先の追跡、安全な既存テストの実行、最小再現で確定または棄却する。裏づかないものは`rejected`、確定に届かないが捨てるべきでないものは確認推奨へ移す
3. **影響度、進行可否、状態を確定する** — 下の定義でメイン担当が最終決定する
4. **収束を判定する** — 未解決の完了阻害要因がなければ`PASS`

## severity（影響度）

- `CRITICAL` — 現実的な経路で、即時の重大事故・壊滅的損失・即時悪用に直結する
- `HIGH` — 主な成果の不達、明確な重大回帰、脆弱性、データや運用の事故、長期保守を直撃する設計欠陥
- `MEDIUM` — 意味はあるが限定的な性能・可用性の低下、品質低下、運用リスク、設計不整合、技術負債
- `LOW` — 具体的な改善価値はあるが、主な成果を重大には損なわない

## blocking（進行可否）

「この指摘を未解決のまま、現在のタスクを`PASS`にできるか」を、影響度とは**別軸**で判定する。

- CRITICAL / HIGHは完了阻害要因、MEDIUM / LOWは原則として完了を妨げない指摘とする
- 影響度によらず、**明示された完了条件または主な成果を満たせない**なら完了阻害要因にできる。その場合は該当する完了条件や成果を名指しし、なぜ完了できないかを書く。名指しできないMEDIUM / LOWは完了を妨げない指摘とする。「重要そう」という理由だけで完了阻害要因にしない
- **CRITICAL / HIGHをメイン担当の判断だけで、完了を妨げない指摘へ下げない。** 直さずに進める場合は`BLOCKED`のままユーザーへ論点と選択肢を出し、受け入れられたものだけ`accepted-risk`にする。判定を通すために影響度を下げて完了阻害要因を消すことも禁止する
- `possible`だけでは完了阻害要因にしない。メイン担当が検証して`confirmed` / `likely`へ上げるか、確認推奨へ移す。ただし壊滅的リスクを排除するのに必須の証拠を取得できない場合は、推測の指摘を作らず、「必要な検証を完了できない」ことを理由にレビューを`BLOCKED`にできる
- ユーザーが理由と条件を明示して受け入れた指摘は`accepted-risk`とし、未解決の完了阻害要因から外す。影響度は変えない

## status

| 状態 | 意味 | 影響度別の件数 | 未解決の完了阻害要因数 |
| --- | --- | --- | --- |
| `resolved` | メイン担当または後続の修正で解消した | 含める | 含めない |
| `unresolved` | 根拠が確定し、未修正 | 含める | `blocking: true` のみ含める |
| `accepted-risk` | 理由と条件を明示して残す | 含める | 含めない |
| `rejected` | 重複・偽陽性・根拠不足で棄却 | 含めない | 含めない |

**メイン担当が独立レビュー前に修正した指摘も`resolved`として影響度別の件数に残す。** ユーザーは「このレビューでどれだけ問題が見つかったか」と「現在の完了阻害要因は何か」を別々に把握できる必要がある。

完了を妨げない指摘は、今回の範囲で修正が明確かつ低リスクなら、同じレビュー内で直してよいが義務ではない。**完了を妨げない指摘を直したことを理由に独立レビューを再実行しない。** 修正が新しい重要な変更面に触れたときだけ通常の割り当てへ戻す。

## 判定

- `PASS` — 必要なレビューが完了し、未解決の完了阻害要因がない（MEDIUM / LOWの残存は許容する）
- `BLOCKED` — 未解決の完了阻害要因がある、必要なレビュアが失敗・中断した、または重要な残存リスクの必須確認を完了できない
- `NOOP` — レビュー対象が存在しない。対象の解決に失敗した場合は `NOOP`ではなくエラーとして報告する

段階が結果を返さなかった場合は、実行失敗として理由を記録し、`BLOCKED`と判定する。完了マーカーのない報告ファイルは中断された部分報告として、完了済みの所見を破棄せず回収する。

## レポート

`<report dir>/integration.md` に書き出し、同じ内容をユーザーへ報告する（recheck とセッション境界の正本）。

- **対象 / レビュー基準 / 変更概要**（挙動資産ならその旨）
- **構成** — メイン担当だけか、選んだ観点と割り当て理由。0名ならその理由、2名なら観点ごとに1行
- **影響度別の統合済み総件数と状態内訳** / **未解決の完了阻害要因数** — 別々に表示する
- **指摘本文** — 影響度 / 完了を妨げるか / 状態 / `file:line` / 何が問題か / どう直すか / 対象のどこが根拠か
- **未解決の完了阻害要因を解消する最短方針**
- **確認推奨** — 確定できなかった懸念を「何が分かれば覆るか」1 行で。重大度なし・非ブロッキング・件数に非算入
- **受け入れ済みリスク** — severity / 残す理由 / 後続対応の条件
- **判定**

該当の無い項目は省いてよい。`NOOP` は 1 行でよい。秘密情報・token・PII は値を引用せず `file:line` と種別だけ書く。

```text
Severity: CRITICAL 0 / HIGH 2 (resolved 1, unresolved 1) / MEDIUM 2 (non-blocking) / LOW 0
Unresolved blockers: 1
Reviewers: メイン担当 + reliability
Verdict: BLOCKED
```
