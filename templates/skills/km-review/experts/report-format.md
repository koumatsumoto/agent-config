# 第三者レビュー 共通出力フォーマット

km-review Phase 3 の 3 レビュア (architect / security / adversary) が共通で従う出力規約。orchestrator は各出力を Phase 4 で統合する。

役割定義 / 担当観点 / 主観点は `architect.md` / `security.md` / `adversary.md` を参照。本ファイルは **出力構造・重大度判定・確信度・偽陽性フィルタ** を一本化する。

出力は **2 層** に分かれる。**機械可読契約**は文字列を厳守し (orchestrator が集計・判定・dedup に使う)、**散文**は項目が伝われば長さ・構成をレビュア判断に委ねる。

## 機械可読契約 (文字列厳守)

- **レビュア見出し**: `architect` → `### システムアーキテクト` / `security` → `### セキュリティ専門家` / `adversary` → `### 敵対レビュア`
- **件数行** (見出し直下に必ず 1 行): `CRITICAL: <n> / HIGH: <n> / MEDIUM: <n> / LOW: <n>`
- **各所見の見出し**: `## <重大度>: <タイトル> [<確信度>]`
- **場所**: `**場所**: <file>:<line>` (dedup のキーになる)

これらは orchestrator が regexp / グルーピングで読むため、表記を揺らさない。

## 散文 (内容が伝われば形式は委ねる)

各所見に最低限「何が問題か」「どう直すか」「diff / 担当 reference のどの観点に該当するか」が伝わるように書く。文数・固定フィールドは課さない。役割固有の補足 (下記) は、判断に効くときに添える。報告はファイルに永続化されうるため、**秘密情報を指摘する際は値そのものを引用せず `file:line` と種別のみ** 記載する (トークン・鍵・PII の平文複製を作らない)。

```
### <レビュア名>
CRITICAL: 0 / HIGH: 1 / MEDIUM: 2 / LOW: 0

## HIGH: [問題タイトル] [confirmed]
**場所**: src/api/users.ts:42
**問題**: 何が問題か
**修正**: どう直すか
**根拠**: diff / 担当 reference のどの観点か
（役割固有の補足があれば続けて書く）
```

指摘ゼロのとき:

```
### <レビュア名>
CRITICAL: 0 / HIGH: 0 / MEDIUM: 0 / LOW: 0
（指摘なし）
```

## 重大度の判定 (「今すぐ直す重さ」)

重大度は「今すぐ直す重さ」を表す。

- `CRITICAL`: 即時悪用可能 / 重大インシデント直結 / 即時データ損失
- `HIGH`: 明確なバグ、仕様回帰、危険な未検証入力、長期保守を直撃する設計欠陥、明確な脆弱性
- `MEDIUM`: 設計不整合、品質特性の低下、テスト不足、技術負債の兆候
- `LOW`: 小さな改善

`CRITICAL` または `HIGH` があれば Phase 4 統合で全体判定が `BLOCKED` となる。

## 確信度ラベル

- `[confirmed]`: diff から直接裏づけ可能、誤検出の可能性ほぼゼロ
- `[likely]`: diff + repo context から推測、コンテキスト次第で偽陽性の可能性あり
- `[possible]`: 一般的な観点として該当しうるが、本変更で実害が出るかは別途確認要

`possible` は重大度を 1 段下げることを検討してよい。ただし **影響が壊滅的 (悪用時 CRITICAL 相当) なら確信度に関わらず重大度を維持** する。

## 偽陽性フィルタリング (出さないもの)

- 好み・様式の好き嫌い、linter / formatter / type checker が機械的に拾うもの
- 今回の diff で導入されていない既存問題 (security は新規 attack surface に既存問題が露呈する場合のみ報告)
- 合意済みの設計判断 (intent context があれば確認)
- 未変更行だけに対する指摘
- diff から裏づけられない一般論だけの推測 (security では「攻撃シナリオが現実的でない」を含む)

**レーンを理由に抑制しない**: 自分の担当観点か迷っても、見えた実質的な懸念は出す。他レビュアと重なる懸念の集約は Phase 4 統合の中央 dedup が一括で行うので、レビュア側で重複回避を予測しなくてよい (各レビュアは独立 = 他レビュアの所見は渡されない。これは視点の多様性確保のためで、報告抑制の根拠ではない)。

## 役割固有の補足 (HIGH 以上で添えると判断に効く)

- architect: `**不可逆性 / 波及**` (例: 公開契約の破壊変更で 3 consumer に互換性連鎖。後戻りに major bump)
- security: `**攻撃シナリオ**` + CWE/OWASP 引用 (引用は `**根拠**` 内)
- adversary: `**再現条件**` (作れる範囲で具体的な入力・経路)

## 判定保留 (context 不足)

該当観点があるが diff だけでは判定しきれない場合、独立セクションに記録する:

```
## 判定保留 (context 不足)
- **観点**: 6-セキュリティ / 真正性
- **何が必要か**: middleware 層での認証適用状況
- **暫定見解**: 認証 middleware が他で適用済なら問題なし、なければ HIGH 相当
```

## 検証済み所見 (reviewed-clear)

「何を検証して健全だったか」を、判定に効く不変条件・surface の **保全確認** に限って記録する。欠陥が少ない対象で「何か見つけねば」というノイズ生成圧を、検証価値の出力に転換する。所見 (欠陥) とは別の独立セクションで返す。

- 対象は **判断に効く不変条件・surface の保全確認のみ** (例: 認可 gate が全新設経路に適用済み / 秘密チェックの 2 gate が維持 / 公開 egress が棚卸し済み)。安心のための一般的な言明は書かない
- **各項目 1 行 + 検証手続き (grep / `file:line` / 列挙方法) の明示を必須** とする。手続きを書けない「clear」は書かない (無検証の安心記述は反証機構を弱め、false negative を増やすチャネルになる)
- **重大度なし・総検出件数に非算入**

```
## 検証済み所見
- 認可 gate は全新設経路に適用済み — 経路 (`handler.ts:20,48,73`) を列挙し各々で `requireAuth()` を確認
```

Phase 4 での消費は「未カバー surface の優先順位付けのみ」に限定される (制約は SKILL.md Phase 4 手順 5: 独立 1 パスに入れない / 除外には Phase 4 のスポット検証を要求)。
