# レビュアの返し方

## 重大度（「今すぐ直す重さ」）

- `CRITICAL` — 即時悪用可能 / 重大インシデント直結 / 即時データ損失
- `HIGH` — 明確なバグ、仕様回帰、危険な未検証入力、長期保守を直撃する設計欠陥、明確な脆弱性
- `MEDIUM` — 設計不整合、品質特性の低下、テスト不足、技術負債の兆候
- `LOW` — 小さな改善

`CRITICAL` または `HIGH` があれば統合で全体判定が `BLOCKED` になる。

## 確信度

`confirmed`（対象から直接裏づけられ、誤検出の可能性はほぼゼロ）/ `likely`（対象 + repo context からの推測。コンテキスト次第で偽陽性）/ `possible`（一般的な観点として該当しうるが、実害が出るかは別途確認要）。

`possible` は重大度を 1 段下げることを検討してよい。ただし**影響が壊滅的（悪用時 CRITICAL 相当）なら確信度に関わらず重大度を維持する。**

## 所見の形

冒頭に重大度別の件数を 1 行。各所見に **重大度 / タイトル / 確信度 / `file:line`（統合の dedup キーになる）/ 何が問題か / どう直すか / 対象のどこが根拠か**。指摘ゼロなら件数ゼロ + 指摘なしと明記する。散文の長さ・構成は内容が伝わる限り委ねる。

HIGH 以上には判断に効く補足を添える — architect は不可逆性・波及（「N consumer に互換性連鎖」）、security は攻撃シナリオ + CWE / OWASP、adversary は再現条件。

報告はファイルに永続化されるため、**秘密情報を指摘するときは値そのものを引用せず `file:line` と種別だけ**書く（トークン・鍵・PII の平文複製を作らない）。

## 出さないもの

- 好み・様式の好き嫌い、linter / formatter / type checker が機械的に拾うもの
- 今回の変更が導入していない既存問題（security は新規 attack surface に既存問題が露呈する場合のみ報告する）
- 合意済みの設計判断（intent があれば確認する）
- 変更されていない箇所だけへの指摘
- 対象から裏づけられない一般論だけの推測（security では「攻撃シナリオが現実的でない」を含む）

上の 2 つ（既存問題 / 未変更箇所）は差分レビューにだけ効く。`--repo` で現状コード全体を見る実行には「今回の変更」が無いので適用せず、対象サブツリーの現状の欠陥をそのまま出す。

## レーンを理由に抑制しない

役割は**注力先の宣言であって報告範囲の制限ではない。** 担当外に見えても、見えた実質的な懸念は出す。他レビュアと重なってよい（集約は統合の責務で、レビュア側で重複回避を予測しなくてよい）。担当外を落とすと、そのレビュアが起動しない実行で誰も見ない観点が生まれる。レビューの最大コストは false negative なので、レーン境界より検出を優先する。出す / 出さないは上の偽陽性フィルタだけで決める。

## 判定保留

該当観点はあるが diff だけでは決めきれないものは、独立セクションに **観点 / 何が必要か / 暫定見解**を書く。保留にする前に「あと何を読めば確定するか」を一度は試す。

## 検証済み所見

「何を検証して健全だったか」を、**判断に効く不変条件・surface の保全確認に限って**記録する（例: 認可 gate が全新設経路に適用済み / 秘密チェックが全 egress で維持されている / 公開 egress が棚卸し済み）。欠陥が少ない対象で「何か見つけねば」というノイズ生成圧を、検証価値の出力へ転換する仕組み。

- 各項目 1 行 + **検証手続き**（grep / `file:line` / 列挙方法）の明示を必須とする。手続きを書けない「clear」は書かない — 無検証の安心記述は反証機構を弱め false negative を増やす
- 安心のための一般的な言明は書かない
- 重大度なし・件数に非算入。所見とは別の独立セクションで返す
