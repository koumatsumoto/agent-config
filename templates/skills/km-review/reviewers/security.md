# security

**反証命題** — この変更は、現実的な攻撃者・濫用者が利用できる経路を新設せず、信頼境界、権限、テナント・ユーザー間の分離、秘密・機密データ、危険な副作用を保全している。

返し方、重要性の判定、担当範囲の規律は、同時に渡される`reviewers/contract.md`に従う。脆弱性クラスの知識は既にある前提で、探索予算は**この対象に固有の信頼境界とデータフロー**の特定へ配分する。

## 探索予算を使うテーマ

- **主体・資産・信頼境界** — 誰がどの入口から何へ到達できるか。信頼済みと未信頼の境界が変更でどう動くか
- **権限** — 認証・認可、テナント、所有者、役割、特権、委譲が全経路で維持され、別経路から迂回できないか
- **機密データ** — 秘密情報、トークン、個人識別情報、内部設定が、入力・保存・ログ・エラー・外部送信・レポートのどこで露出または過剰共有されるか
- **未信頼入力から実行まで** — 外部入力がクエリ、コマンド、テンプレート、パス、コード、LLMのツール・プロンプト、外部送信へ到達する境界
- **影響の大きい副作用** — 削除、送信、課金、本番反映、CI/CD、認証情報の利用を、越権・濫用で実行できないか
- **濫用と監査** — 正当な利用者の濫用がセキュリティ上の影響を持つとき、検出・追跡・否認防止が足りるか

## 境界

セキュリティ上の影響がない通常障害、性能劣化、再試行、復旧はreliabilityが主担当とする。現実的な攻撃者、入口、破られる境界、得られる結果を構成できない一般的な堅牢化の提案は指摘にしない。

## 指摘の根拠

**攻撃・濫用主体、入口、前提、破られる境界、達成される結果**を一つのシナリオとして示す。秘密値そのものはレポートへ複製しない。
