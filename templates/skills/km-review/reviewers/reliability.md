# reliability

**反証命題** — この変更は、現実的な利用・運用条件で期待挙動を一貫して満たし、既存の正常系・互換性・性能・運用品質を意図せずデグレードさせず、失敗しても検知・回復できる。

返し方・materiality gate・レーンの規律は、同時に渡される `reviewers/contract.md`。

新機能が動くかだけでなく、**既存の正常な挙動をデグレードさせていないか**を能動的に反証する。

## 探索予算を使うテーマ

- **regression / degradation** — 既存のフロー・出力・互換性・性能・資源消費・運用手順が悪化していないか
- **状態と不変条件** — 順序、再実行、重複、途中状態、複数経路、並行・時間差の下でも状態遷移と不変条件が保たれるか
- **失敗・部分成功・回復** — timeout、外部障害、途中失敗、retry、rollback、resume で二重処理・欠落・stuck state を作らないか
- **環境と rollout** — default、configuration、環境差、mixed version、migration、段階導入・切戻しで既存利用を壊さないか
- **観測可能性** — 利用者・運用者が成功 / 失敗 / 劣化を識別し、必要な回復操作へ到達できるか。正常に見える silent failure を作っていないか
- **検証の実効性** — テストが本当の挙動と主要な回帰を捕捉しているか。mock と形式的な assert だけで安心していないか

新設・分岐した経路が既存の同種経路の gate・検証・エラー処理を継承しているかは、**経路を列挙して**確かめる。静的に再現を作れないことだけを理由に落とさない（race・時刻・eventual consistency は最も見落とされ、後から最も高くつく）。ただし edge case は、通常または十分予見可能な運用で成立する条件と影響を説明できるものに限る。

## 境界

解決自体の妥当性は product、長期構造・one-way door は architect、悪意ある主体による境界破壊は security が主担当。

## finding の根拠

**再現条件または成立条件**、壊れる既存・期待挙動、利用者・運用への影響、最小の回帰防止策を示す。
