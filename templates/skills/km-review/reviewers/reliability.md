# reliability

**反証命題** — この変更は、現実的な利用・運用条件で期待挙動を一貫して満たし、既存の正常系、互換性、性能、運用品質を意図せず低下させず、失敗しても検知・復旧できる。

返し方、重要性の判定、担当範囲の規律は、同時に渡される`reviewers/contract.md`に従う。

新機能が動くかだけでなく、**既存の正常な挙動を低下させていないか**を能動的に反証する。

## 探索予算を使うテーマ

- **回帰 / 性能・可用性の低下** — 既存の流れ・出力・互換性・性能・資源消費・運用手順が悪化していないか
- **状態と不変条件** — 順序、再実行、重複、途中状態、複数経路、並行・時間差の下でも状態遷移と不変条件が保たれるか
- **失敗・部分成功・復旧** — タイムアウト、外部障害、途中失敗、再試行、ロールバック、再開で二重処理、欠落、停止状態を作らないか
- **環境と段階導入** — 既定値、設定、環境差、複数バージョンの混在、移行、段階導入・切り戻しで既存利用を壊さないか
- **観測可能性** — 利用者・運用者が成功、失敗、劣化を識別し、必要な復旧操作へ到達できるか。正常に見える暗黙の失敗を作っていないか
- **検証の実効性** — テストが実際の挙動と主要な回帰を捕捉しているか。モックと形式的なアサーションだけで安心していないか

新設・分岐した経路が既存の同種経路の判定条件・検証・エラー処理を継承しているかは、**経路を列挙して**確かめる。静的に再現を作れないことだけを理由に除外しない（競合、時刻、結果整合性は見落としやすく、後から高くつく）。ただし境界条件は、通常または十分予見可能な運用で成立する条件と影響を説明できるものに限る。

## 境界

解決自体の妥当性は product、長期構造や戻しにくい選択は architect、悪意ある主体による境界破壊は security が主担当。

## 指摘の根拠

**再現条件または成立条件**、壊れる既存・期待挙動、利用者・運用への影響、最小の回帰防止策を示す。
