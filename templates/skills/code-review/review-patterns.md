# Review Patterns

コードレビュー時の品質特性別アンチパターン集。SKILL.md の Phase 4（品質特性）で参照する。

## 性能効率性

### 1. アルゴリズム計算量

- ネストループによる O(n²) 以上の処理（配列の中で配列を線形探索 → Map/Set に変換）
- ソート済みデータに対する線形探索（二分探索が使える場面）
- 全件取得してからフィルタリング（DB/API 側でフィルタすべき）

### 2. I/O パターン

- N+1 クエリ: ループ内で個別にクエリを発行（バッチ取得・JOIN に変換）
- 非同期コンテキストでの同期ブロッキング（`requests.get` in asyncio、sync DB call in async handler）
- コネクションプーリングなしの繰り返し接続

### 3. リソース管理

- 上限なしのインメモリキャッシュ（LRU/TTL なしで成長し続ける）
- ループ内での大きなオブジェクト生成（ループ外で再利用可能）
- ページネーションなしの大量データ取得（メモリ溢れのリスク）
- ストリーム処理可能なデータの全件メモリ展開

### 4. フロントエンド固有

- 不要な再レンダリング（deps 配列の誤り、オブジェクトリテラルの毎回生成）
- バンドルサイズの大幅増加（巨大ライブラリの追加に lazy loading なし）
- 画像・メディアの最適化なし読み込み

## 互換性

### 5. 破壊的変更

- 必須パラメータの追加（既存クライアントが壊れる → オプショナルにするかデフォルト値を設定）
- レスポンス構造の変更（フィールド削除、型変更 → バージョニングか段階的移行）
- エラーコード/ステータスコードの変更（クライアントの分岐が壊れる）

### 6. インターフェース設計

- 内部実装の詳細が API に漏れている（DB カラム名がそのまま JSON フィールドに）
- 一貫性のない命名（`getUserById` と `fetch_user_list` の混在）
- 過大な責務を持つエンドポイント（1つの API で複数の無関係な処理）

### 7. エラー契約

- エラーレスポンスの形式が既存パターンと不一致
- HTTP ステータスコードの誤用（200 で返すエラー、バリデーション失敗に 500）
- エラーメッセージに内部情報の漏えい（スタックトレース、DB スキーマ）

## 保守性（テスト品質）

### 8. テストの有効性

- diff の変更を実際に検証していないテスト（形式的にテストが存在するだけ）
- 実装の詳細に依存したテスト（内部メソッド呼び出し回数の検証等 → 振る舞いを検証すべき）
- `toBeTruthy` / `assert result` のような曖昧なアサーション（具体的な値を検証すべき）
- スナップショットテストの過剰使用（意図しない変更検出には有効だが、仕様の明示にならない）

### 9. テストの信頼性

- 共有ミュータブル状態への依存（他テストの実行結果で成否が変わる）
- 実行順序依存（テスト A が先に実行されないと B が失敗）
- 時刻依存のテスト（固定時刻を注入すべき）
- 外部サービスへの実通信（モック/スタブを使うべき）

### 10. テストの保守性

- テストヘルパー/ファクトリの不使用（各テストで長大なセットアップを繰り返す）
- テスト名が「何を検証しているか」を表現していない
- 1つのテストで複数の無関係な振る舞いを検証している

## 信頼性（可観測性）

### 11. ログとトレース

- 重要操作（特に失敗パス）のログ出力が欠けている
- ログに文脈情報が不足（リクエストID、ユーザーID、操作対象）
- 構造化されていないログ（文字列結合のみ → JSON/構造化ログを推奨）
- 分散トレースのコンテキスト伝播が途切れている

### 12. 監視とヘルスチェック

- 新機能にメトリクス/アラートが追加されていない
- ヘルスチェックエンドポイントが新しい依存関係を反映していない
- SLI/SLO に影響する変更にダッシュボード更新がない
