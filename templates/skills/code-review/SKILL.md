# Code Review

未コミット変更を対象に、ISO/IEC 25010 (SQuaRE) の品質モデルに基づく体系的なレビューを行う。

## レビューの重心

開発者は実装時に「仕様どおりに動くか」（機能適合性）を意識して作業する。そのため要件充足の観点は自然と満たされやすい。一方、設計の妥当性や非機能品質特性（セキュリティ・信頼性・性能効率性・保守性）は実装者の視野外になりがちで、レビューで初めて発見される問題が多い。このスキルの最大の価値は Phase 3（設計妥当性）と Phase 4（品質特性）にある。

## Workflow

1. **変更把握・分類**: 変更ファイルを収集し、変更タイプとリスクを判定してレビュー深度を決定する
2. **要件充足性** — 機能適合性: 仕様を満たしているか、正確に動作するか
3. **設計妥当性** — システム・ソフトウェア設計: 関数→モジュール→システムの多層で設計が適切か
4. **品質特性** — 機能適合性以外の品質: セキュリティ・信頼性・性能効率性・保守性・互換性
5. **報告**: 問題を重大度順に報告する。`CRITICAL/HIGH` があればコミットをブロックする

## Phase 1: 変更把握・分類

`git diff --name-only` で変更ファイルを収集し、変更の全体像を把握する。これにより後続フェーズの注力ポイントが決まる。

### 変更タイプの判定

- `feat`: 新機能の追加
- `fix`: バグ修正
- `refactor`: 振る舞いを変えないコード改善
- `test`: テストの追加・修正のみ
- `config/chore`: 設定変更、依存更新、CI/CD 等
- `docs`: ドキュメントのみの変更 → `/doc-review` に委譲

### リスクプロファイルの判定

以下に該当する変更は **高リスク** として扱う:

- 認証・認可ロジック
- 決済・課金処理
- データアクセス層・スキーマ変更
- 暗号化・シークレット管理
- 外部 API との通信
- ファイルシステム・OS コマンド操作

### レビュー深度マトリクス

| 変更タイプ | Phase 2 要件充足 | Phase 3 設計妥当性 | Phase 4 セキュリティ | Phase 4 その他品質特性 |
|---|---|---|---|---|
| feat (高リスク) | Full | Full | Full + checklist | Full |
| feat (標準) | Full | Full | Quick scan | Full |
| fix | Full | 変更関数+呼び出し元 | Quick scan | 正確性重点 |
| refactor | 振る舞い不変を確認 | Full | 信頼境界に触れる場合のみ | 保守性重点 |
| test | Skip | Skip | Skip | テスト品質のみ |
| config/chore | Quick | Skip | シークレットスキャンのみ | Skip |

## Phase 2: 要件充足性（機能適合性）

ユーザーの元の要求を振り返り、変更が仕様を正確に満たしているか確認する。

### 仕様との突合

- 要求された機能・修正がすべて実装されているか
- 要求されていない変更が混入していないか
- エッジケースや境界条件が仕様レベルで考慮されているか
- 元の要求が会話履歴から不明確な場合、その旨を報告し、推測で判断しない

### 正確性

- 仕様どおりの動作をするか
- 既存機能を壊していないか（仕様回帰）
- データの整合性は保たれるか（型変換、丸め、タイムゾーン）
- 条件分岐に漏れがないか（exhaustiveness）

## Phase 3: 設計妥当性

変更が設計として妥当かを、関数→モジュール→システムの順に確認する。

### 関数/メソッドレベル

- 入出力の型は正しいか。`null` / `undefined` / `None` の扱いは適切か
- エッジケース（空配列、0、空文字、境界値）でも正しく動作するか
- エラーパスは適切にハンドリングされているか
- 副作用が明確か（引数の変更、グローバル状態の変更）

見落としやすいパターン:
- サイレント型変換（文字列と数値の暗黙比較、truthy/falsy の誤用）
- catch-all 例外の握り潰し（`except Exception: pass`、空の `catch {}`）
- ミュータブルオブジェクトのデフォルト引数・共有参照
- off-by-one エラー（`<` vs `<=`、0-indexed vs 1-indexed）

### モジュール/ファイルレベル

- 1つのファイル/クラスが1つの責務に集中しているか
- 依存の方向は適切か（具象→抽象、外→内）
- 公開インターフェースは最小限か（不要な export / public がないか）
- 変更が他モジュールに予期しない影響を与えないか

見落としやすいパターン:
- 循環依存の導入
- 内部型の公開 API へのリーク
- God class/module（1ファイルに責務が集中しすぎ）

### システム/アーキテクチャレベル

- データフロー全体で型安全性が保たれているか
- 信頼境界（外部入力、認証、データ永続化）を跨ぐ箇所は安全か
- 変更の波及範囲を把握できているか
- パフォーマンスへの影響（N+1 クエリ、不要なループ、メモリリーク）はないか

見落としやすいパターン:
- 非同期コンテキストでの同期ブロッキング呼び出し
- 無制限に成長するキャッシュ/キュー
- 外部サービス呼び出しへのサーキットブレーカー欠如

## Phase 4: 品質特性

### セキュリティ

信頼境界に触れる変更を優先的に確認する。詳細なチェックリストは security-checklist.md を参照。

- ハードコードされたシークレットがないか
- 認証・認可が適切に実装されているか
- 外部入力が検証なく使用されていないか（SQL, テンプレート, シェル, パス結合）
- 例外の握り潰しによる fail-open がないか
- 機密情報がログ/エラー出力に含まれていないか

### 信頼性

- 例外が適切に伝播しているか（握り潰し、cause チェーンの欠落）
- リソース解放は確実か（ファイル、接続、トランザクション）
- 並行アクセスで整合性が壊れないか（TOCTOU、共有状態）
- 外部サービス障害時の振る舞いは適切か（タイムアウト、リトライ、フォールバック）
- 重要操作が適切にログ出力されているか（特に失敗パス）
- 構造化ログが使われ、トレース可能か

### 性能効率性

- ホットパスに O(n²) 以上のアルゴリズムが導入されていないか
- N+1 クエリや不要な繰り返しリクエストがないか
- 無制限に成長するキャッシュ、キュー、バッファがないか
- ループ内での不要なオブジェクト生成やメモリ確保がないか
- ページネーションなしの大量データ取得がないか

### 保守性

- 変数名・関数名が意図を正確に表現しているか
- ネストが深すぎないか（早期 return で簡潔にできないか）
- 同一ロジックのコピペがないか
- 変更箇所に対応するテストが追加・更新されているか
- テストが実際に diff の変更を検証しているか（形だけのテストではないか）
- テストがエッジケースをカバーしているか
- テストが独立しているか（共有ミュータブル状態、実行順序依存がないか）

### 互換性

- 既存の呼び出し元/クライアントが変更なしで動作するか（後方互換性）
- 破壊的変更がある場合、移行パスが提供されているか
- エラーの型・コードが既存パターンと一貫しているか
- 命名が既存 API サーフェスと統一されているか

## Mandatory Blockers

Phase 4 セキュリティの項目を検出した場合、コミットをブロックする。

## Severity Guide

- `CRITICAL`: 機密漏えい、認可欠如、任意コード実行、fail-open など即時悪用可能
- `HIGH`: 明確なバグ、仕様回帰、悪用可能な入力検証不足
- `MEDIUM`: 保守性低下、テスト不足、設計の不整合、不適切なエラー処理
- `LOW`: 微小改善

## Output Format

### サマリー（必ず冒頭に出力）

```
## レビュー結果

**変更分類**: feat (高リスク) | 変更行数: 450行 | ファイル数: 8
**検出件数**: CRITICAL: 0 / HIGH: 1 / MEDIUM: 2 / LOW: 1
**コミット判定**: ⚠️ BLOCKED（HIGH 以上の問題あり）
```

### 問題報告

問題ごとに以下の形式で報告する。確信度（`confirmed` = 確認済み / `suspected` = 疑い）を付与する。

```
## HIGH: 未検証の外部入力がクエリに使用されている [confirmed]

**場所**: src/api/users.ts:42
**問題**: リクエストパラメータ `sort_by` が検証なしに SQL ORDER BY 句に結合されている。攻撃者が任意の SQL フラグメントを注入できる。
**修正**: 許可されたカラム名のホワイトリストで検証する。
```
