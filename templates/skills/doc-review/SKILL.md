# Document Review

未コミットのドキュメント変更を対象に、整合性と正確性を重視した体系的なレビューを行う。

## レビューの目的

作業者はドキュメントの追加部分に意識を集中し、部分的な修正が全体構造を崩す問題、複数ドキュメント間の矛盾、読者にとっての理解しやすさが視野外になりやすい。このスキルの最大の価値は Phase 2（構造的整合性）と Phase 3（横断整合性）にある。Phase 4（一次情報検証）は時間がかかるが、誤情報の防止に不可欠である。

レビュー時の行動原則: 違和感を覚えたら常に改善の余地を疑い、多角的に分析する。構造の検討と分析は常に深く行う。

## ドキュメント品質の原則

ドキュメントは「詳細を書くこと」ではなく「ゼロベースの読者が全体像を曖昧さなく把握できる構造を設計すること」である。以下の 3 原則がすべてのフェーズの判断基準となる。

1. **構成の明確さ**: ゼロベースで読んだ読者が「何がどこにあるか」を迷わない。情報は体系的に整理し、要点を最小限に絞る。詳細はサブドキュメントに委譲し、情報アーキテクチャを意識的に設計する
2. **冗長の排除**: 同じ情報が複数箇所にあると更新時に矛盾が生じ、情報がノイズになる。Single Source of Truth を徹底する
3. **必要事項の網羅**: シンプルにしすぎて本質的に必要な情報を省いてはいけない。簡潔さと網羅性を両立させる

## Success Criteria

- 変更された文書だけでなく、その周辺文書との整合を確認する
- 事実関係は一次情報まで戻って確認する
- 読者を迷わせる構造上の欠陥と更新漏れを優先して拾う

## Workflow

1. Phase 1: 変更把握・分類
2. Phase 2: ドキュメント内整合性（「構成の明確さ」「必要事項の網羅」を軸に）
3. Phase 3: ドキュメント間整合性（「冗長の排除」を軸に）
4. Phase 4: 一次情報による正確性検証
5. Phase 5: 偽陽性フィルタリング

## Phase 1: 変更把握

`git diff --name-only` で変更ファイルを集める。コードのみ変更なら本スキルは使わない。

|ドキュメントタイプ|Phase 2|Phase 3|Phase 4|
|---|---|---|---|
|README / ガイドライン / ルール|Full|Full|Full|
|要件ドキュメント|Full|Full|Focused|
|仕様書|Focused|Focused|Full|
|アーキテクチャ / 設計書|Full|Full|Focused|
|設定ドキュメント / 手順書|Quick|Focused|Full|

## Phase 2: ドキュメント内整合性

変更差分だけでなく、変更されたドキュメントの全体を読む。部分的な追記・修正によって構造・書式・明瞭性が崩れていないか検証する。「構成の明確さ」と「必要事項の網羅」の原則に照らし、ゼロベースの読者にとっての理解しやすさを最重視する。

確認観点:
- セクション構成の論理的な流れ（順序、粒度の統一）
- 目次・見出しと実際の内容の対応
- ドキュメント内での用語・表記の統一
- 前後のセクションとの整合性（前提の矛盾、説明の重複・欠落）
- フォーマットの一貫性（リスト記号、コードブロック言語指定、強調表記の用法）
- 読者にとっての明瞭性（専門用語の初出説明、前提知識の明示、文の長さ）

見落としやすいパターン:
- 部分修正で生じる「浮いたセクション」（前後の文脈から切断された段落）
- 見出しレベルの不整合（h2 の下に h4 が突然現れる）
- 冒頭の概要文が本体の内容と乖離している（本体を更新して概要を放置）
- 導入なしにいきなり詳細に入る（読者が文脈を掴めない）
- 手順の番号付けと実際のステップ数の不一致
- 重要な警告が目立たない場所に埋もれている

## Phase 3: ドキュメント間整合性

変更内容に関連する他のドキュメントを探索し、矛盾・重複・更新漏れを検出する。内部リンクの健全性もこのフェーズで確認する。「冗長の排除」の原則に基づき、Single Source of Truth が維持されているかを重点的に検証する。

確認観点:
- 同じ情報が複数ドキュメントに重複して記載されていないか
- ドキュメント間で矛盾する記述がないか
- 一方を更新して他方が古いまま放置されていないか
- 内部リンク（ファイルパス・アンカー）の参照先が存在するか

見落としやすいパターン:
- CLAUDE.md / README / docs/ の三重管理による矛盾
- インストール手順やセットアップ手順の複数箇所記載
- 用語定義がドキュメントごとに微妙に異なる
- 相対パスと絶対パスの混在による参照の不整合

## Phase 4: 一次情報による正確性検証

ドキュメントの記述内容を鵜呑みにせず、一次情報まで遡って正確性を検証する。情報の鮮度（陳腐化）もこのフェーズで確認する。多少時間がかかっても一次情報の確認を省略しない。まず repo 内の実装、設定、ヘルプ出力を確認し、それで足りない場合だけ外部一次情報を当たる。

確認観点:
- **システム仕様・API 仕様**: 実装コードを読んで記述と一致するか確認する
- **設定・コマンド**: 実際の設定ファイルやヘルプ出力と照合する
- **外部参照**: リンク先の存在と内容の妥当性を確認する
- **鮮度**: 非推奨・廃止された機能への言及、期限切れ表現がないか確認する

見落としやすいパターン:
- コード例が実際の API シグネチャと不一致（引数の順序、型、デフォルト値の誤り）
- 実行不可能なコード例（import 漏れ、未定義変数、非推奨 API の使用）
- 設定ファイルのパスやキー名が実際のものと異なる
- コマンド例の出力が現バージョンの実際の出力と異なる
- バージョン番号の陳腐化、「近日公開」「将来的に」等の期限切れ表現

## Phase 5: 偽陽性フィルタリング

以下は除外する:

- 今回の変更で導入されていない既存問題
- 単なる文体の好み
- 読者層に合わせた意図的な簡略化
- 自動生成コンテンツだけの差分
- 未変更セクションだけに対する指摘

注意: 上記カテゴリに該当しない「違和感」は除外しない。構造上の問題や改善の余地を示す違和感は、明確なエラーでなくても報告する。

## 判定

- `CRITICAL`: 危険な手順や破壊的な誤情報
- `HIGH`: 明確な事実誤認、一次情報との不一致、構造破綻
- `MEDIUM`: 整合性不足、曖昧さ、更新漏れ、構造上の違和感や読者を迷わせる構成問題
- `LOW`: 微小改善

`CRITICAL` または `HIGH` があればコミットをブロックする。検出された指摘は `LOW` を含め原則すべて対応する。影響が大きい修正のみユーザーに判断を委ねる。

出力形式は `report-format.md` を参照。
