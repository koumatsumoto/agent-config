# Skill Improvement

挙動資産は agent の事前分布であり、**変更が意図した改善を起こすか・既存挙動を退行させないかは diff の静的レビューでは判定できない**。走らせて比べるしかない。本 skill は改善シグナルを実挙動の証拠に変換して採否を決め、使った題材と判定を記憶（scenario bank）に残す。回すたびに検証資産が増え、次の改善が安く鋭くなるループとして運用する。

**コスト原則**: 検証コストは変更の残存リスクに比例させる。軽い変更に重い検証を積まず、重い変更を無検証で通さない。計測器・モデル・ラウンド数はユーザーの明示指定が常に優先。

方法（eval-first・blind A/B・bank）は挙動資産一般に使える。ただし版の渡し方と bank の置き場は skill 一式を前提に書いてあるので、rule や `CLAUDE.md` のような単体ファイルではロード経路と正本の位置を読み替える。

## 何が改善を起動するか

改善アイデア・実走メモ・レビュー指摘に加えて、**実挙動の証拠**も一級の入口として扱う。

- **実走の観察** — 指示が働かなかった箇所・毎回手作りで補った手順・読まれなかった reference・誤読された分岐。最も安く現実に接地したシグナルで、そのまま題材の種になる
- **剪定シグナル** — A/B の wash が続く、肥大して標準ケースの遵守率が下がった疑い。削る改善も同じループで扱う

既に編集済みの変更を検証する依頼なら、base（変更前）を `git show <ref>:<path>` 等で references ごと一時ディレクトリに再現し、candidate（作業ツリー）と比べる。この場合も診断は省けない — 効く層・変更タイプ・wash リスクの特定は検証設計に要る。

## 改善ループ

1. **シグナルを具体化する** — 「どの場面で・現状どうなるか・どうなってほしいか」に落とす。答えが検証設計を変える曖昧さが残るならユーザーに確認する
2. **診断する** — 対象一式と、あれば記憶（bank。置き場と様式は `references/scenario-bank.md`）を読み、**効く層・分岐**（変更しない層が単独で拾える改善は差が出ない = wash リスク）、**正本の所在**（手元が配布コピーなら正本を特定する。実験は複製で行えるが、採用の反映先と bank の置き場は常に正本）、**変更タイプ**（`references/scenario-design.md`。題材の設計がここで変わる）を特定する
3. **方針を合意する** — 現状と期待のギャップを明文化してユーザーと合意する
4. **題材を先に固定する** — **candidate を書く前に**題材・期待品質・名指し観点を確定する（`references/scenario-design.md`）。起草後に題材を作ると、candidate が通りやすい題材を無意識に選ぶ設計バイアスが入る。順序そのものが blind の一部
5. **candidate を起草する** — 現行版一式を一時ディレクトリに複製して編集する（正本・配布コピーを直接編集しない）。**差分の継ぎ足しで終えず、影響範囲を既存記述ごと統合・整理して一つの整合した最終版にする** — 継ぎ足しは重複・矛盾・dangling 参照を溜め、差分レビューでは全体の破綻を見逃す。必要なら節構成も再編する。記述は現在形で現設計の意図だけを書く
6. **証拠を測る** — 下表で計測器を決め、選択と理由を宣言してから実施する
7. **判定する** — 採用 / 低マージン採用 / 不採用。採用時は「この変更が**何を犠牲にしうるか**」を 1 行で明記し、それが統制題材・回帰題材で覆われていることを確認する
8. **記憶して正本へ反映する** — 判定の根拠になった題材・合否線・再走トリガ・観測された落とし穴を対象の bank へ書き戻す（判定履歴は書かない）。採用は正本へ反映し、題材設計や judge 観点の一般知見は本 skill の references へ還元する。検証の記録（題材 × 改善点の対応表・各判定・トレードオフ・敗因の帰着先）は対象 repo の delivery 慣行（PR 本文かコメント）に残す

## 計測器を選ぶ

変更の性質で選ぶ。迷ったら重い側へ倒す — 軽い側の誤選択は、挙動に影響する変更を無検証で通す事故になる。

| 変更の性質 | 計測器 |
| --- | --- |
| ロード境界・分岐・既定値・判断基準を変えない表現整理 | **self-check** — candidate を通読し、意図しない意味変化・判断基準の変化・description（トリガー）への影響が無いことを確かめる |
| 挙動・判断・出力構造・既定値・reference のロード境界を変える | **blind A/B**（`references/ab-test.md`） |
| 内部機構（分類ルーティング・報告永続化・recheck 等、実行の流れと信頼性を変える変更） | **dogfood** — 候補を実タスクに走らせ、機構が働くか（分類・出力契約・統合整合）を観測する。単一実行の質の差に現れにくく A/B では wash しやすい。挙動の質に劣化リスクがある層は A/B で補う |
| 剪定（節・機構の削除、圧縮） | **ablation**（`references/ab-test.md`） |
| bank を持つ対象への、挙動に触れる後続変更 | 上のいずれかに加えて**回帰再走**（`references/scenario-bank.md`） |

複数の配布先（Claude Code / Codex CLI 等）に配られる対象で強モデル前提の書き方が疑われるときは、弱い側の実行条件でも 1 走確かめる（floor。低マージン判定の根拠になる）。

## 判定

評価するのは「**この指示に従うと開発の成果物・判断の質が高まるか**」（軸は `references/ab-test.md`）。手順や分岐が発火したこと自体は改善の根拠にしない — トリガー・分岐を変えたときの発火検証は、質を見る前提の健全性ゲートとしてだけ使う。

**採用**（改善が実挙動で観測できた）/ **低マージン採用**（強モデルでは差が出ないが floor として残す価値を説明できる）/ **不採用**（どちらも説明できない）。差が出ないときは、まず題材が改善を分離できているか（きわどさ・規模・名指し観点）を疑って設計し直す。再設計しても差が出なければ、低マージンか不採用かを正直に切り分ける。

**wash は剪定の合図。** 設計し直しても base ≒ candidate なら、その変更は不要ルールの疑いが濃い。挙動に現れない重い機構は本質だけ残して compact 化する — 指示過多は標準ケースの遵守率と出力品質を下げ、継ぎ足しの累積そのものが劣化要因になる。肥大が疑われる既存節には、wash を待たず ablation を能動的に当ててよい。

**A/B を採用ゲートに留めない。** 劣り / wash の失敗モードをトレースから特定して該当改善を作り直し、再検証する。観測した欠陥クラスを改善へ還元して質を引き上げる。

## 責務の境界

変更の正しさ（バグ・設計・セキュリティ・不変条件）のレビューは km-review の責務で、本 skill は「変更で開発の質が上がるか」の検証に絞る。**二層は相補的**で、A/B を通過しても km-review が静的な不変条件の綻び（統合・圧縮で落ちた load-bearing な gate 等）を捕まえることがある。採用前に両方を通し、A/B で gate 遵守を既に観測済みの層は correctness 側を軽量チェックに留めてよい。A/B と judge には実環境の subagent 機構を使う。新規 skill をゼロから作ること、assertion ベースの定量 eval を回すことは対象外。
