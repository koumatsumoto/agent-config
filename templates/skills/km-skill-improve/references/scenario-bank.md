# scenario bank（検証の記憶）

対象ごとに、**挙動を変えたときに何を測り直すか**と、その題材を蓄積するファイル。改善のたびに題材をゼロから設計して捨てる状態をやめ、後続の変更で回帰題材として再利用する。bank は「この資産が満たし続けるべき挙動」の実行可能な仕様集として機能する。

## 置き場

対象の**正本**が属する repo 直下の `evals/<対象名>.md`（例: `evals/km-plan.md`）。bank は runtime で読まれる資産ではなく、メンテナが改善を検証するための材料なので、配布対象のディレクトリには置かない。配布コピー側に bank を作らない。bank が無い対象への初回検証で、判定の根拠になった題材があれば新規作成する。

## 構成

3 節だけを置く。どれもコードから導出できず、実走で焼かれて初めて分かる情報に限る。

- **再走トリガ** — 「触った箇所 → 再走する題材」の対応表。変更のたびに、どの題材を回すかをここで引く
- **題材と合否線** — 1 題材 = 1 項目。タスクプロンプトの要旨・実行条件（sandbox・与える repo / diff・実行時前提）と、合否を分ける線（「〜が成果物に含まれる / 〜へ倒れない」）を再現に足る具体度で書く
- **落とし穴** — 題材構築・解釈で踏むと測定が濁る罠、wash になりやすい構造、観測された揺らぎ

**判定履歴を書かない** — 「版 M を走らせたら結果 N だった」は commit / PR に属する記録で、次の判断の参照点にならないうえ、挙動を変えるたびに書き直しが要る。bank に残すのは現在も成立すべき期待だけ。判定に使わなかった思いつきも書かない — bank の信頼性が回帰の価値を決める。

## 運用

- **読む** — 診断で必ず確認する。効く層と重なる題材が、回帰題材・ablation 題材の第一候補
- **書く** — 記憶の段階で、今回の判定の根拠になった題材と再走トリガを追記する。同じ層を検証する題材は統合し、重複を作らない
- **更新・退役** — 設計判断が変わって合否線が陳腐化したら、現行の期待に書き換えるか削除する
- **規模** — 1 対象あたり数題材に保つ。回帰再走のコストは bank の規模に比例するため、層の代表題材だけを残す

## 回帰再走

bank を持つ対象への後続変更で、過去に確立した挙動の退行を検出する。

- 再走トリガ表から**今回の変更が触れる層の題材**を選ぶ。全題材の再走はコストに見合わず、関連の無い題材は選ばない
- candidate 単独で再走し、bank の合否線を満たすかを確認する。base との比較は不要 — 合否線が絶対基準として既に確立している
- 満たさなければ退行。差し戻すか、合否線そのものが陳腐化した（設計判断が変わった）なら bank を更新・退役させる
