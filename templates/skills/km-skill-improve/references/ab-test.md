# blind A/B 運用テスト

base 版と candidate 版を素の subagent で実際に動かし、成果物の質を blind 比較して採否を決める。ablation と変異レースは同じ基盤の派生。

## サンドボックス契約

生成 subagent に与える権限・条件は**全題材・両版で統一する**。版ごとに違えば比較にならない。

- **可**: read-only のファイル調査（Read / Grep / Glob 等）
- **不可**: ファイル書き込み・git / gh・ネットワーク・その他副作用のあるコマンド実行・subagent 起動（対象が subagent を要求する場面は実行不能として記録させ、代行させない。代行させると資産でなく subagent の機転を測ることになる）
- 成果物（実行するはずのコマンド・生成する本文・下す判断）はテキストで返させる
- 「対象に書かれていないことは推測で足さない」を明示する — 測るのは資産の効果であって subagent の機転ではない
- ユーザーは応答できない。対象がユーザー確認を要求する場面では、確認文（質問・選択肢）を出力に残したうえで、置いた前提を明記して先へ進ませる
- **モデルは生成 2 体で同一、judge も含め全ラウンドで固定**する。既定はセッションの既定モデルで、ユーザー指定が常に優先。強モデルほど base が自力で補って wash に寄ることを織り込み、題材のきわどさを決める

## 生成に渡すもの

素の subagent 2 体を**同一メッセージで並列起動**する（独立・公平）。

- **役割を「対象が起動された状態の開発 agent」に置く** — 対象の指示に従ってユーザ依頼に対応させる。資産を*分析*させると成果物が出ず、比較対象が生まれない
- **対象一式だけを絶対パスで**渡す（references 込みで相対参照が解決できる形）。相手版の存在も比較目的も伝えない
- **読む順序を指定する** — 「まず SKILL.md を読み、SKILL.md が指示するタイミングで references を読む」。これを省くと references を先読みされ、ロード境界を動かした改善は base と candidate が同着になって測れない
- **タスクプロンプトは両版で同一**にする（対象 root のパスだけ差し替える）
- 実行時条件（今日の日付・対象 repo・分岐に効く前提）とサンドボックス契約を添える
- **最終報告に含めさせるもの**: 対象の出力契約から列挙した成果物（実行するはずのコマンド列 / 書き出すはずのファイルの完全な本文 / 下した判断 / ユーザーへの最終報告文）と、**挙動トレース**（どの reference をいつ読んだか・どの分岐を選んだか・ユーザー確認をどこで擬制したか）。成果物が同着でも「candidate の新記述が読まれたのか、読まれなかったのか」はトレースにしか現れない
- 完了通知にメトリクス（tokens / 所要時間）があれば、届いたつど記録する

## blind 化

judge に「どちらがどの版か」を漏らさないための機械的手順。

1. 生成結果を**成果物 + 挙動トレース**の 2 部構成で、題材 × 版ごとのファイルに保存する
2. judge 用に**中立ラベル**のファイルへ複製し、A / B への割り当ては題材ごと・ラウンドごとに入れ替える（base = A に固定しない）
3. 複製後に**リーク検査** — ファイル名・見出し・本文に版を推測させる語や orchestrator の私見注記が残っていないか、grep と目視で確かめる。成果物が長いなら judge にはファイルパスを渡して Read させる（inline 貼り付けは orchestrator の context を浪費する）

## judge に渡す契約

第三の subagent を、生成側と同じモデルで起動する。

- **どちらが base / candidate かは伏せ、提示順に意味がないことを明示する**（位置バイアス回避）
- 題材タスクと実行条件、対象が何のための資産か 1〜2 行、期待される正しい挙動があればそれ。成果物内の事実主張は対象 repo を read-only で参照して検証してよいと伝える
- 下の評価軸と、`scenario-design.md` で決めた名指し観点
- **返させるもの**: 評価軸ごとの優劣と根拠（成果物からの具体的な引用・参照を必ず添えさせる）/ 名指し観点ごとの A・B・同等 / 総合判定（A / B / 僅差。優劣を根拠をもって示せないときは無理に勝敗を付けず「僅差」と申告させる）/ 各版の長所・短所
- どちらがどの指示書によるかの推測はさせない。判定は成果物の質のみで行わせる

### 評価軸

- **目的達成** — ユーザーが本当に達成したいこと（ビジネス価値）を的確に捉え達成しているか
- **スコープ判断** — 扱う範囲の振り分け（同対応 / 後続 / 対象外）が過不足ないか
- **成果物の質** — 読み手がそのまま次工程に進める質か
- **手戻り / 事故リスク** — 無関係変更の混入・逸脱・停滞を招く判断がないか

## 判定と再走

- 名指し観点で candidate が勝ち総合が僅差なら、狙った改善は「観測できた」と扱ってよい（総合は他要因のゆらぎを含む）。逆に**総合で勝っても名指し観点に差が無ければ、狙った改善の証拠にはならない**
- **judge に丸投げしない。** 自分でも 2 成果物を評価軸で分析し、judge の結論も自分の結論も疑い、根拠を成果物とトレースで裏づけてから採用する。判定が割れたらなぜ割れたかを詰める
- judge が僅差を申告したとき、または judge と自分の判定が割れたときだけ、同条件でもう 1 対再走する。1 走の差はノイズと区別できず、全題材の複数回走行はコストに見合わない
- 統制題材での負けは、敗因が candidate の記述に帰着するか（→ 差し戻し対象）、走ごとに異なる content レベルの揺らぎか（→ 残存リスクとして bank に記録し判定を左右させない）をトレースで区別する

## unblind 敗因分析と差し戻し

判定が確定したら対応を明かし、優劣の原因を本文のどの記述かに帰着させる。「candidate のどの指示が効いたか / 効かなかったか（**読まれたのに従われなかったのか、そもそも読まれなかったのか**）」「base の何が不足を生んだか」を成果物とトレースから特定する — ロード境界の問題と記述の問題は直し方が違う。

- 観測された退行・曖昧さ・矛盾は candidate に反映する。**削り過ぎ（base にあった load-bearing な一文の喪失）が敗因なら、復元も差し戻しの一形態**
- どの記述にも帰着できない差（題材のゆらぎ等）は判定の重みを下げる
- **再走ラウンド** — 修正した candidate で該当題材を再走する。タスクは前ラウンドと同一、A / B の割り当ては入れ替え、モデルは固定のまま。何を直して何を確認するラウンドかを 1 行宣言してから走らせる

## 変異レース

構造の再設計を伴うとき、または前ラウンドで candidate が負けたときに、**仮説の異なる** candidate 2 案を base と同一題材で並列生成し、同じ judge に比較させる。

- 各案は異なる改善仮説を体現させる（同じ仮説の言い換え 2 案は無意味）。案の数は 2 が上限 — 3 案以上はコストに見合わず判定も割れやすい。ラベルは中立記号で、blind 化とリーク検査は A/B と同じ手順
- 負けた案が**特定題材でだけ**勝っていれば、その勝ち要素を勝ち案へ交叉し、交叉部分を含む題材で再測定する（交叉は無条件マージではない）

## ablation

「この節・機構は本当に成果物の質に寄与しているか」を測る。対象節だけを除去して参照整合を最小限直した版を candidate、現行を base として、同じ基盤で比べる。

- 題材は **bank の回帰題材のうち、当該節が採用の根拠になったもの**を最優先で使う。その題材で質が落ちなければ、節の存在理由が消えている
- 差が出なければ削除を採用する（wash = 剪定の合図の能動版）。差が出たら節は load-bearing — bank に「この題材が当該節の根拠」と追記して将来の再判定を安くする。一度に削るのは 1 つの節・機構に絞る（複数同時に削ると敗因を帰着できない）
