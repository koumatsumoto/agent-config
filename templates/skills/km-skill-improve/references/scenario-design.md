# 題材の設計

**candidate を書く前に**確定する。起草後に題材を作ると、candidate が通りやすい題材を無意識に選ぶ設計バイアスが入る。

## 共通原則

- **変更が効く層・分岐を狙う** — 変更しない層が単独で拾える題材は base / candidate が同着（wash）になる。改善が特定分岐でのみ発火するなら、題材をその分岐に倒す
- **きわどい題材を選ぶ** — base が既にこなせる無難なタスクでは差が出ない。その改善が一番効くはずの境界事例を選ぶ
- **成果物は対象の出力契約から定義する** — レビュー資産ならレビューレポート、計画資産なら計画書、コミット資産ならコミット分割とメッセージ。何を判定対象にするかを生成前に決める
- **測るのは統合版** — candidate は差分の継ぎ足しでなく、影響面を既存ごと統合・整理した最終版。継ぎ足し版を測ると全体整合の破綻を A/B が見逃す
- **統制題材を 1 つ混ぜる** — 対象の欠陥クラスに該当しない標準的な題材を両版で走らせ、改善が指示過多・過剰儀式（boilerplate な出力・不要な手続きの増加）で標準ケースを劣化させていないかを見る。採用時のトレードオフ確認はここで判定する
- **複数挙動に及ぶ変更は対応表を作る** — 各挙動を踏む題材に束ね、検証の網羅を確認する
- **bank を再利用する** — 対象に `evals/scenarios.md` があれば関連題材を回帰題材として組み込む。新設計するのは bank が覆っていない部分だけでよい
- **対象がレビュー系のとき** — 題材 = 仕込み欠陥入りの diff（両版共通）、base / candidate = 資産のバージョン。その資産でその diff をレビューさせ、出たレポートを比べる。継承すべき gate・不変条件が diff の外にあるなら対象 repo を read-only で与えて経路探索まで測る（diff に閉じると継承漏れ題材が両版とも拾えず wash になる）

## 変更タイプ別の要点

変更タイプは 4 つ。**①構造・既定値**（成果物の構造・既定挙動を変える）/ **②検出・判断**（見落とし検出・判断品質を上げる）/ **③効率**（探索・読み込み・手戻りを減らす）/ **④トリガー・分岐**（description・gate・レベル選択を変える）。

**①構造・既定値** — 標準の A/B でよい。既定挙動でない構造変化は差が出やすい。

**②検出・判断**

- **base floor を先に測る** — A/B に入る前に base を 1 回流し、base が取りこぼす（= 改善層が初めて効く）ことを確認する。base が既に拾うなら題材を作り直す（wash の未然防止）。floor を A/B 本走と同一のタスク・同一のサンドボックス契約で行ったなら、その成果物を A/B の base 側にそのまま再利用してよい（生成 agent 同士は状態を共有しないので独立性は保たれる）
- **仕込みはカモフラージュする** — 「重大な欠陥を置けば差が出る」ではなく「base が取りこぼす程度に subtle か」が題材の合否基準。(a) どの観点も強く所有しない死角に置く / (b) 無害な額面で警戒を下げる / (c) 局所では正しく見えるが全体を見ると問題になる
- 強モデルでは確定欠陥は両版が拾う。差は**不確実性処理の規律**（確定できない懸念を曖昧に hedge するか、覆す条件を名指しした構造化された保留にするか）に出やすい — 名指し観点として judge へ渡す
- **経済性・トリアージ系の改善は仕込みに階層を混ぜる** — 方針・feasibility を崩す欠陥と、実装後に安く直せる可逆な実装詳細級の欠陥を同一題材に混在させ、前者を捕捉しつつ後者を深掘りせず委譲できるか（労力配分）を測る。高影響（security / 秘密情報 / 不可逆 / 正しさ）を落としていないかも軸に含める

**③効率**

- **非効率が実害になる規模で測る** — 小さい題材は強モデルが力技で吸収して差が消える。探索予算の緩和なら「確認に上限超の読み込みが要る / 鍵ファイルが優先されにくい配置」の題材にする
- 探索・出典・コード前提に関わる改善は、実在する repo を read-only で調べさせて測る（架空の前提では実挙動を測れない）
- **コストを計測する** — 完了通知に tokens / 所要時間があれば各走で記録し、質と並ぶ判定材料にする（提供されない環境では読み込みファイル数・手順数の観察で代替する）

**④トリガー・分岐**

- 発火**すべき**入力と**すべきでない**入力の対を用意する。should-not は近接 near-miss（キーワードは重なるが別の対応が正しい依頼）を選ぶ。明白に無関係な入力は何も検証しない
- 発火検証は健全性ゲート。分岐を変えたのに意図どおり発火しなければ、質を見る以前に不採用

## 名指し観点

この改善が狙う具体挙動を、総合評価に埋もれさせないための個別比較観点。judge へ渡す。

検出・判断系なら「仕込んだ欠陥への言及の有無と扱いの質 / 過剰検出の不在 / 不確実性処理の規律」、構造系なら「期待する構造要素の有無と質」、統制題材なら「過剰儀式・boilerplate の不在」。
