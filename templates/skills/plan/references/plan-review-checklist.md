# plan-review-checklist.md

`.plan/` 計画ファイルを第三者目線でレビューするための観点・重大度定義・出力形式。km:plan Phase 3 で subagent またはメイン agent が読む。反映の反復・収束判定は orchestrator（SKILL.md Phase 3）が行い、本ファイルはレビュー自体の基準だけを管轄する。

## 基本観点（常に確認）

- 目的と成功条件が **検証可能** な形で書かれているか
- 実装者が追加判断なしで作業できるか（依存関係・未決事項・判断軸がそろっているか）
- 背景と設計判断の **理由** が残っているか（決定だけで理由のない箇所はないか）
- 制約・前提・非スコープが明確か
- 却下案と却下理由が書かれているか
- 実装手順が **依存順** に並んでいるか（不用意に並列化できる前提になっていないか）
- テストや検証方法が具体的か（"テストする" ではなく何を動かしてどう確認するか）
- 外部仕様や最新情報が必要な場合に **確認方針** があるか（最新性を cached 情報に依存していないか）
- GitHub issue に載せてもローカルファイル参照に依存しないか（`.plan/` を「元計画」「参照先」としてリンクしていないか）
- 複雑な構成や流れがある場合、Mermaid 図で説明した方が読み手に伝わるか
- 受け入れ済みリスクに重大度・残す理由・後続対応条件がそろっているか

## 高リスク時の専門家観点

計画の性質に合わせて追加する。すべてを必ず実施する必要はない。

- **セキュリティ**: 認証 / 認可、秘密情報、サプライチェーン、破壊的操作の扱い
- **データ移行**: スキーマ変更、バックフィル、ダウンタイム、rollback
- **インフラ / 運用**: デプロイ、CI/CD、運用手順、監視・アラート
- **API 契約**: 後方互換、versioning、クライアント影響、deprecation 手順
- **UX / docs**: ドキュメント整合、エンドユーザー向け文言、操作手順

## 重大度と対応

各指摘を次の 4 段階で判定する。

- `CRITICAL`: そのままだと計画が破綻する / 不可逆な事故を招く
- `HIGH`: 設計の前提が揺らぐ / 実装者が判断不能になる
- `MEDIUM`: 実装時に追加コストやリスクを生むが、計画の骨子は崩れない
- `LOW`: 読みやすさや細部の改善にとどまる

`CRITICAL` / `HIGH` は計画をそのまま進められない指摘、`MEDIUM` / `LOW` は進行可能だが改善余地のある指摘として返す。反復・収束判定・本文への反映・受け入れ済みリスク化は orchestrator（SKILL.md Phase 3）が行う。

## 出力形式

レビュアは本文を書き換えず、指摘だけを返す（反映は orchestrator が行う）。先頭に重大度別件数、続けて指摘を 1 件ずつ並べる。

```
CRITICAL: 0 / HIGH: 1 / MEDIUM: 2 / LOW: 0

## HIGH: [問題タイトル] [confirmed | likely | possible]
**対象箇所**: <節名や該当記述>
**問題**: 何が問題か（2-4 文で具体的に）
**修正案**: どう直すか（具体的に）
```

確信度ラベルは任意で付す: `[confirmed]` 計画記述から直接裏づく / `[likely]` 文脈依存 / `[possible]` 一般論として該当（実害は別途確認要）。

計画だけでは前提（コードベースについての「調査で分かった事実」等）の真偽を判定できない場合は、独立した「判定保留」セクションに **対象・何を確認すれば判定できるか・暫定見解** を書く。

指摘が無い観点は記載不要。指摘ゼロのときは `CRITICAL: 0 / HIGH: 0 / MEDIUM: 0 / LOW: 0`（指摘なし）と返す。
