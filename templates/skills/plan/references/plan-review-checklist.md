# plan-review-checklist.md

`.plan/` ファイルを対象にした agentic 計画レビューの観点集。

## 基本観点（常に実施）

- 目的と成功条件が **検証可能** な形で書かれているか
- 実装者が追加判断なしで作業できるか（依存関係、未決事項、判断軸がそろっているか）
- 背景と設計判断の **理由** が残っているか（決定だけで理由のない箇所はないか）
- 制約、前提、非スコープが明確か
- 却下案と却下理由が書かれているか
- 実装手順が **依存順** に並んでいるか（不用意に並列化できる前提になっていないか）
- テストや検証方法が具体的か（"テストする" ではなく何を動かしてどう確認するか）
- 外部仕様や最新情報が必要な場合に **確認方針** があるか（最新性を cached 情報に依存していないか）
- GitHub issue に載せてもローカルファイル参照に依存しないか（`.plan/` を「元計画」としてリンクしていないか）
- 複雑な構成や流れがある場合、Mermaid 図で説明した方が読み手に伝わるか
- issue URL 作成後の **2-step sync** が必要な場合、手順が計画に入っているか
- 既存 issue 更新を行う場合、ユーザーの明示指示と marker の有無が確認されているか

## 高リスク時の専門家レビュー候補

計画の性質に合わせて追加レビュー観点を足す。すべてを必ず実施する必要はない。

- **セキュリティ専門家**: 認証/認可、秘密情報、サプライチェーン、破壊的操作の扱い
- **データ移行レビューア**: スキーマ変更、バックフィル、ダウンタイム、rollback
- **インフラ / 運用レビューア**: デプロイ、CI/CD、運用手順、監視・アラート
- **API 契約レビューア**: 後方互換、versioning、クライアント影響、deprecation 手順
- **UX / docs レビューア**: ドキュメント整合、エンドユーザー向け文言、操作手順

## 重大度と対応

レビュー結果は次の 4 段階で記録する。

- `CRITICAL`: そのままだと計画が破綻する / 不可逆な事故を招く
- `HIGH`: 設計の前提が揺らぐ / 実装者が判断不能になる
- `MEDIUM`: 実装時に追加コストやリスクを生むが、計画の骨子は崩れない
- `LOW`: 読みやすさや細部の改善にとどまる

各指摘には **対象箇所・問題・修正案** を書く。

## Review Loop

- 最大 **2 pass** とする
- 1 pass 目で `CRITICAL` / `HIGH` が出たら plan 本文を修正し、2 pass 目で再確認する
- 2 pass 目でも `CRITICAL` / `HIGH` が残る場合、**GitHub issue 化を止め**、ユーザーに判断を委ねる
- `MEDIUM` / `LOW` は原則反映する。意図的に残す場合は plan 本文の「受け入れ済みリスク」相当の節に重大度・残す理由・後続対応条件を記録してから issue 化する
- 指摘の反映は plan 本文への直接修正だけにとどめる。レビュー履歴は plan 本文・issue body・issue comments のいずれにも残さない（最終計画と意図的な「受け入れ済みリスク」のみが残る）

## Multi-agent / Single-agent の使い分け

- multi-agent が使える環境では、別エージェントに `.plan/` ファイルをレビューさせる（メイン agent の視点バイアスを避けるため）
- 使えない場合はメイン agent が「第三者レビュー」と明示して同じ観点でレビューする。自分の計画を評価する自己矛盾を意識して、できるだけ critical に読む
