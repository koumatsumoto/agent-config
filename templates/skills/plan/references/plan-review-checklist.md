# plan-review-checklist.md

`.plan/` 計画ファイルを第三者目線でレビューするための観点・重大度・出力形式。著者バイアスを避けるため subagent（使えない環境ではメイン agent）が読む。反復・収束判定・本文反映は orchestrator（SKILL.md Phase 3）の責務で、本ファイルはレビュー基準だけを管轄する。

最も重要な問いは「**この計画が本質的に満たすべきもの（ユーザが本当に達成したいビジネス価値・要件）を正しく捉え、取り違えていないか**」。項目の存在チェックではなく、実コードベースに当てて推論する（前提は repo を読んで確かめる）。検証コストは欠陥の期待値に配分する: 出典付きの事実主張は、真偽が設計判断・作業単位の成否を左右する **load-bearing** なものを全数、その他をサンプル（目安 3 件）で照合し、労力は判断（Goal 取り違え・破綻箇所・スコープ）に集中させる。

## generalist レンズ（見落としを潰す）

- Goal が測定可能な anchor として明示され、DoD が合否判定でき反証可能か。"検証可能" なだけでなく "正しいもの" を測っているか。**anchor が内部整合しているか**（DoD が Goal に無い変更・撤去を要求していないか / Goal の約束をどの DoD も担っていない欠けがないか）
- goal ↔ 作業単位 ↔ 検証の双方向カバレッジ（DoD に紐づかない単位＝スコープ漏れ / どの単位・検証でも満たされない DoD＝抜け）
- 実装者が追加判断なしで進められるか。要件・スコープ・受け入れ条件・依存関係に曖昧・未確定・抜けがないか
- 背景・設計判断の理由・却下案・非スコープ・前提が押さえられ、issue 単体で読めるか
- 作業単位を実コードに沿って辿り、抜け・未定義・依存順の誤りが出ないか。検証方法が具体か

## adversary レンズ（敵対的分析）

計画を「正しい / 十分」と仮定せず、崩しにいく。

- **この計画は本質的要件を達成しない、という最強の論証を試みよ**。崩せなければ達成する理由を述べる
- 前提・事実主張を真偽判定する。出典付きは直接たどって確認し、出典の無い主張は「判定保留 / 要検証」とする
- 計画を実コードベースに対して頭の中で実行し、**最初に破綻 / 未定義になる箇所を 1 つ**具体的に示す
- 抜けた手順、順序の罠、最悪入力 / 異常系 / 不可逆操作への無防備を探す
- 計画が検討していない**最強の代替案を 1 つ**提示し、実際に優れているか評価する（steelman）

## 専門家レンズ（高リスク時のみ追加）

計画が触れる領域の観点だけ足す: **security**（認証・認可 / 秘密情報 / サプライチェーン / 破壊的操作 / LLM の tool・入力境界）、**architect**（公開 API・契約・スキーマ・データモデル・依存方向 — 覆すコストが高い不可逆判断は plan 時に捕まえるのが最安）、**データ移行 / インフラ運用 / 後方互換 / UX・docs**。

## 指摘の深掘り度（可逆性トリアージ）

計画時点はプロジェクトで最も情報が少ない。実装詳細（エッジケース・異常系の個別処理・パラメータ調整）をそこで詰めるのは、最も判断材料が乏しいときに最も細かい判断をすることになる。詰めるタイミングは詳細度でなく**可逆性**で決める。

まず**高影響カテゴリ**（security / 秘密情報 / 認証・認可 / 不可逆・広範囲な影響 / feasibility・正しさを壊す懸念）に触れないことを確認する。触れるなら実装詳細に見えても深掘りして通常の指摘にする（該当性の認識に要る調査を短絡で飛ばさない）。触れない実装詳細は 2 軸で判定する:

- (a) **方針変更性**: 間違っていたら方針・設計が変わるか
- (b) **手戻りコスト**: 実装後に発覚すると手戻りが大きいか（不可逆・広範囲・公開契約）

いずれか Yes なら通常の指摘として深掘りする。**両方 No なら調査・論証せず「実装時確認事項候補」として 1 行で列挙するに留める**（レビューコストは調査の時点で発生するため、調査そのものを断つ）。情報の多い実装後に委ねるほうが安く正確に決まる — 「不可逆判断は plan 時が最安」と同一原則の裏面。

## 重大度

- `CRITICAL`: 計画が破綻する / 不可逆な事故を招く / 本質要件を取り違えている
- `HIGH`: 設計の前提が揺らぐ / 実装者が判断不能になる
- `MEDIUM`: 実装時に追加コストやリスクを生むが、骨子は崩れない
- `LOW`: 読みやすさや細部の改善

`CRITICAL` / `HIGH` はそのまま進められない指摘、`MEDIUM` / `LOW` は進行可能だが改善余地のある指摘として返す。

## 出力形式

本文は書き換えず、指摘だけを返す（反映は orchestrator が行う）。先頭に重大度別件数、続けて指摘を 1 件ずつ:

```
CRITICAL: 0 / HIGH: 1 / MEDIUM: 2 / LOW: 0

## HIGH: [問題タイトル] [confirmed | likely | possible]
**レンズ**: generalist | adversary | security 等
**対象箇所**: <節名や該当記述>
**問題**: 何が問題か（2-4 文で具体的に）
**修正案**: どう直すか（具体的に）
```

- 確信度ラベルは任意: `[confirmed]` 計画・repo から直接裏づく / `[likely]` 文脈依存 / `[possible]` 一般論として該当
- 計画だけで前提の真偽を判定できないものは独立の「**判定保留**」セクションに、対象・何を確認すれば判定できるか・暫定見解を書く
- 可逆性トリアージで両方 No の実装詳細は独立の「**実装時確認事項候補**」セクションに、重大度を付けず 1 行ずつ列挙する（調査・論証はしない）
- 指摘ゼロのときは `CRITICAL: 0 / HIGH: 0 / MEDIUM: 0 / LOW: 0`（指摘なし）と返す
