# plan-review-checklist.md

`.plan/` 計画ファイルを第三者目線でレビューするための観点・重大度・出力形式。km:plan Phase 3 で、計画の著者であるメイン agent のバイアスを避けるため subagent（subagent が使えない環境ではメイン agent）が読む。反復・収束判定・本文反映は orchestrator（SKILL.md Phase 3）が行い、本ファイルはレビュー基準だけを管轄する。

計画レビューで最も重要なのは **「この計画が本質的に満たすべきもの（ユーザが本当に達成したいビジネス価値・要件）を正しく捉え、取り違えていないか」**。多角的に作り込むことより、本質を勘違いしていないかをまず問う。観点は「項目が存在するか」のチェックではなく、**実コードベースに当てて推論する**形で見る（前提は repo を読んで確かめる）。

レビューは 2 レンズで行う。

## generalist レンズ（見落としを潰す）

- **Goal（本質的要件・ビジネス価値）が測定可能な anchor として明示され、DoD が合否判定でき反証可能な形で成功条件を検証しているか**（"検証可能" であるだけでなく "正しいもの" を測っているか。的外れな成功条件になっていないか）
- **goal ↔ 手順 ↔ 検証のカバレッジに抜けが無いか**（DoD に紐づかない手順＝スコープ漏れ / 手順・検証で満たされない DoD＝抜け、の双方向を点検する）
- 実装者が追加判断なしで進められるか。要件・スコープ・受け入れ条件に曖昧・未確定・抜けはないか（依存関係・判断軸を含む）
- 背景と設計判断の理由、却下案と却下理由、非スコープ、前提・制約が押さえられているか
- 実装手順を実コードに沿って辿り、抜け・未定義・依存順の誤りが出ないか
- 検証方法が具体か（何を動かしどう確認するか）、最新性が要る箇所に確認方針があるか、issue 単体で読めるか

## adversary レンズ（敵対的分析）

計画を「正しい / 十分」と仮定せず、崩しにいく。

- **この計画は本質的要件を達成しない、という最強の論証を試みよ**。崩せなければ達成する理由を述べる。アプローチ自体が要件を取り違えていないかを疑う
- 計画の「前提」「調査で分かった事実」を真偽判定する。**出典（`file:line` 等）が付いていれば直接たどって確認し、出典の無い事実主張は「判定保留 / 要検証」とする**（偽なら指摘、計画だけで判定できないなら判定保留）
- 計画手順を実コードベースに対して頭の中で実行し、**最初に破綻 / 未定義になる箇所を 1 つ**具体的に示す
- 抜けた手順、順序の罠、最悪入力 / 異常系 / 不可逆操作への無防備を探す
- 計画が検討していない **最強の代替案を 1 つ**提示し、それが実際に優れているか評価する（steelman）

## 高リスク時の専門家レンズ（必要に応じて追加）

計画が高リスク領域に触れる場合だけ、該当観点を必要な分だけ足す。すべてを必ず実施する必要はない。

- **security**: 認証 / 認可、秘密情報、サプライチェーン、破壊的操作、LLM の tool 実行 / 入力境界
- **architect**: 公開 API・契約・スキーマ・データモデル・依存方向など、後から覆すコストが高い不可逆判断（plan 時に捕まえるのが最安）
- **データ移行 / インフラ運用 / API 契約 / UX・docs**: 該当する場合の移行・運用・後方互換・ドキュメント整合

## 重大度と対応

各指摘を次の 4 段階で判定する。

- `CRITICAL`: そのままだと計画が破綻する / 不可逆な事故を招く / 本質要件を取り違えている
- `HIGH`: 設計の前提が揺らぐ / 実装者が判断不能になる
- `MEDIUM`: 実装時に追加コストやリスクを生むが、計画の骨子は崩れない
- `LOW`: 読みやすさや細部の改善にとどまる

`CRITICAL` / `HIGH` は計画をそのまま進められない指摘、`MEDIUM` / `LOW` は進行可能だが改善余地のある指摘として返す。反復・収束判定・本文への反映・受け入れ済みリスク化は orchestrator（SKILL.md Phase 3）が行う。

## 出力形式

レビュアは本文を書き換えず、指摘だけを返す（反映は orchestrator が行う）。先頭に重大度別件数、続けて指摘を 1 件ずつ並べる。

```
CRITICAL: 0 / HIGH: 1 / MEDIUM: 2 / LOW: 0

## HIGH: [問題タイトル] [confirmed | likely | possible]
**レンズ**: generalist | adversary | security 等
**対象箇所**: <節名や該当記述>
**問題**: 何が問題か（2-4 文で具体的に）
**修正案**: どう直すか（具体的に）
```

確信度ラベルは任意で付す: `[confirmed]` 計画記述・repo から直接裏づく / `[likely]` 文脈依存 / `[possible]` 一般論として該当（実害は別途確認要）。

計画だけでは前提（コードベースについての「調査で分かった事実」等）の真偽を判定できない場合は、独立した「判定保留」セクションに **対象・何を確認すれば判定できるか・暫定見解** を書く。

指摘が無い観点は記載不要。指摘ゼロのときは `CRITICAL: 0 / HIGH: 0 / MEDIUM: 0 / LOW: 0`（指摘なし）と返す。
