# plan-template.md

`.plan/` に書き出す計画本文の **観点集**。固定テンプレートや必須セクション集ではない。セクション名・順序・粒度は計画ごとに調整する。

計画は内容が全て。読み手は他 AI か未来の自分である前提で、要約ではなく「なぜこの計画か」と「何を成功とみなすか」が分かる読み物として書く。

## 最低限含める観点

それぞれの計画で、以下の観点が落ちていないか確認する。落ちていても意図的ならよい。

- **何を達成する計画か**（目的・対象）
- **なぜその計画が必要か**（背景・問題・きっかけ）
- **何を成功とみなすか**（検証可能な受け入れ条件）
- **何をやらないか、今回の対象外にするか**（非スコープ）
- **調査で分かった重要な事実**（現状の前提・制約・依存）
- **主要な設計判断と、その理由**
- **検討したが採用しない選択肢と、その理由**（却下案）
- **実装や作業を進める順序**（依存関係を踏まえた手順）
- **どう検証するか**（テスト、静的解析、手動確認）
- **リスク、未決事項、受け入れ済みリスク**
- **GitHub issue に載せてもローカルファイル参照に依存しないか**
- **複雑な構成や流れがある場合、Mermaid 図で説明した方が読み手に伝わるか**

## 管理メタデータ

GitHub issue に全文ミラーする plan body には、`km:plan` 管理 issue を識別するための marker を入れる。

```markdown
<!-- km:plan:managed -->
```

marker はセクションではなく metadata として扱う。計画本文の先頭近く（タイトル直下など読み手を邪魔しない位置）に 1 行で置く。

## GitHub issue 全文ミラーを前提にした書き方

- `.plan/` ファイルへのローカルパスを「元計画」「source of truth」「参照先」として書かない。GitHub 読者は `.plan/` を読めない
- 画像やリンクは GitHub 上でも閲覧できるものだけを使う
- コードブロックは言語 tag を付ける（`bash`, `yaml` など）
- backtick を含むコマンド例を書く場合、`--body "..."` 経由での shell 展開を避けるため `--body-file` で渡す前提にする

## Mermaid 図の使いどころ

必須ではないが、以下のような場合は図解を検討する。

- 3 コンポーネント以上の構成 → `flowchart`
- 時系列のやり取り → `sequenceDiagram`
- 状態遷移が重要 → `stateDiagram`
- 責務境界やデータフロー → `flowchart` with subgraph

## 2-step sync に必要な記述

新規 issue 作成では URL が後から判明するため、以下を plan 本文に含めておく。

- issue URL の placeholder（issue 作成後に書き込む欄）
- issue title の案
- issue body = この plan 本文、という運用メモ（`km:plan` 自体の設計ドキュメントではない通常の計画では省略可）

## 受け入れ済みリスクの書き方

agentic review で出た `MEDIUM` / `LOW` を意図的に残す場合、以下を必ず記録する。

- 重大度（`MEDIUM` / `LOW`）
- 残す理由
- 後続対応条件（どのタイミングで再評価するか）

これを書かずに残したリスクは、レビュー loop で再提起される。
