# plan-template.md

`.plan/` に書き出す計画本文（= GitHub issue 本文）の観点集。固定テンプレートではなく、セクション名・順序・粒度は計画ごとに調整する。km:plan Phase 2 で本文を組み立てる前に読む。

計画 issue は実装 agent への**ゴール契約**として書く。読み手は他 AI か未来の自分で、issue 単体で「何を達成すべきか・何に依拠してよいか・何を守るべきか・どうなれば完了か」が分かれば、実装経路は読み手が自分で選べる。手順の逐一指定は契約の一部ではない — 経路を縛るのは、それ自体が制約（設計判断・依存順・不可逆性）であるときだけにする。

## ゴール契約の構成要素

各計画で以下が落ちていないか確認する。落ちていても意図的ならよい。

- **Anchor（冒頭に固定する 1 ブロック）**: 以降の手順・検証・レビューすべてが参照する基準点
  - **Goal** — 達成すべきビジネス価値・要件（目的・対象）
  - **Non-goal** — やらない・今回の対象外（スコープ境界）
  - **Definition of Done** — goal を満たしたと言える受け入れ条件を、合否判定でき反証可能な形で。"検証可能" なだけでなく "正しいもの" を測り、Goal と矛盾しない（Goal に無い変更を要求しない / Goal の約束を欠かさない）。今回の変更に固有の条件だけを書き、repo 全般の規範・delivery 一般条件は再掲しない。計画を左右する品質特性（性能・サイズ・保守性・トークン効率など非機能）があれば、その合否条件も DoD に含める。主要トレードオフは anchor でなく「設計判断」「却下案」に落とす
- **背景** — なぜこの計画が必要か（問題・きっかけ）
- **依拠する事実と前提** — 調査で分かった現状・制約・依存。各事実に出典（`file:line`・コマンド出力の要点）を付け、最新性が要る箇所は確認時点も残す。レビュアと実装 agent が再調査せず真偽を検証できる形にする
- **設計判断とその理由 / 却下案とその理由** — 実装 agent が同じ分岐で迷わない・別の道へ逸れないための制約
- **作業単位への分解** — 手順書ではなく「独立に検証できる作業単位」の列。各単位に受け入れ条件（**成果水準**で書く: 何が達成できていれば合格か。エッジケースの網羅列挙はせず個別の異常系は実装時確認事項へ）・検証・依存順を付け、どの DoD を満たすかを紐付ける。goal ↔ 作業単位 ↔ 検証の双方向で抜け（DoD に紐づかない単位＝スコープ漏れ / どの単位・検証でも満たされない DoD＝抜け）を潰す。1 issue を複数 PR に割るなら切れ目も示す
- **検証** — 何を動かしどう確認して DoD を証明するか（テスト・静的解析・手動確認）
- **リスク・未決事項** — 受け入れ済みリスクと実装時確認事項は下の書式で

## DoD の self-lint 基準（Phase 2 pre-write gate）

- **測定手続きの一意性**: 各 DoD が「何をどう実行して合否を判定するか」と一意な閾値を持つ。自作 DoD は第三者の反証者のつもりで読み、「これで不合格になる具体入力」を 1 つ挙げられなければヘッジ扱い
- **ヘッジ語を含めない**: 約 / おおむね / ほぼ / 十分 / 適切に / なるべく / 可能な限り / 基本的に / 一定の / 程度 — 閾値をぼかして反証を不能にする語。数量は境界値で書く（「50 文字以下」であって「約 50 文字」でない）
- **DoD ↔ 作業単位の双方向参照**: すべての DoD に担当作業単位があり、すべての作業単位が少なくとも 1 つの DoD または delivery 規約を参照する。DoD 非参照で正当な例外は km:github-workflow へ委譲する PR 作成・ブランチ操作・報告に限る。準備・調査だけの単位も、成果が下流の DoD に紐づくならその DoD を参照する
- **出典の再確認**: 出典付き主張は書き出し時点で引用先を開き、行番号・内容の一致を確認する（誤引用をレビューまで生き残らせない）

## issue 全文ミラーを前提にした書き方

- `<!-- km:plan:managed -->` marker を本文先頭近く（タイトル直下など）に 1 行で置く（km:plan 管理 issue の識別子）
- issue URL の placeholder を本文に用意する（2-step sync で作成後に書き込む）。issue title 案は本文に埋め込まず、`gh issue create --title` に渡す値としてチャットで提示する
- `.plan/` ファイルへのローカルパスを「元計画」「参照先」として書かない（GitHub 読者は読めない）。km:plan 内部の用語・phase 番号も本文に書かない（読者は skill を知らない）。画像・リンクは GitHub 上で閲覧できるものだけ。コードブロックには言語 tag を付ける
- 構成が複雑なとき（3 コンポーネント以上・時系列のやり取り・状態遷移・責務境界）は Mermaid 図を検討する

## 受け入れ済みリスクの書き方

レビューで出た `MEDIUM` / `LOW` を意図的に残す場合、**重大度・残す理由・後続対応条件**（いつ再評価するか）を記録する。これを書かずに残すとレビュー loop で再提起される。

## 実装時確認事項の書き方

可逆性トリアージ（plan-review-checklist.md）で「実装時に詰めるほうが安い」と委譲した項目の申し送り。計画時点で論証しない。

- 1 行の確認事項 + 手戻りが小さい根拠 1 行
- **消化規約**: 各項目を該当する作業単位の検証に紐付けるのを既定とする（作業単位が実行されれば消化される保証パス）。紐付けられないものは Phase 5 Report でユーザへ明示し、実装 PR の報告で消化結果を残す
- `CRITICAL` / `HIGH` 相当（計画が破綻 / 前提が揺らぐ）はここに委譲せず計画時に詰める
