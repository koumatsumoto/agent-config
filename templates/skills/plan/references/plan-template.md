# plan-template.md

`.plan/` に書き出す計画本文の **観点集**。固定テンプレートや必須セクション集ではない。セクション名・順序・粒度は計画ごとに調整する。km:plan Phase 2 で本文を組み立てる前に読む。

計画は内容が全て。読み手は他 AI か未来の自分である前提で、要約ではなく「なぜこの計画か」と「何を成功とみなすか」が分かる読み物として書く。

## 最低限含める観点

それぞれの計画で、以下の観点が落ちていないか確認する。落ちていても意図的ならよい。

- **Goal を測定可能な anchor として冒頭に固定する**（本質的に満たすべきものを取り違えのない形で計画本文の先頭付近に置き、以降の手順・検証・レビューが参照する基準点にする。次の 3 点を 1 ブロックにまとめる: **Goal**＝達成すべきビジネス価値・要件（目的・対象） / **Non-goal**＝やらない・今回の対象外（スコープ境界） / **Definition of Done**＝goal を満たしたと言える受け入れ条件を **合否判定でき反証可能な形** で。"検証可能" であるだけでなく "正しいもの" を測る。**計画を左右する品質特性**（サイズ・性能・保守性・トークン効率など非機能）がある場合は、その合否条件も DoD に含める。品質特性が争点にならない軽量計画には boilerplate な DoD を強制しない — 固定テンプレートでなく観点集として、計画を左右するものだけ落とす。Clarify Gate で確認する **主要トレードオフ**は anchor に含めず、下の「主要な設計判断」「却下案」の節に落とす）
- **なぜその計画が必要か**（背景・問題・きっかけ）
- **調査で分かった重要な事実・依拠する前提**（現状の前提・制約・依存。各事実に **出典（`file:line`・コマンド出力の要点など）** を付け、最新性が要る箇所は確認時点も残す。レビュアが再調査せず真偽を検証できる形にする）
- **主要な設計判断と、その理由**
- **検討したが採用しない選択肢と、その理由**（却下案）
- **検証可能な作業単位への分解と進める順序**（手順を「独立に検証できる作業単位」に分け、各単位に受け入れ条件・検証・依存順を付ける。各作業単位・各検証を **どの DoD を満たすか紐付け**、goal ↔ 手順 ↔ 検証の双方向の抜け（goal に紐づかない手順＝スコープ漏れ / 手順・検証で満たされない goal＝抜け）を潰す。**受け入れ条件は成果水準で書く**（何が達成できていれば合格か）— 網羅的なエッジケース列挙で書かず、個別の異常系は「実装時確認事項」へ回す。1 issue を複数 PR に割るなら切れ目も示す。実装 agent が再分解せず最初の単位から着手できる粒度にする）
- **どう検証するか**（テスト、静的解析、手動確認。何を動かしどう確認するか）
- **リスク、未決事項、受け入れ済みリスク**（および可逆性トリアージで委譲した項目があれば「実装時確認事項」。両者の書き方は下の個別節）

## DoD の self-lint 基準（Phase 2 gate）

km:plan Phase 2 の pre-write gate（SKILL.md）が DoD・作業単位に適用する 4 点の合否基準と判定例。検査項目の定義・合否例はこの節に一元化し、SKILL 側の gate はここを参照して適用する。

- **測定手続きの一意性**: 各 DoD が「何をどう実行して合否を判定するか」と一意な閾値を持つ。合格例:「3 ファイルを通読し相互参照先がすべて実在する」「grep で対象の 2 択列挙がゼロ件」。不合格例:「品質が高い」「おおむね網羅されている」（実行手続きも一意な閾値も無い）。**著者バイアス下限**: 自作 DoD は第三者の反証者になったつもりで読み、各 DoD に「これで不合格になる具体入力」を 1 つ挙げられなければヘッジ扱いにする
- **ヘッジ語（DoD に含めない）**: 約 / おおむね / ほぼ / 十分 / 適切に / なるべく / 可能な限り / 基本的に / 一定の / 程度。閾値をぼかして反証を不能にする語。数量は範囲でなく境界値で書く（「50 文字以下」であって「約 50 文字」でない）
- **DoD ↔ 作業単位の双方向参照**: すべての DoD に担当作業単位があり、すべての作業単位が少なくとも 1 つの DoD **または** delivery 規約を参照する。DoD 非参照で正当な例外は **km:github-workflow へ委譲する PR 作成・ブランチ操作・報告に限る**（この集合を閉じておき、DoD に紐づかない作業単位を delivery と誤ラベルして通さない。該当しないものはスコープ漏れ候補）。準備・調査だけの作業単位も、成果が下流の DoD 達成に紐づくならその DoD を参照する
- **出典の再確認**: 「調査で分かった事実」の出典付き主張（`file:line` 等）は、書き出し時点で引用先を開いて行番号・内容の一致を確認する（誤引用・行ズレをレビューまで生き残らせない）

## 管理メタデータ

GitHub issue に全文ミラーする plan body には、`km:plan` 管理 issue を識別するための marker を入れる。

```markdown
<!-- km:plan:managed -->
```

marker はセクションではなく metadata として扱う。計画本文の先頭近く（タイトル直下など読み手を邪魔しない位置）に 1 行で置く。

## GitHub issue 全文ミラーを前提にした書き方

issue body は `.plan/` ファイルの全文ミラーなので、ローカル環境を前提にした記述をしない。

- `.plan/` ファイルへのローカルパスを「元計画」「source of truth」「参照先」として書かない。GitHub 読者は `.plan/` を読めない
- 画像やリンクは GitHub 上でも閲覧できるものだけを使う
- コードブロックは言語 tag を付ける（`bash`, `yaml` など）
- backtick を含むコマンド例は、`--body "..."` 経由の shell 展開を避けるため `--body-file` で渡す前提で書く

## Mermaid 図の使いどころ

必須ではないが、以下のような場合は図解を検討する。

- 3 コンポーネント以上の構成 → `flowchart`
- 時系列のやり取り → `sequenceDiagram`
- 状態遷移が重要 → `stateDiagram`
- 責務境界やデータフロー → subgraph 付き `flowchart`

## 2-step sync に必要な記述

新規 issue 作成では URL が後から判明するため、本文側に issue URL の placeholder（issue 作成後に書き込む欄）を用意しておく。

issue title の案は本文に埋め込まない。本文は全文ミラーされるため、作業用メタデータを公開 issue 本文に残さない。title は `gh issue create --title` に渡す値としてチャットで提示する。

## 受け入れ済みリスクの書き方

agentic review で出た `MEDIUM` / `LOW` を意図的に残す場合、以下を必ず記録する。

- 重大度（`MEDIUM` / `LOW`）
- 残す理由
- 後続対応条件（どのタイミングで再評価するか）

これを書かずに残したリスクは、レビュー loop で再提起される。

## 実装時確認事項の書き方

計画レビューの可逆性トリアージ（plan-review-checklist.md）で「実装時に詰めるほうが安い」と判断して委譲した指摘を記録する。計画時点で論証せず、実装者への申し送りとして残す。

- 1 行の確認事項 + **手戻りが小さい根拠 1 行**（なぜ計画時でなく実装時でよいか）
- **消化規約**（silent drop を防ぐ）: 各項目を **該当する作業単位の検証に紐付ける**のを既定とする（plan 内で完結し、作業単位が実行されれば消化される保証パス）。紐付けられないものは Phase 5 Report でユーザへ明示し、実装 PR の報告で消化結果（どう確認・解決したか）を残す（実装者の自発性に依存する補助パス）
- `CRITICAL` / `HIGH` 相当（計画が破綻 / 前提が揺らぐ）はここに委譲しない。計画時に詰める
