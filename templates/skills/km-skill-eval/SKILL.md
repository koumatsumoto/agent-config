# Skill Evaluation

ユーザーが知りたい問いに答える最小限の証拠を集める。対象を編集せず、採否はユーザーと呼び出し元に委ねる。変更の正しさは`km-review`、改善案の起草・実装は通常の開発フローまたは`km-plan`が担う。

## 起動条件

評価の明示依頼（スキルの指名、A/B比較、シナリオテスト、回帰確認など）、または提示した評価案への同意がある場合だけ実行する。
AIから提案できるのは、変更効果の重要な不確実性が実走でしか解消できず、結果が意思決定を変えうる場合だけ。資産の変更、`evals/`の題材、A/Bの実行可能性だけを理由に起動・提案しない。通常の変更は完了確認と`km-review`で閉じる。

## 問いと方法

対象資産・比較する版・差分・関連する`evals/<target>.md`を確認し、問いを一つに定める。

| 問い | 方法 | 結論 |
| --- | --- | --- |
| 期待挙動が出るか | 変更後をシナリオで実行し、期待と照合 | `期待を満たした` / `期待を満たさなかった` / `判断保留` |
| 重要挙動を壊していないか | 関連する既存シナリオだけ再実行 | 同上。合意済みの要求・契約変更で古くなった期待は陳腐化として分ける |
| 以前より良いか・どの案が良いか | 比較評価を行う。評価案を書く前に`references/comparison.md`を読む | `A 優位` / `B 優位` / `同等` / `判断保留` |
| 参照・配布・構文・文言が整合するか | 実走せず静的・決定的に確認 | 確認結果と実走不要の理由 |

分類外の問いには差分に合う方法を設計してよい。変更後だけの成功は改善の証拠ではない。相対的な主張には比較評価を使い、相対差を問われていなければA/Bを足さない。

## 評価案

問い、方法と理由、シナリオ、評価軸と合否線、実行条件、走行数を実行前に示す。各シナリオは差分の具体的な仮説に対応させ、既存の関連項目を使うか、不足分だけ作る。一般的な品質確認や重複を足さない。
明示依頼済みで、低コストかつ解釈が明白なら同意待ちにしない。対象・問いが曖昧、比較や再走でコストが大きく増える、または解釈がユーザーのトレードオフに依存する場合だけ、推奨案を添えて確認する。

## 実行

- 対象版とシナリオを渡した分離コンテキストのsubagentで生成する。設計者自身の演技を証拠にしない
- skill本文の評価では`SKILL.md`から始め、referencesは指定時点で読む。rule・`CLAUDE.md`は実運用の読み込み方法に合わせる。起動判断の評価では本文を強制ロードせず、実際の選択用メタデータとユーザー依頼から始める
- 通常の推論・専門知識は禁止しない。未確認の事実・権限・観測結果を補って成功扱いせず、対象の制約を変えない。実行不能な操作は代行せず、そのまま記録する
- ユーザーが応答できないときは、対象に明示されたfallbackの範囲だけで続行し、確認文と採用前提を記録する。確認待ちで止まる契約なら、確認内容と停止位置を返して止める
- 成果物と、referenceを読んだ時点・選んだ分岐のトレースを返させる。未読と、読んだが従わなかった場合を区別する
- 必要な分離実行が使えなければ代行せず、評価案までを返して`判断保留`とする
- 初回で結論が明確なら再走しない。ノイズと差を区別できない場合だけ追加実行の価値を判断する

## 結論・報告

方法に応じた結論を、観測された挙動・成果物、成立範囲、限界とともに示す。単一走行から一般化せず、routing・計画の成功を実操作の成功にしない。契約どおりの停止は期待達成になり得るが、環境不足で必要な操作を観測できなければ`判断保留`とする。
固定テンプレートや常設保存先は作らず、問い、方法と十分な理由、シナリオ・評価軸・条件、観測結果と成果物、結論と成立範囲を報告する。保留・追加評価が必要なら、その理由と最小の次の対応を添える。
長い結果は一時ファイルに置いてよい。明示要求か納品上の必要がなければリポジトリの追跡対象にせず、自動採用・自動編集もしない。

## 回帰材料

`evals/<target>.md`は任意。今回の問いに関係する項目だけ読み、存在を理由に全件再走・毎回更新しない。今後も守るべき安定した挙動で、再利用価値の高いシナリオを新しく得た場合だけ記録を提案する。判定履歴は書かない。
