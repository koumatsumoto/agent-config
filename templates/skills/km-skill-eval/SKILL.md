# Skill Evaluation

挙動資産の効果には、実際に走らせないと確かめられないものがある。本 skill はその評価だけを担い、**ユーザーが明示的に求めたときだけ起動する**。

評価の重さは変更種別から機械的に決まらない。まず**ユーザーが何を知りたいか**を固定し、その問いに答えるだけの証拠を選ぶ。

## 起動条件

次のどちらかを満たすときだけ走る。

1. ユーザーが評価を明示的に依頼した（`km-skill-eval`の指名、A/B比較、シナリオテスト、回帰確認など）
2. AIが最小の評価案を提示し、ユーザーが実行に同意した

挙動資産を変更したことは起動理由にならない。通常の変更は完了確認と km-review で閉じる。

AI から提案してよいのは、**変更効果に重要な不確実性が残り、それが実走でしか解消できず、結果が意思決定を変えうる**ときだけ。資産を変更したこと・`evals/` に題材があること・A/B が実行可能であることは、いずれも提案理由にならない。提案を定例作業にしない。

## 評価フロー

### 1. 対象と問いを固定する

対象資産、比較する版、変更差分、あれば`evals/<target>.md`を確認する。そのうえで、ユーザーが知りたいことを一つの問いに落とす。

- **期待挙動** — 変更後に狙った挙動が出るか
- **既知回帰** — 既に守っている重要挙動を壊していないか
- **相対優位** — 版や案のどちらが、指定された目的で優れているか
- または対象固有の問い

参照整合・配布結果・文言のように静的かつ決定的に決着する問いなら、実走せずその理由を返す。

### 2. 最小の評価案を作る

問い / 選ぶ方法とその理由 / シナリオ / 評価軸と合否線 / 実行条件 / 必要な走行数を決める。

- 各シナリオは**変更差分の具体的な仮説**に対応させる。一般的な「品質確認」や重複したシナリオを足さない
- 既存シナリオは今回の変更に関係するものだけ使う。足りなければ、その場で専用のシナリオと評価軸を作る
- 比較評価を選ぶなら、**案を書く前に** `references/comparison.md` を読む。公平性の条件と比較軸が、そのまま評価案の実行条件になる
- 実行前に評価案をユーザーへ示す。明示依頼済みで、低コストかつ結果の解釈が明白なら、同意待ちで止めず続行してよい

改めて確認するのは、**対象や問いが曖昧** / **A/B・複数案・複数回走行でコストが大きく増える** / **結果の解釈がユーザーのトレードオフに依存する**ときだけ。推奨案を添えて聞く。

### 3. 実行する

問いに答える最小限だけ走らせる。

- **実挙動は分離したコンテキストで生成する。** 対象版とシナリオだけを与えたサブエージェントに走らせ、評価を設計したメイン担当が対象の挙動を自分で演じた結果を証拠にしない
- **読む順序を指定する** — 「まず `SKILL.md` を読み、`SKILL.md` が指示するタイミングで references を読む」。先読みされると、ロード境界を動かした変更は観測できない
- **対象に書かれていないことを推測で足させない** — 測るのは資産の効果であって、走らせた agent の機転ではない
- **実行できない操作を代行させない** — 実行不能として記録させる。ユーザーが応答できない条件では、確認文と置いた前提を出力へ残して先へ進ませる
- **成果物と挙動トレースの両方を返させる** — どの reference をいつ読んだか、どの分岐を選んだか。成果物が同じでも、「新しい記述が読まれたうえで従われなかったのか、そもそも読まれなかったのか」はトレースにしか現れない
- 必要な分離実行が使えない環境では、代行や推測で埋めず、評価案までを返して `判断保留` とする
- 初回で結論が明確なら再走しない。ノイズと結論を区別できないときだけ、追加実行の価値を判断する

### 4. 結論を出す

- 絶対評価: `期待を満たした` / `期待を満たさなかった` / `判断保留`
- 比較評価: `A 優位` / `B 優位` / `同等` / `判断保留`

根拠（観測された挙動と成果物）、結論が成立する範囲、限界を添える。単一走行から一般化しない。

対象は編集しない。採否はユーザーと呼び出し元が決める。必要な場合だけ、次に行う最小限の対応を示す。

## 方法を選ぶ

| 知りたいこと | 方法 |
| --- | --- |
| 変更後に期待した挙動が出るか | **シナリオ評価** — 変更後だけを、変更が効く具体的な場面で走らせ、期待挙動と照合する。トリガー・分岐・出力契約・内部機構・新規 skill の確認はここ |
| 既知の重要挙動を壊していないか | **回帰評価** — `evals/<target>.md` などの既存シナリオのうち、今回の変更に関係するものだけを変更後の版で再実行する。変更前との比較は要らない |
| 変更前より良くなったか / どの案が良いか | **比較評価** — `references/comparison.md` |
| 参照・配布・構文が整合するか | 実走しない。静的・決定的に確かめる |

上の分類に収まらない問いには、変更差分に合わせて方法をその場で設計してよい（実タスクでの試用、対象節を外した版との対比など）。方法名を増やすことが目的ではなく、問いへ直接答えられることを優先する。

**変更後だけの成功は「期待挙動を確認した」証拠であって、「変更前より改善した」証拠ではない。** 相対的な主張には比較評価が要る。相対差を問われていない場合は、A/B 比較を追加しない。

回帰評価で既存の期待が現設計と食い違うときは、失敗ではなく**期待の陳腐化**として報告する。

## 報告

固定テンプレートも常設の保存先も作らない。今回の判断を再検証できる範囲で次を含める。

- 評価した問い
- 選んだ方法と、その方法で十分な理由
- シナリオ・評価軸・実行条件
- 観測結果と、根拠になった成果物
- 結論と、それが成立する範囲
- `判断保留` または追加評価が要るなら、その理由と必要最小限の次の対応

長い生成結果は一時ファイルへ置いてよい。ユーザーの明示要求かdelivery上の必要がない限り、リポジトリの追跡対象にしない。

## `evals/` の扱い

`evals/<target>.md` は任意の回帰材料。

- 存在すれば、今回の問いに関係する項目だけ候補として読む
- 題材があることを理由に全件再走しない。評価のたびに更新しない
- 今後も守るべき安定した挙動を表す再利用価値の高いシナリオを新しく得たときだけ、記録を提案してよい
- 判定履歴は書かない

## 責務の境界

- 変更の正しさ（バグ・設計・不変条件・セキュリティ）は km-review。評価はこれを代替しない
- 改善案の起草・実装は通常の開発フロー、または km-plan
- 評価結果は意思決定の材料であり、自動採用でも対象の自動編集でもない
