# Quality Patterns

Phase 4（品質特性）の詳細パターン集。各カテゴリのアンチパターンと確認観点を示す。

## セキュリティ

### シークレット管理

- API キー・トークンのハードコード、`.env` の平文保存、ログへの機密情報混入
- Git 履歴へのシークレット残存

### 認証・認可

- エンドポイント/操作の認証欠如、リソースレベル認可の粒度不足
- セッション管理（有効期限、固定化対策）、パスワードハッシュ（bcrypt, argon2）

### 入力検証

- スキーマバリデーション未適用（Zod, Pydantic）
- ファイルアップロードの種類・サイズ制限、リダイレクト先のホワイトリスト検証

### インジェクション

- SQL: パラメータ化クエリ / ORM 未使用
- XSS: `dangerouslySetInnerHTML`、未エスケープ出力
- コマンド / パス / テンプレートインジェクション

### 暗号化

- 非推奨アルゴリズム（MD5, SHA1, DES）、非セキュア乱数生成
- TLS 未使用、保存時暗号化の欠如

### サプライチェーン

- 既知脆弱性パッケージ、ロックファイル未固定
- 依存関係混乱攻撃（npm: `@org/` スコープ未使用、PyPI: 内部名の未登録）

### デシリアライゼーション

- Python: `pickle.loads` / `torch.load`（`weights_only=True` 未指定）
- TS: `JSON.parse` 後の型未検証、prototype pollution（再帰マージの危険性）

### SSRF・競合状態

- ユーザー入力由来の HTTP リクエスト先、プライベート IP 未ブロック
- TOCTOU、トランザクション分離レベル

### ブラウザセキュリティ（Web）

- CORS 最小化、CSP、Cookie 属性（`HttpOnly`, `Secure`, `SameSite`）、CSRF

### 不正利用防止

- レート制限、大量データ操作の制限、リソース消費上限

## 信頼性

### エラーハンドリング

- 例外の握り潰し（`except Exception: pass`、空 `catch`）→ fail-open の原因
- Python: `raise ... from` で cause チェーン保持
- TS: neverthrow 等の Result 型で明示的エラーハンドリング

### リソース管理

- Python: `with` 文 / `contextmanager` でリソース解放を保証
- TS: `using` キーワード（Explicit Resource Management, TS 5.2+）で確定的クリーンアップ
- DB コネクション・ファイルハンドル・トランザクションの解放漏れ

### 並行性

- Python asyncio: 同期ブロッキング呼び出し（`requests.get` in async）、無制限タスク生成
- 共有ミュータブル状態への並行アクセス、ロック粒度の不適切さ
- 外部サービス障害: タイムアウト・リトライ・サーキットブレーカーの欠如

### 可観測性

- 重要操作（特に失敗パス）のログ欠如、文脈情報不足（リクエスト ID 等）
- 構造化ログ未使用（文字列結合のみ）
- 分散トレースのコンテキスト伝播途切れ

## 性能効率性

### アルゴリズム計算量

- ネストループ O(n²)（配列内線形探索 → Map/Set に変換）
- ソート済みデータの線形探索（二分探索が使える場面）
- 全件取得後フィルタ（DB/API 側でフィルタすべき）

### I/O パターン

- N+1 クエリ（バッチ取得・JOIN・DataLoader に変換）
- Python: async ハンドラ内の同期ブロッキング
- コネクションプーリングなしの繰り返し接続

### リソース管理

- 上限なしインメモリキャッシュ（LRU/TTL 必須）
- ページネーションなしの大量データ取得
- ストリーム処理可能なデータの全件メモリ展開
- Python: `all()`/`any()` にリスト内包表記（短絡評価が効かない → ジェネレータ式に）

### フロントエンド固有

- 不要な再レンダリング（deps 配列の誤り、オブジェクトリテラル毎回生成）
  - React Compiler 導入済みなら手動メモ化は不要
- バンドルサイズ: CJS 出力で tree-shaking 無効化、`import type` 未使用
- target 設定が低すぎるポリフィル肥大化

## 保守性

### コード品質

- 命名が意図を表現していない、ネストが深い（早期 return で簡潔化可能）
- 同一ロジックのコピペ、未使用コード・エクスポートの残存
  - TS: Knip でモジュール横断の dead export 検出
  - Python: vulture で未使用コード検出

### 型安全性

- TS: branded type で ID 型の混同防止（UserId / OrderId）、discriminated union で網羅的分岐
- Python: Pydantic strict mode で暗黙型変換を禁止、MyPy plugin で型安全性を担保
- バリデーション境界の明確化（外部入力は Zod/Pydantic で検証、内部は型を信頼）

### テストの有効性

- diff の変更を実際に検証していないテスト（形式的に存在するだけ）
- 実装詳細に依存（内部メソッド呼び出し回数 → 振る舞いを検証すべき）
- `toBeTruthy` / `assert result` のような曖昧なアサーション
- スナップショットテストの過剰使用

### テストの信頼性

- 共有ミュータブル状態への依存、実行順序依存
- 時刻依存（固定時刻を注入すべき）
- 外部サービスへの実通信（モック/スタブを使うべき）

### テストの保守性

- テストヘルパー/ファクトリの不使用（各テストで長大なセットアップ）
- テスト名が「何を検証しているか」を表現していない
- 1 テストで複数の無関係な振る舞いを検証

## 互換性

### 破壊的変更

- 必須パラメータの追加（既存クライアント破壊 → オプショナル化 or デフォルト値）
- レスポンス構造の変更（フィールド削除・型変更 → バージョニング or 段階的移行）
- エラーコード/ステータスコードの変更
- TS: エクスポート型の変更は MAJOR バージョン（semver-ts: "no new red squiggles" 原則）

### インターフェース設計

- 内部実装の API リーク（DB カラム名 → JSON フィールド）
- 一貫性のない命名（`getUserById` と `fetch_user_list` の混在）
- 過大な責務のエンドポイント

### エラー契約

- エラーレスポンス形式の既存パターンとの不一致
- HTTP ステータスコードの誤用（200 エラー、バリデーション失敗に 500）
- エラーメッセージへの内部情報漏えい（スタックトレース、DB スキーマ）
