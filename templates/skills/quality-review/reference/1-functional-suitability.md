# 機能適合性 (Functional Suitability)

ISO/IEC 25010:2023 の機能適合性に関するリファレンス。差分レビューでは「機能が足りないか」だけでなく、「呼び出し側が必要な情報や失敗意味を保てているか」を見る。

## 副特性ごとのアンチパターン + diff シグナル

### 機能完全性 (Functional Completeness)

- 既存画面 / API / CLI から呼べていた操作経路が消えている
- 新しい列挙値・状態・権限ロール・入力種別に対する分岐が足りない
- 監査、再試行、キャンセル、ロールバック、設定変更など運用上必要な機能が追加変更で落ちている
- 利用者が必要とするフィールド、ステータス、理由コード、メタデータが返らない

### 機能正確性 (Functional Correctness)

- 空値、null、ゼロ、最大値、部分失敗で振る舞いが崩れる
- リトライ可能なエラーと致命的エラーが区別されない
- HTTP ステータスや戻り値の意味が壊れている
- バッチ処理で一部失敗時の副作用や再試行方針が定義されていない

### 機能適切性 (Functional Appropriateness)

- 単純な目的に不要な手順や API 呼び出しを増やしている
- 類似機能間でパラメータ名・戻り値・挙動が不必要に揺れている
- 便利さ優先で安全性や正確性を損なう既定値を導入している

## surface 条件付き補助観点

- `HTTP API`: ステータスコード、理由コード、部分失敗の表現、エラー応答の一貫性を見る
- `async job / queue`: 冪等再実行時の意味、部分成功 / 部分失敗の扱いを確認する
- `CLI / developer tool`: help、exit code、dry-run、破壊的操作の導線が用途に対して適切かを見る

## false positive 注意

- 単なる内部リファクタリングで公開挙動が変わっていないなら、機能完全性の指摘を過剰に広げない
- 会話コンテキストや diff から要求が復元できない場合、要件不足を推測で断定しない
- エラー表現の好みだけで「不正確」としない。利用者契約が壊れるかで判断する
