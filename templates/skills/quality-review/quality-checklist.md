# Quality Review Checklist

品質特性レビューで使用するチェックシート。Tier ごとに確認の優先度が異なる。各チェック項目を順に確認し、結果をレポートに反映する。判断に迷う場合は `reference/` 配下の該当リファレンスを参照する。

## Tier 1: 常に確認

### セキュリティ (Security)

#### 機密性

- [ ] シークレット（API キー, トークン, パスワード）がコード・ログ・レスポンス・設定ファイル（`.env`, `.pem`, `.key` の Git 管理）に漏えいしていないか
- [ ] diff にシークレットの追加/削除痕跡がある場合、Git 履歴への残存リスクを認識しているか
- [ ] ログやエラーメッセージに PII・トークン・セッション ID が混入していないか
- [ ] レスポンスにスタックトレース・DB スキーマ・内部 ID などの内部情報が漏えいしていないか

#### 真正性

- [ ] リソースレベル認可の粒度は十分か（オブジェクト ID のオーナーシップ検証。IDOR 脆弱性の防止）
- [ ] セッション管理に固定化対策・有効期限・トークンローテーションがあるか
- [ ] 認証ミドルウェア/デコレータの適用漏れがないか（全エンドポイント・全操作経路）

#### 責任追跡性

- [ ] 重要操作（権限変更, データ削除, 設定変更）に監査ログが出力されているか
- [ ] ログにユーザー ID・リクエスト ID 等のコンテキスト情報があり操作者を特定できるか
- [ ] 監査ログの改ざん耐性: 通常のアプリケーションログと分離されており上書き不可能か

#### 否認防止

- [ ] 重要操作（決済, 承認, データ削除）に改ざん検知可能な監査証跡があるか

#### 完全性

- [ ] 外部入力にスキーマバリデーション（型・形状の検証）が適用されているか
- [ ] SQL インジェクション対策: パラメータ化クエリ/ORM を使用しているか（`$queryRawUnsafe`, f-string SQL 等の未使用）
- [ ] XSS 対策: `dangerouslySetInnerHTML`、テンプレートの未エスケープ出力（`| safe`, `{% autoescape false %}`）がないか
- [ ] デシリアライゼーション攻撃のベクトルが遮断されているか（pickle, yaml.load の Loader 未指定, prototype pollution による再帰マージ, JSON.parse 後の型未検証）
- [ ] SSRF のベクトルが遮断されているか（ユーザー入力由来の HTTP リクエスト先、プライベート IP/ループバック未ブロック）
- [ ] コマンド/パスインジェクションが防がれているか（`child_process.exec`, `subprocess.run(shell=True)`, ユーザー入力のファイルパスへの直接結合）

#### 耐性

- [ ] 認証エンドポイントと高コスト API にレート制限・リソース上限があるか
- [ ] アップロードサイズ・バッチサイズ・リクエストボディサイズの制限があるか
- [ ] 大量データ操作の制限: 全件削除・全件更新が単一リクエストで実行可能な設計になっていないか
- [ ] サプライチェーンリスク: ロックファイル固定、既知脆弱性パッケージの排除、npm `@scope` 未使用

#### 暗号化（実務補助）

- [ ] 非推奨アルゴリズム（MD5, SHA1 のハッシュ用途、DES, RC4）を使用していないか
- [ ] セキュリティ用途に非セキュア乱数（`Math.random()`, `random.random()`）を使用していないか
- [ ] パスワードハッシュは bcrypt / argon2 を使用し、ソルト付きか
- [ ] 平文通信がないか（TLS 未使用の外部通信、保存時暗号化の欠如）

#### ブラウザセキュリティ（実務補助、Web 変更がある場合のみ）

- [ ] CORS 設定: ワイルドカード (`*`) + credentials の組み合わせ、オリジン検証の欠如がないか
- [ ] Cookie 属性: `HttpOnly`, `Secure`, `SameSite` が設定されているか
- [ ] CSP: `Content-Security-Policy` が設定され、`unsafe-inline` / `unsafe-eval` が回避されているか

### 信頼性 (Reliability)

#### 無欠陥性

- [ ] 例外の握り潰し（`except Exception: pass`、空 `catch`）や fail-open パターンがないか。特に認証・認可チェックのエラー時にアクセス許可にフォールバックしていないか
- [ ] エラーの cause チェーンが保持されているか（Python `raise ... from`、TS エラーラッピング）

#### 可用性

- [ ] 単一障害点がないか（1 つの外部サービス障害でシステム全体が停止する設計）
- [ ] ヘルスチェック（readiness/liveness probe）が適切に設定されているか
- [ ] グレースフルシャットダウン（SIGTERM ハンドリング、in-flight リクエストの完了待ち）が実装されているか

#### 障害許容性

- [ ] 外部サービス呼び出しにタイムアウトが設定されているか（HTTP, DB, 外部 API）
- [ ] リトライに指数バックオフとジッターが設定されているか。非冪等操作のリトライが防がれているか
- [ ] 障害中の外部サービスへの継続的アクセスでカスケード障害が起きないか（サーキットブレーカーの欠如）
- [ ] バッチ処理の部分障害: 一部失敗時に全体ロールバックではなく、部分成功と失敗内訳を返せるか

#### 回復性

- [ ] リソース（DB コネクション, ファイルハンドル, トランザクション）がエラーパスでも確実に解放されるか
- [ ] 一時ファイル・一時テーブル・ロックのクリーンアップ漏れがないか
- [ ] リトライ時の冪等性: 二重処理を防ぐ冪等キーや重複チェックがあるか

#### 並行性（実務補助）

- [ ] 共有ミュータブル状態への並行アクセスが安全か（ロック, TOCTOU 競合）
- [ ] 無制限タスク生成がないか（セマフォ/ワーカープールでの並列数制限）
- [ ] トランザクション分離: 読み取り一貫性の欠如や lost update がないか

#### 可観測性（実務補助）

- [ ] 構造化ログが使用されているか（文字列結合のみではなく、リクエスト ID・ユーザー ID 等のコンテキスト付き）
- [ ] 分散トレースのコンテキスト伝播が維持されているか（HTTP ヘッダ/メッセージメタデータの転送）
- [ ] 重要なビジネス操作にメトリクス（カウンター/ヒストグラム）が計装されているか

### 性能効率性 (Performance Efficiency)

#### 時間効率性

- [ ] 不要な O(n²) や N+1 クエリ、全件取得後フィルタがないか
- [ ] 同期ブロッキング I/O がリクエストハンドラ内にないか（`fs.readFileSync`, `requests.get` in async）
- [ ] ソート済みデータの線形探索（→ 二分探索）、配列内線形探索（→ Map/Set）がないか

#### 資源効率性

- [ ] インメモリキャッシュに LRU/TTL 上限があるか、大量データを全件メモリ展開していないか
- [ ] ストリーム処理可能なデータの全件メモリ展開がないか（大規模 JSON/CSV の一括読み込み）
- [ ] コネクションプーリングなしの繰り返し接続（DB, HTTP クライアント）がないか

#### 容量充足性

- [ ] 大量データ取得にページネーション・バッチサイズ制限・バックプレッシャーがあるか
- [ ] 外部 API への同時接続数制限があるか（無制限の並列リクエスト防止）

#### フロントエンド固有（実務補助、Web 変更がある場合のみ）

- [ ] 不要な再レンダリング: deps 配列の誤り、オブジェクトリテラル毎回生成（React Compiler 導入済みなら手動メモ化は不要）
- [ ] バンドルサイズ: CJS 出力で tree-shaking 無効化、`import type` 未使用、動的 import 未活用

### 保守性 (Maintainability)

#### モジュール性

- [ ] 同一ロジックのコピペがないか（共通関数/モジュールへの抽出が必要な重複）
- [ ] 未使用コード/エクスポートが残存していないか
- [ ] 過大な関数/クラスに複数の関心が混在していないか（単一責任原則）
- [ ] 依存方向が逆転していないか（上位モジュールが下位の実装詳細に依存）

#### 再利用性

- [ ] 標準ライブラリや既存ヘルパーで代替可能な自前実装（ユーティリティの再発明）がないか
- [ ] 汎用処理がプロジェクト固有のコンテキストに密結合していないか

#### 解析性

- [ ] 意図が明確な命名、適切なネスト深度、マジックナンバーの定数化がされているか
- [ ] 暗黙的な依存がないか（モジュール初期化の副作用、グローバル状態への依存）

#### 修正性

- [ ] 変更の波及範囲が予測困難な設計になっていないか（1 箇所の変更が多数のファイルに影響）
- [ ] 設定とロジックが密結合していないか（ビジネスルールのハードコード）

#### 試験性

- [ ] テストは diff の変更を実際に検証し、実装詳細ではなく振る舞いをアサートしているか
- [ ] 曖昧なアサーション（`toBeTruthy`, `assert result`）がないか — 具体的な値を検証すべき
- [ ] テストの信頼性: 共有ミュータブル状態への依存、実行順序依存、時刻依存、外部サービスへの実通信がないか
- [ ] テストの保守性: テストヘルパー/ファクトリが活用されているか、テスト名が検証内容を表現しているか

#### 型安全性（実務補助）

- [ ] バリデーション境界が明確か（外部入力は Zod/Pydantic、内部は型を信頼）
- [ ] TS: branded type で ID 型の混同防止、discriminated union で網羅的分岐、`as` 型アサーションの乱用がないか
- [ ] Python: Pydantic strict mode、`Literal` 型での値制約、`TypeGuard`/`TypeIs` での型絞り込みが適切か

## Tier 2: 変更タイプに応じて確認

### 互換性 (Compatibility)

#### 共存性

- [ ] 共有リソース（ポート, 環境変数, キャッシュキー, キュー名）で他コンポーネントと衝突しないか
- [ ] 共存時の資源飽和: ワーカ数/プールサイズの過剰引き上げで他プロセスを圧迫しないか
- [ ] ローカル前提の衝突: 固定パス（`/tmp/app.sock`）、単一プロセス前提ロックがないか

#### 相互運用性

- [ ] 公開契約（API, CLI, 設定, DB スキーマ）に破壊的変更がないか。ある場合、バージョニングや段階的移行が用意されているか
- [ ] データ形式やプロトコルの変更が、受信側/送信側の双方で整合しているか（フィールド名, 日時形式, エンコード）
- [ ] プロトコル/認証の不整合がないか（ヘッダ名変更, 署名方式変更, HTTP ステータスコードの意味変更）

### 安全性 (Safety)

#### 運用制約

- [ ] 入力値に上限・範囲制約が設定されているか。unsafe なデフォルト（`debug=true`, `cors_allow_all=true`）がないか
- [ ] 設定値の妥当性が起動時にバリデーションされているか（不正な設定で静かに誤動作しないか）

#### リスク識別

- [ ] 破壊的操作や高コスト操作に確認・警告・dry-run があるか
- [ ] 閾値超過（上限値到達, リソース逼迫, 危険な設定値）で警告ログや UI 表示があるか

#### フェイルセーフ

- [ ] 障害時にシステムが安全な状態にフォールバックするか（fail-closed、トランザクション保護）
- [ ] エラー後にシステムが不整合な状態に留まらないか（状態マシンのリセット/ロールバック）

#### ハザード警告

- [ ] 危険な操作のログレベルは適切か（破壊的操作が INFO ではなく WARNING/ERROR で記録されているか）
- [ ] 不可逆操作やデータ損失リスクがある操作にユーザー向け警告メッセージがあるか

#### 安全な統合

- [ ] 外部 API レスポンスが実行時検証されているか（型アサーション `as`/`cast` のみではなく Zod/Pydantic でパース）
- [ ] 外部システム障害の考慮: 接続不能・タイムアウト・不正レスポンス・レート制限超過のハンドリングがあるか
- [ ] ウェブフック/コールバックの署名検証があるか（リプレイ攻撃への脆弱性防止）
- [ ] 外部 API のバージョン固定があるか（破壊的変更への耐性）

### 機能適合性 (Functional Suitability)

#### 機能完全性

- [ ] 変更後も必要な操作経路・出力・管理機能が維持されているか
- [ ] 新しい列挙値・状態・権限ロール・入力種別に対する分岐漏れがないか
- [ ] 呼び出し元や利用者が必要とするフィールド・ステータス・メタデータが返されているか

#### 機能正確性

- [ ] 境界値（空, null, ゼロ, 最大値）や部分失敗で正しく振る舞うか
- [ ] リトライ可能なエラーと致命的エラーが区別されているか
- [ ] HTTP ステータスコードが適切か（200 でエラー返却、バリデーション失敗に 500 等の誤用がないか）

#### 機能適切性

- [ ] 既存能力で達成できることに過剰な手順を強いていないか
- [ ] 類似機能間でパラメータ名・戻り値・挙動が不必要に揺れていないか

### 柔軟性 (Flexibility)

#### 適応性

- [ ] ハードコードされた値（URL, パス, ポート）が環境依存を生んでいないか
- [ ] OS 固有パス区切り文字の直接使用がないか（→ `path.join` / `pathlib`）
- [ ] ドキュメント化されていない環境変数への依存（デフォルト値未設定で起動時クラッシュ）がないか

#### スケーラビリティ

- [ ] スケーリング阻害要因（ステートフル前提, ローカルファイル依存, 単一インスタンス前提）がないか
- [ ] 分散環境で破綻する前提（グローバル変数での状態共有, インメモリキュー, プロセス内スケジューラー）がないか

#### 設置性

- [ ] 手作業前提の導入（暗黙の前提パッケージ, 順序依存のマイグレーション）がないか
- [ ] 更新/ロールバックが可能か（one-way migration, 後方互換性のない設定変更への対応）

#### 置換性

- [ ] 特定ベンダー/製品への不必要なロックインを強めていないか
- [ ] 依存逆転の欠如: 呼び出し側が具体実装を直接 new/import し、テストダブルや代替実装に差し替えにくくなっていないか

## Tier 3: 接点変更があるときだけ確認

### インタラクション能力 (Interaction Capability)

#### 適切度認知性・自己記述性

- [ ] 利用者は何ができるか・何を入力すべきかを見て理解できるか（ラベル, ヘルプ, エラーメッセージの自己記述性）
- [ ] コマンド名/ラベルが用途を明確に表現しているか（`run`, `exec`, `doit` のような不明瞭な名前がないか）
- [ ] エラーメッセージが原因と次の行動を伝えているか（内部コードのみ、処理中/成功/失敗の状態不明がないか）

#### 習得性・操作性

- [ ] 操作手順が不自然に複雑でないか（初期化→設定→実行の順序依存、同じ操作に複数の別名フラグ）
- [ ] キーボード/支援技術で操作可能か（`div` の `onClick` 不使用、フォーカス管理、セマンティック要素の使用）
- [ ] よく使う操作が深い階層に埋もれていないか、バッチ操作が提供されているか

#### ユーザーエラー防止

- [ ] 破壊的操作や誤入力に対する防止策（確認ダイアログ, バリデーション, Undo, 差分プレビュー）があるか
- [ ] フォーム入力制約（型, 範囲, 必須項目）のその場検証があるか

#### ユーザー支援・包摂性

- [ ] 回復支援（Undo, 再試行, 補助メッセージ, FAQ/ヘルプ導線）が提供されているか
- [ ] アクセシビリティ（`img` の `alt`, `aria-*`, 見出し階層, キーボード操作, 色覚差への配慮）に問題がないか
- [ ] 多言語/現場運用（ローカライズ不能な固定文言, 画面幅や端末制約の無視）が考慮されているか
