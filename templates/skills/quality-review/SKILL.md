# Quality Review

未コミット変更を対象に、ISO/IEC 25010:2023 の品質モデルに基づく非機能品質レビューを行う。

開発者は「仕様どおりに動くか」に集中しがちで、非機能品質特性（セキュリティ・信頼性・性能効率性・保守性など）は視野外になりやすい。本スキルはこれらを体系的に確認する。コードdiffから直接検出可能な観点を重視し、アーキテクチャレベルの懸念やツールで検出すべき問題は対象外とする。

関連: `/km:intent-review`（要件充足）, `/km:code-review`（設計・バグ・規約）, `/km:doc-review`（ドキュメント整合性）

## Workflow

1. **Phase 1: 変更把握・分類** — 変更ファイルを収集し、変更タイプとレビュー深度を決定
2. **Phase 2: 品質特性レビュー** — Tier 1 は全変更で確認、Tier 2 は変更タイプに応じて確認
3. **Phase 3: 偽陽性フィルタリング** — 検出項目を再評価し、ノイズを除外
4. **Phase 4: 判定と報告** — 重大度順に報告。`CRITICAL/HIGH` でコミットをブロック

## Phase 1: 変更把握・分類

`git diff --name-only` で変更ファイルを収集し、変更タイプを判定してレビュー深度を決定する。`docs` のみの変更は `/km:doc-review` に委譲する。

レビュー深度は 4 段階: **Full**(網羅的) / **Focused**(変更関連を重点的) / **Quick**(特定観点のみ) / **Skip**(省略)

| 変更タイプ | Tier 1 | Tier 2 |
|---|---|---|
| feat | Full | Full |
| fix | Focused | Focused |
| refactor | Focused | Quick |
| test | Quick | Skip |
| config/chore | Quick | Skip |

## Phase 2: 品質特性レビュー

必ず quality-patterns.md を読み込み、各特性のパターンに照らしてレビューすること。

ISO/IEC 25010:2023 の 9 品質特性を、コードdiffレビューでの実効性に基づき再構成している。互換性 (Compatibility) の確認観点は機能適合性（API契約・破壊的変更）と柔軟性（環境結合）に統合した。各特性の副特性はコードdiffから検出可能なものを選定しており、全副特性を網羅するものではない。

Tier 1 は全変更で確認、Tier 2 は変更タイプに応じて確認、Tier 3 は該当する変更がある場合のみ確認する。

### Tier 1: 常に確認する品質特性

#### 1. セキュリティ (Security)

副特性: 機密性, 完全性, 否認防止, 責任追跡性, 真正性, 耐性

確認の問い:
- この変更は認証・認可の境界を正しく維持しているか？ エンドポイントや操作にミドルウェア/デコレータの適用漏れはないか？
- 外部入力はすべてスキーマバリデーションを経てからロジックに到達しているか？ SQL, XSS, コマンド, パス, SSRF の各インジェクションベクトルは遮断されているか？
- 機密情報（トークン, 鍵, PII）がログ・レスポンス・Git 履歴に漏れていないか？
- 暗号・乱数の使用は現行推奨に沿っているか？（MD5/SHA1/DES/Math.random の不適切使用）
- 不正利用に対する耐性は考慮されているか？（レート制限, リソース上限, アップロードサイズ制限）
- 重要操作（権限変更, データ削除）の監査ログは記録されているか？

#### 2. 信頼性 (Reliability)

副特性: 無欠陥性, 可用性, 障害許容性, 回復性

確認の問い:
- エラーハンドリングは例外を握り潰さず、因果チェーンを保持しているか？ fail-open パターン（エラー時にアクセス許可にフォールバック）はないか？
- リソース（DB コネクション, ファイルハンドル, トランザクション）は確実に解放されるか？（Python: `with`/`contextmanager`, TS: `using`/`try-finally`）
- 外部サービス呼び出しにタイムアウト・リトライ（指数バックオフ）・サーキットブレーカーは設定されているか？ 非冪等操作のリトライは防がれているか？
- 並行処理で共有ミュータブル状態へのアクセスは安全か？ 無制限タスク生成はないか？
- 重要操作（特に失敗パス）の可観測性は確保されているか？ 構造化ログ、コンテキスト情報（リクエスト ID 等）、分散トレースの伝播は適切か？

#### 3. 性能効率性 (Performance Efficiency)

副特性: 時間効率性, 資源効率性, 容量充足性

確認の問い:
- 不要な O(n²) や全件取得後フィルタなど非効率なアルゴリズムはないか？ N+1 クエリ、同期ブロッキング I/O はないか？
- メモリ上限のないキャッシュ、ストリーム処理可能なデータの全件メモリ展開、コネクションプーリング欠如はないか？
- ページネーション・バッチサイズ制限・バックプレッシャー機構など、大量データに対する容量制御はあるか？

#### 4. 保守性 (Maintainability)

副特性: モジュール性, 再利用性, 解析性, 修正性, 試験性

確認の問い:
- 型安全性は適切か？（TS: branded type で ID 混同防止, discriminated union で網羅的分岐 / Python: Pydantic strict mode, Literal 型で値制約）
- バリデーション境界は明確か？ 外部入力は Zod/Pydantic で検証し、内部は型を信頼する原則が守られているか？
- テストは変更を実際に検証し、実装詳細ではなく振る舞いをアサートしているか？ 曖昧なアサーション（`toBeTruthy`, `assert result`）はないか？
- 同一ロジックのコピペ、未使用コード/エクスポート、過度に深いネストはないか？

### Tier 2: 変更タイプに応じて確認する品質特性

#### 5. 安全性 (Safety)

副特性（コードレビュー対象）: 運用制約, フェイルセーフ, 安全な統合

確認の問い:
- 入力値に上限・範囲制約が設定されているか？（バッチサイズ, ファイルサイズ, ループ回数, 再帰深度）unsafe なデフォルト（`debug=true`, `cors_allow_all=true`, タイムアウトなし）はないか？
- 障害時にシステムは安全な状態にフォールバックするか？ fail-open ではなく fail-closed が原則。トランザクション未使用による部分書き込み・データ破損のリスクはないか？
- 外部システムとの統合は防御的か？ レスポンスの実行時検証（型アサーションだけでなく）、タイムアウト、部分障害ハンドリング、ウェブフック署名検証は適切か？

#### 6. 機能適合性 (Functional Suitability)

副特性（コードレビュー対象）: 機能正確性, 機能適切性

確認の問い:
- API 契約は一貫しているか？ 同一リソースで異なるレスポンス構造、不統一なエラー形式、フィールド型のエンドポイント間不一致はないか？
- 破壊的変更が含まれていないか？ 必須パラメータ追加、フィールド削除、型変更、エラーコード変更（TS: エクスポート型変更は semver-ts "no new red squiggles" 原則）
- 境界値（空配列, null, ゼロ, 最大値）は正しくハンドリングされているか？ 部分的な失敗（バッチ処理で一部だけ失敗）のハンドリングはあるか？

#### 7. 柔軟性 (Flexibility)

副特性（コードレビュー対象）: 適応性, スケーラビリティ

確認の問い:
- ハードコードされた値（URL, パス, ポート, 上限値）が環境依存を生んでいないか？ ドキュメント化されていない環境変数への暗黙の依存はないか？
- スケーリング阻害要因はないか？ ステートフルな前提（セッションのメモリ保存, ローカルファイル依存）、単一インスタンス前提の設計（ローカルファイルロック）、プロセス間共有状態

### Tier 3: 限定的に確認する品質特性

#### 8. インタラクション能力 (Interaction Capability)

JSX/HTML の変更がある場合のみ確認する:
- アクセシビリティ属性（`aria-*`, `alt`, `role`）は適切か？ セマンティック要素が使われているか？
- ユーザーエラー防止（入力制約, 破壊的操作の確認ダイアログ）は考慮されているか？

## Phase 3: 偽陽性フィルタリング

報告前に各検出項目を再評価し、以下に該当するものは除外する:
- **既存の問題**: 今回の変更で導入されたものではない
- **ツール検出対象**: Linter・型チェッカー・フォーマッターで検出すべき問題
- **意図的な変更**: 会話履歴で明示的に合意された設計判断
- **未変更行の問題**: 変更されていない行に対する指摘
- **過度な指摘**: シニアエンジニアが指摘しないレベルの些末な問題

## Phase 4: 判定と報告

重大度:
- `CRITICAL`: 機密漏えい、認可欠如、任意コード実行、fail-open など即時悪用可能
- `HIGH`: 明確なバグ、仕様回帰、悪用可能な入力検証不足
- `MEDIUM`: 保守性低下、テスト不足、設計の不整合、不適切なエラー処理
- `LOW`: 微小改善

`CRITICAL` または `HIGH` を検出した場合、コミットをブロックする。

### サマリー（必ず冒頭に出力）

```
## レビュー結果

**変更分類**: feat (高リスク) | 変更行数: 450行 | ファイル数: 8
**検出件数**: CRITICAL: 0 / HIGH: 1 / MEDIUM: 2 / LOW: 1
**コミット判定**: ⚠️ BLOCKED（HIGH 以上の問題あり）
```

### 問題報告

問題ごとに以下の形式で報告する。確信度（`confirmed` = 確認済み / `suspected` = 疑い）を付与する。

```
## HIGH: 未検証の外部入力がクエリに使用されている [confirmed]

**場所**: src/api/users.ts:42
**問題**: リクエストパラメータ `sort_by` が検証なしに SQL ORDER BY 句に結合されている。攻撃者が任意の SQL フラグメントを注入できる。
**修正**: 許可されたカラム名のホワイトリストで検証する。
```
