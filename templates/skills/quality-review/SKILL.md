# Quality Review

未コミット変更を対象に、ISO/IEC 25010:2023 の品質モデルに基づく品質レビューを行う。

開発者は「仕様どおりに動くか」に集中しがちで、品質特性（セキュリティ・信頼性・性能効率性・保守性・機能適合性など）は視野外になりやすい。本スキルはこれらを体系的に確認する。コードdiffから直接検出可能な観点を重視し、diff から裏づけられない推測は扱わない。

関連: `/km:intent-review`（要件充足）, `/km:code-review`（設計・バグ・規約）, `/km:doc-review`（ドキュメント整合性）

## Workflow

1. Phase 1: 変更把握・分類
2. Phase 2: 品質特性レビュー
3. Phase 3: 偽陽性フィルタリング
4. Phase 4: 判定と報告

## Phase 1: 変更把握・分類

`git diff --name-only` で変更ファイルを収集し、変更タイプを判定してレビュー深度を決定する。`docs` のみの変更は `/km:doc-review` に委譲する。

レビュー深度は 4 段階: **Full**(網羅的) / **Focused**(変更関連を重点的) / **Quick**(特定観点のみ) / **Skip**(省略)

|変更タイプ|Tier 1|Tier 2|
|---|---|---|
|feat|Full|Full|
|fix|Focused|Focused|
|refactor|Focused|Focused|
|test|Quick|Quick|
|config/chore|Quick|Quick|

Quick の適用ルール:
- `test`: Tier 1 は保守性（試験性）, 信頼性（失敗パス・時刻依存・モック境界）, セキュリティ（危険なテスト用緩和）のみを重点確認する
- `config/chore`: Tier 1 はセキュリティ, 信頼性, 性能効率性、Tier 2 は互換性, 安全性, 柔軟性を優先確認する
- Quick では全特性を均等に見るのではなく、上記の優先観点に絞る。差分に根拠が見えない特性は原則スキップする

## Phase 2: 品質特性レビュー

Phase 2 実行前に必ず `quality-patterns.md` を読み込み、各特性のパターンに照らしてレビューすること。

ISO/IEC 25010:2023 の 9 品質特性を、コードdiffレビューで扱いやすい Tier に並べ替えている。ISO の品質特性そのものは統合・削除しない。各特性の副特性を核にしつつ、diff から判断しやすい実務補助観点を追加している。

システム全体の構成・運用・履歴確認が必要な懸念は、今回の diff や同一変更セットに直接根拠がある場合のみ報告する。根拠の弱い推測は報告しない。

Tier 1 は全変更で確認、Tier 2 は変更タイプと変更内容に応じて確認、Tier 3 はユーザー/運用者接点の変更がある場合のみ確認する。

### Tier 1: 常に確認する品質特性

#### 1. セキュリティ (Security)

副特性: 機密性, 完全性, 否認防止, 責任追跡性, 真正性, 耐性

確認の問い:
- この変更は認証・認可の境界を正しく維持しているか？ エンドポイントや操作にミドルウェア/デコレータの適用漏れはないか？
- 外部入力はすべてスキーマバリデーションを経てからロジックに到達しているか？ SQL, XSS, コマンド, パス, SSRF の各インジェクションベクトルは遮断されているか？
- 機密情報（トークン, 鍵, PII）がログ・レスポンス・Git 履歴に漏れていないか？
- 暗号・乱数の使用は現行推奨に沿っているか？（MD5/SHA1/DES/Math.random の不適切使用）
- 不正利用に対する耐性は考慮されているか？（レート制限, リソース上限, アップロードサイズ制限）
- 重要操作（権限変更, データ削除）の監査ログは記録されているか？

#### 2. 信頼性 (Reliability)

副特性: 無欠陥性, 可用性, 障害許容性, 回復性

確認の問い:
- エラーハンドリングは例外を握り潰さず、因果チェーンを保持しているか？ fail-open パターン（エラー時にアクセス許可にフォールバック）はないか？
- リソース（DB コネクション, ファイルハンドル, トランザクション）は確実に解放されるか？（Python: `with`/`contextmanager`, TS: `using`/`try-finally`）
- 外部サービス呼び出しにタイムアウト・リトライ（指数バックオフ）・サーキットブレーカーは設定されているか？ 非冪等操作のリトライは防がれているか？
- 並行処理で共有ミュータブル状態へのアクセスは安全か？ 無制限タスク生成はないか？
- 重要操作（特に失敗パス）の可観測性は確保されているか？ 構造化ログ、コンテキスト情報（リクエスト ID 等）、分散トレースの伝播は適切か？

#### 3. 性能効率性 (Performance Efficiency)

副特性: 時間効率性, 資源効率性, 容量充足性

確認の問い:
- 不要な O(n²) や全件取得後フィルタなど非効率なアルゴリズムはないか？ N+1 クエリ、同期ブロッキング I/O はないか？
- メモリ上限のないキャッシュ、ストリーム処理可能なデータの全件メモリ展開、コネクションプーリング欠如はないか？
- ページネーション・バッチサイズ制限・バックプレッシャー機構など、大量データに対する容量制御はあるか？

#### 4. 保守性 (Maintainability)

副特性: モジュール性, 再利用性, 解析性, 修正性, 試験性

確認の問い:
- 型安全性は適切か？（TS: branded type で ID 混同防止, discriminated union で網羅的分岐 / Python: Pydantic strict mode, Literal 型で値制約）
- バリデーション境界は明確か？ 外部入力は Zod/Pydantic で検証し、内部は型を信頼する原則が守られているか？
- テストは変更を実際に検証し、実装詳細ではなく振る舞いをアサートしているか？ 曖昧なアサーション（`toBeTruthy`, `assert result`）はないか？
- 同一ロジックのコピペ、未使用コード/エクスポート、過度に深いネストはないか？

### Tier 2: 変更タイプに応じて確認する品質特性

#### 5. 互換性 (Compatibility)

副特性（コードレビュー対象）: 共存性, 相互運用性

確認の問い:
- 外部 API, イベント, メッセージ, CLI, 設定ファイル, DB スキーマなど公開契約に破壊的変更はないか？ バージョニングや段階的移行なしに既存利用者を壊していないか？
- 他製品・他コンポーネントと情報交換する境界で、データ形式, 必須項目, 命名, ステータスコード, 認証方式の不整合はないか？ 受信側/送信側で相互利用できる形になっているか？
- 共通環境・共有資源を使う前提で衝突は起きないか？ ポート, ファイルパス, 環境変数名, キュー名, トピック名, テーブル名, キャッシュキー空間, CPU/メモリ消費で他プロダクトに悪影響を与えないか？

#### 6. 安全性 (Safety)

副特性（コードレビュー対象）: 運用制約, リスク識別, フェイルセーフ, ハザード警告, 安全な統合

確認の問い:
- 入力値に上限・範囲制約が設定されているか？（バッチサイズ, ファイルサイズ, ループ回数, 再帰深度）unsafe なデフォルト（`debug=true`, `cors_allow_all=true`, タイムアウトなし）はないか？
- 危険な操作や高コスト操作について、リスクの識別とユーザー/運用者への警告があるか？ 破壊的変更, 金銭影響, 物理デバイス制御, 大量送信/削除に確認や警告があるか？
- 障害時にシステムは安全な状態にフォールバックするか？ fail-open ではなく fail-closed が原則。トランザクション未使用による部分書き込み・データ破損のリスクはないか？
- 外部システムとの統合は防御的か？ レスポンスの実行時検証（型アサーションだけでなく）、タイムアウト、部分障害ハンドリング、ウェブフック署名検証は適切か？

#### 7. 機能適合性 (Functional Suitability)

副特性（コードレビュー対象）: 機能完全性, 機能正確性, 機能適切性

確認の問い:
- 変更後も、利用者や周辺システムが必要とする操作・入力経路・出力・管理機能は欠けていないか？ 既存機能の削除や分岐漏れで必要機能が失われていないか？
- 追加・変更された機能は、境界値（空配列, null, ゼロ, 最大値）や異常系を含めて正しく振る舞うか？ 部分的な失敗（バッチ処理で一部だけ失敗）のハンドリングはあるか？
- 似た機能に対して不自然に複雑な操作や迂回的な実装を強いていないか？ 既存能力で達成できるべきことを過剰な手順で実現していないか？
- 利用者や呼び出し元が期待する結果を返すための前提条件・エラー契約は明確か？ リトライ可能なエラーと致命的エラーの区別はあるか？

#### 8. 柔軟性 (Flexibility)

副特性（コードレビュー対象）: 適応性, スケーラビリティ, 設置性, 置換性

確認の問い:
- ハードコードされた値（URL, パス, ポート, 上限値）が環境依存を生んでいないか？ ドキュメント化されていない環境変数への暗黙の依存はないか？
- スケーリング阻害要因はないか？ ステートフルな前提（セッションのメモリ保存, ローカルファイル依存）、単一インスタンス前提の設計（ローカルファイルロック）、プロセス間共有状態
- インストール, デプロイ, 更新, ロールバック, アンインストールに不必要な手作業や暗黙の前提はないか？ 起動時設定の妥当性検証や安全なデフォルトはあるか？
- 特定ベンダー/製品への不必要なロックインを強めていないか？ 抽象化なしの SDK 直結, 独自データ形式固定, 差し替え不能な密結合はないか？

### Tier 3: 限定的に確認する品質特性

#### 9. インタラクション能力 (Interaction Capability)

UI, CLI, 管理画面, エラーメッセージ, スクリプト化されたオペレーション手順など、diff に直接現れるユーザー/運用者接点の変更がある場合のみ確認する。

副特性（コードレビュー対象）: 適切度認知性, 習得性, 操作性, ユーザーエラー防止, ユーザー関与, ユーザー支援, 包摂性, 自己記述性

確認の問い:
- 利用者は何ができるか・何を入力すべきかを見て理解できるか？ ラベル, ヘルプ, プレースホルダ, コマンド名, エラーメッセージは自己記述的か？
- 破壊的操作や誤入力を防ぐ設計になっているか？ 入力制約, 確認ダイアログ, Undo/再試行, 明確なバリデーションフィードバックはあるか？
- 繰り返し使う接点として不必要に不快・単調・負担が大きい設計になっていないか？ レイアウト, 文言, 反応性, フィードバックが継続利用を妨げていないか？
- 特定の利用者だけを前提にしていないか？ キーボード操作, スクリーンリーダー, 多言語, 色覚差, 現場運用の制約に配慮しているか？

## Phase 3: 偽陽性フィルタリング

報告前に各検出項目を再評価し、以下に該当するものは除外する:
- **既存の問題**: 今回の変更で導入されたものではない
- **ツール検出対象**: Linter・型チェッカー・フォーマッターで検出すべき問題
- **意図的な変更**: 会話履歴で明示的に合意された設計判断
- **未変更行の問題**: 変更されていない行に対する指摘
- **根拠不足**: システム全体の構成・運用・履歴確認が必要で、今回の diff からは裏づけられない推測
- **過度な指摘**: シニアエンジニアが指摘しないレベルの些末な問題

## Phase 4: 判定と報告

重大度:
- `CRITICAL`: 機密漏えい、認可欠如、任意コード実行、fail-open など即時悪用可能
- `HIGH`: 明確なバグ、仕様回帰、悪用可能な入力検証不足
- `MEDIUM`: 保守性低下、テスト不足、設計の不整合、不適切なエラー処理
- `LOW`: 微小改善

`CRITICAL` または `HIGH` を検出した場合、コミットをブロックする。

出力形式は `report-format.md` を参照。
