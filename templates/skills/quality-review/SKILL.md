# Quality Review

未コミット変更を対象に、ISO/IEC 25010 (SQuaRE) の品質モデルに基づく体系的な品質レビューを行う。

## レビューの重心

開発者は実装時に「仕様どおりに動くか」を意識して作業する。一方、非機能品質特性（セキュリティ・信頼性・性能効率性・保守性など）は実装者の視野外になりがちで、レビューで初めて発見される問題が多い。このスキルは ISO/IEC 25010 の8品質特性を軸に、コードの非機能品質を体系的に確認する。

関連スキル:
- `/km:code-review`: 要件充足・設計妥当性・バグ検出など開発観点のレビュー。本スキルとは観点が異なり、相互に補完する
- `/km:doc-review`: ドキュメントの整合性・正確性レビュー

## Workflow

1. **Phase 1: 変更把握・分類** — 変更ファイルを収集し、変更タイプを判定してレビュー深度を決定する
2. **Phase 2: 品質特性レビュー** — ISO/IEC 25010 の8特性を体系的に確認する
3. **偽陽性フィルタリング** — 検出項目を再評価し、ノイズを除外する
4. **報告** — 問題を重大度順に報告する。`CRITICAL/HIGH` があればコミットをブロックする

## Phase 1: 変更把握・分類

`git diff --name-only` で変更ファイルを収集し、変更タイプを判定してレビュー深度を決定する。`docs` のみの変更は `/km:doc-review` に委譲する。

レビュー深度は 4 段階: **Full**(網羅的) / **Focused**(変更関連を重点的) / **Quick**(特定観点のみ) / **Skip**(省略)

| 変更タイプ | Phase 2 |
|---|---|
| feat | Full |
| fix | Focused |
| refactor | Focused |
| test | Quick |
| config/chore | Quick |

## Phase 2: 品質特性レビュー

ISO/IEC 25010 の8品質特性に照らして変更を確認する。必ず quality-patterns.md を読み、各カテゴリのパターンに照らしてレビューすること。

### 1. 機能適合性 (Functional Suitability)

機能の正確性・完全性そのものではなく（それは `/km:code-review` の範疇）、品質の観点から確認する。

確認観点:
- API 契約の一貫性（同一リソースで異なるレスポンス構造、不統一なエラー形式）
- エラー処理の網羅性（happy path のみの考慮、異常系の未考慮）
- 境界値の扱い（空配列、null、ゼロ、最大値のハンドリング）

### 2. 性能効率性 (Performance Efficiency)

確認観点:
- アルゴリズム計算量（不要な O(n²)、全件取得後フィルタ）
- I/O パターン（N+1 クエリ、同期ブロッキング、コネクションプーリング）
- リソース管理（無制限キャッシュ、ページネーション欠如、ストリーム未使用）

### 3. 互換性 (Compatibility)

確認観点:
- 破壊的変更（必須パラメータ追加、レスポンス構造変更、エラーコード変更）
- インターフェース設計（内部実装の API リーク、命名の不一貫性）
- エラー契約（形式の不一致、ステータスコード誤用、内部情報漏えい）

### 4. 使用性 (Usability)

確認観点:
- API の使いやすさ（直感的でないパラメータ名、不必要に複雑な呼び出し手順）
- エラーメッセージの質（内部コードのみ、原因や対処法が不明）
- 設定のデフォルト値（unsafe なデフォルト、開発者を罠にかけるデフォルト）
- CLI/API の一貫性（同じ操作で異なるフラグ名、不統一な出力形式）

### 5. 信頼性 (Reliability)

確認観点:
- エラーハンドリング（例外の握り潰し、cause チェーンの欠如）
- リソース管理（DB コネクション・ファイルハンドル・トランザクションの解放漏れ）
- 並行性（同期ブロッキング、無制限タスク生成、共有ミュータブル状態）
- 可観測性（重要操作のログ欠如、構造化ログ未使用）

### 6. セキュリティ (Security)

確認観点:
- シークレット管理（ハードコード、ログ混入、Git 履歴残存）
- 認証・認可（エンドポイントの認証欠如、セッション管理）
- 入力検証・インジェクション（SQL, XSS, コマンド, パス）
- 暗号化（非推奨アルゴリズム、非セキュア乱数）
- サプライチェーン（脆弱性パッケージ、ロックファイル未固定）

### 7. 保守性 (Maintainability)

確認観点:
- コード品質（意図を表現しない命名、深いネスト、コピペ、未使用コード）
- 型安全性（branded type、discriminated union、バリデーション境界）
- テストの有効性・信頼性・保守性

### 8. 移植性 (Portability)

確認観点:
- ハードコードされたファイルパス・URL（環境ごとに異なる値の直書き）
- OS 固有の API 使用（Windows 固有パス区切り、Unix 固有コマンド）
- 環境変数への暗黙の依存（ドキュメント化されていない環境変数の参照）
- コンテナ化への障壁（ローカルファイルシステムへの強い依存、ポート固定）

## 偽陽性フィルタリング

報告前に各検出項目を以下のカテゴリに照らして再評価し、該当するものは除外する。開発者にとってノイズとなる指摘を減らすことで、真に重要な問題に集中できるようにする。

除外カテゴリ:
- **既存の問題**: 今回の変更で導入されたものではない（変更前から存在した問題）
- **ツール検出対象**: Linter・型チェッカー・フォーマッターで検出すべき問題（CI で別途検出される前提）
- **意図的な変更**: 会話履歴で明示的に議論・合意された設計判断
- **未変更行の問題**: 変更されていない行に対する指摘
- **過度な指摘**: シニアエンジニアが指摘しないレベルの些末な問題

## 判定と報告

問題の重大度を判定し、結果を報告する。

重大度:
- `CRITICAL`: 機密漏えい、認可欠如、任意コード実行、fail-open など即時悪用可能
- `HIGH`: 明確なバグ、仕様回帰、悪用可能な入力検証不足
- `MEDIUM`: 保守性低下、テスト不足、設計の不整合、不適切なエラー処理
- `LOW`: 微小改善

`CRITICAL` または `HIGH` を検出した場合、コミットをブロックする。

### サマリー（必ず冒頭に出力）

```
## レビュー結果

**変更分類**: feat (高リスク) | 変更行数: 450行 | ファイル数: 8
**検出件数**: CRITICAL: 0 / HIGH: 1 / MEDIUM: 2 / LOW: 1
**コミット判定**: ⚠️ BLOCKED（HIGH 以上の問題あり）
```

### 問題報告

問題ごとに以下の形式で報告する。確信度（`confirmed` = 確認済み / `suspected` = 疑い）を付与する。

```
## HIGH: 未検証の外部入力がクエリに使用されている [confirmed]

**場所**: src/api/users.ts:42
**問題**: リクエストパラメータ `sort_by` が検証なしに SQL ORDER BY 句に結合されている。攻撃者が任意の SQL フラグメントを注入できる。
**修正**: 許可されたカラム名のホワイトリストで検証する。
```
