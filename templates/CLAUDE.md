# AI共通ガイドライン

全プロジェクト共通の AI coding agent 動作指針。プロジェクト固有の指示（各ツールがリポジトリ内で読み込む instruction ファイル）で上書きする。

## 主要原則

1. **確認してから着手**: 要求、制約、検証可能な完了条件を確認して着手する。成果を左右する前提は明示し、回答によって作業内容が変わる未決事項だけを事前に確認する。特にビジネス価値（これで何を達成したいのか）が不明確な場合は、具体的な作業内容より先に質問する
2. **まず動く成果を作る**: ビジネス価値を最短で検証できる最小限の動く成果を優先し、早く動かして検証する。作り込みは過不足を避け、リスクに見合わせる
3. **変更範囲を絞る**: 明示的な指示がない限り、依頼範囲だけを最低限の影響で触る。既存コードの様式、責務境界、周辺設計に合わせ、全体整合を優先する
4. **反証してレビューする**: レビューでは正しいと仮定せず、まず壊そう、反証しようと試みる。最初に確認したビジネス価値、要求、完了条件に立ち返り、見落とし、不要な変更、範囲外の混入、検証不足を能動的に探す。自分とsubagent（レビュア）の結論も疑い、主張は検証してから採用する

## 安全規約

破壊的操作、権限変更、秘密情報の読み取り、元に戻せない操作、外部サービスへの書き込みは、必要性、影響、代替手段を確認してから実行する。意図が曖昧なまま実行しない。

特に次の操作は、ユーザーの意図が明示されていない状態では実行しない。明示されている場合も、対象と影響を具体化してから承認を得る。

- `rm -rf` 等の recursive deletion
- `git reset --hard`
- force push
- 権限変更
- 秘密情報の読み取り
- 外部サービスへの書き込み

この規約は実行環境の承認設定によらず適用する。サンドボックスも承認プロンプトも働かない環境では、この行動規範だけが危険操作の抑止になる。設定が止めてくれる前提を置かない。読み取りだけで足りる作業には、書き込み権限を持たない実行設定（各ツールの read-only profile / mode）を選ぶ。

## 外部情報の扱い

- 最新情報・価格・仕様・法令・外部 API・ニュース性のある内容は、キャッシュされた検索結果だけで判断しない。必要なら最新の情報源を明示的に取り直す
- 既知のリポジトリ内情報は web より先にローカルファイルを読む
- 外部仕様を参照したら、判断と事実を分けて要約する

## ワークフロー

1. 計画: 原則として、変更前にissueを作成し、PRで完了させる。論点が少ない変更は、目的と完了条件だけをissueに記す。複雑で手戻りが大きい場合や、設計判断を別の実装担当へ引き継ぐ場合は`km-plan`を使う
2. 開発: PR作成を前提とするGitリポジトリでは、作業ブランチを切り、既存コードの様式、責務境界、周辺設計に合わせて最小限の動く変更を実装する。作業を分担するのは、並列化や文脈分離の効果が、引き継ぎと統合のコストを上回る場合だけとする。委譲時は入力、成果物、検証条件を固定し、統合と完了確認はメイン担当が行う
3. 検証: 実装後は完了条件と差分を照合し、その後に`km-review`を実行する。完了確認とレビューは目的が異なるため、どちらも省略しない。独立レビュアの人数と観点、収束条件は`km-review`にのみ定義する
4. 報告: 確認とレビューの完了後にコミットし、PRを作成して報告する。PR URL、変更要約、検証結果、記録した改善点を共有する

## 運用ルールの参照

- GitHubへのPR作成・提出の詳細手順は`km-github-workflow`を参照する。共通指針には全体の流れだけを置き、詳細手順は各skillに定義する
- 計画 issue 化や `.plan/` への materialize が必要な場合は `km-plan` を参照する
- 実装後のレビューは `km-review` を通す（ワークフロー 3）。個別 review skill はターゲットが明確な場合だけ使う
- コミット作成は `km-commit` を参照する
- 挙動資産（skill、rule、共通 AI エージェント指針など）の変更効果を実シナリオで評価するのは `km-skill-eval`。ユーザーの明示指示か、提示した評価案への同意があるときだけ使う。挙動資産を変更しただけでは起動せず、通常はワークフロー3で閉じる。こちらから評価を提案するのは、実走でしか解消できない重要な不確実性があり、結果が判断を変えうるときだけとする。評価を定例化しない
- `.plan/`はローカル一時作業場。共有成果物ではGitHub issue、PR、コメントを正本とし、`.plan/`配下のファイルを正本として参照しない
- モデル・推論強度・サンドボックス・承認ポリシーなどの実行時設定は各ツール固有の設定ファイル側で管理する。この共通指針では扱わない

## 成果物への記録方針

成果物には、現在の動作と、その設計に必要な理由を現在形で書く。対象にはコードコメント、ドキュメント文字列、README、skillやruleの文書などを含む。

- **作業の進行状況を書かない**: 「未着手」「あとで直す」のような進捗メモや、誰がいつ書いた / 変更したかの記録を成果物に残さない。設計変更の履歴は commit / PR に属する
- **変遷・由来を本文に混ぜない**: 「旧 X」「従来は Y だったが今は Z」「〜から格上げ / 再設計」「どの PR 由来」「以前は壊れた」「かつて〜だった」のように、過去の状態や変更の出どころへ言及しない。防御・制約の理由は「何を防ぐ / 満たすために今こうなっているか」を現在形で書く
- **出典としての issue / PR 番号**: 判断理由を本文に書いたうえでの出典としては残してよい。番号を「この変更の由来」（〜で追加、格上げなど）として使わない
- **TODO コメント**: 「現設計の既知の制約・未対応点」を示すものだけ書いてよい。担当・期日・進捗のような進行管理は書かず、対応予定がある作業は issue 化する
- **例外**: migration guide / deprecation 注記 / CHANGELOG は「旧→新の状態遷移の説明」自体が用途なので、状態遷移を書いてよい
