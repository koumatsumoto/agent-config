# AI共通ガイドライン

## 主要原則

1. **確認してから着手**: 要求、制約、検証可能な完了条件を確認して着手する。成果を左右する前提は明示し、回答によって作業内容が変わる未決事項だけを事前に確認する。特にビジネス価値（これで何を達成したいのか）が不明確な場合は、具体的な作業内容より先に質問する
2. **まず動く成果を作る**: ビジネス価値を最短で検証できる最小限の動く成果を優先し、早く動かして検証する。作り込みは過不足を避け、リスクに見合わせる
3. **変更範囲を絞る**: 明示的な指示がない限り、依頼範囲だけを最低限の影響で触る。既存コードの様式、責務境界、周辺設計に合わせ、全体整合を優先する
4. **反証してレビューする**: レビューでは正しいと仮定せず、まず壊そう、反証しようと試みる。最初に確認したビジネス価値、要求、完了条件に立ち返り、見落とし、不要な変更、範囲外の混入、検証不足を能動的に探す。自分とsubagent（レビュア）の結論も疑い、主張は検証してから採用する
5. **実挙動で確かめる**: テストや実行環境、実データで確認できる事項は実際に動かして検証し、推測より観測結果を優先する

## 安全規約

破壊的・不可逆な操作、秘密情報の読み取り、外部サービスへの書き込みは、ユーザーの明示的な意図がある場合だけ実行する。読み取りだけで足りる作業では read-only の実行設定を使う。

## ワークフロー

1. **計画**: 原則として作業前にissueを作成し、PRで完了させる。論点が少ない作業は目的と完了条件だけをissueに記す。複雑で、誤方向に進んだ場合の手戻りが大きいときは`km-plan`を使う
2. **開発**: 作業ブランチを切り、既存コードの様式、周辺設計に合わせて最小限の動く成果を実装する
3. **検証**: 実装後は完了条件と差分を照合し、その後にread-only quality gateとして`km-review`を実行する。完了確認とレビューは目的が異なるため、どちらも省略しない。`PASS`なら提出へ進む。`BLOCKED`ならreviewを終了し、開発側でblockerの解消に必要な範囲だけを修正し、関連検証後に`km-review --recheck`で確認する。権限・要件内で安全に解消できない場合やユーザー判断が必要な場合は、`BLOCKED`として停止する
4. **提出**: `km-github-workflow`に従ってコミット・PR作成まで完了し、PR URL、変更要約、検証結果を報告する

## 記録方針

コードコメントやドキュメントには現在の動作と設計理由を書く。変更の経緯・作業履歴・過去状態は commit / PR に残し、現在の設計説明へ混ぜない。履歴自体を扱う CHANGELOG、migration guide、deprecation は除く。
